# What 1.0 means, and why this isn't it yet

**Status: ready — ADR 0025's gate is satisfied as of 2026-08-28.** This doc
exists so "when can we ship 1.0" has one place to answer it, instead of an
inference from scattered status lines across the README, `future-features.md`,
and the decision log.

## The gate

A `1.0.0` tag is a semver promise: the DSL and runtime API described in
[the DSL reference](docs/implemented/reference/index.md) won't change in a
breaking way without a major-version bump. That promise could not be made
honestly until
[ADR 0025](decisions/0025-the-dsl-names-one-idea-one-way-and-a-word-earns-its-place-by-being-used.md)
landed — a real, scoped, breaking redesign of exactly the surface a 1.0 tag
freezes:

- `has_many` / `has_one` / `belongs_to` are deleted outright (all three
  compile to `reference_to` today; nothing replaces them).
- `identified_by`'s three current forms (bare field, `ValueObject, as:`,
  block) collapse to one.
- Reference traversal gets its own `/` operator, splitting what `.` does
  today between "hop to another record" and "walk a field."
- The attribute type position loses the quoted-string and
  default-to-`String` forms — a bare constant becomes the only spelling.
- The closed-set wrapper block goes away in favor of an `attribute`
  keyword (`one_of:`) for the single-field case.

Every bluebook in the corpus used several of these before the migration.
Shipping 1.0 before this landed would have frozen syntax the project had
already decided to remove — the exact failure mode semver exists to prevent,
on day one of using it.

**So: 1.0 ships now that ADR 0025's sequenced plan has landed and the corpus
is migrated to the post-cleanup surface.** `docs/dsl-work-slices.md` tracks
every individual slice (S0a/S0b through S13, the full ADR 0025 scope); all
are DONE as of 2026-08-28, most recently S6 (events first-class) and S7
(reactions), which closed with the corpus's last ~128 `emits`/policy `on`/
saga-`transition`/`starts_on`/`ends_on` sites migrated from quoted strings to
bare constants. (S14–S18 are ADR 0026 scope, a separate decision record —
not part of this gate; S18 in particular is explicitly scoped but not
started, and does not block this tag.)

## What "the 1.0 DSL surface" will mean, once frozen

The [22 documented DSL contexts](docs/implemented/reference/index.md),
generated from the aggregate-local tables under `lib/hecks/language/` and
held equal to them by `spec/reference_golden_spec.rb` — post-ADR-0025. Every
construct in that reference, demonstrated in the example/framework corpus,
with a passing doctest. Nothing broader: a construct that exists in code but
has no corpus use and no doctest doesn't earn a stability promise just by
compiling (this is literally ADR 0025's own fourth principle — "a word
earns its place by being used" — applied to the release process, not just
the language).

**Explicitly not covered by the eventual 1.0 promise, even once it ships,
without a separate note when it happens:** anything in this README's
"Experimental or partial" or "Planned or research only" lists at the time
of the 1.0 tag. Concretely, as of 2026-08-27: query DSL aggregation
(doesn't exist), Rust codegen's `read_model` gap, Rails integration, Drivers,
a durable outbox (since shipped — ADR 0053, `Runtime::Outbox` — but the
adapter-host protocol and standalone relay it leaves open stay outside the
promise), and whatever ADR 0025 leaves for a later slice if it ships
in stages rather than all at once.

## What else has to be true first

Independent of ADR 0025, tracked here so this doc is the one place that
says "not yet, and here is the whole list," not just the DSL-syntax part:

1. ~~**ADR 0025 lands**, corpus migrated, docs regenerated.~~ **Resolved,
   2026-08-28.** The gate. All of S0a/S0b and S1–S13 are DONE per
   `docs/dsl-work-slices.md`, live-verified rather than trusted. Corpus is
   fully migrated to the post-cleanup surface — the last quoted-string
   `emits`/policy `on`/saga-`transition`/`starts_on`/`ends_on` sites (128 of

   this gate's scope. `docs/implemented/reference/*.md` regenerated and
   held equal to the live grammar by `spec/reference_golden_spec.rb`.
   Full gate green: rspec 2297/2297, model_check 0 errors, doc_coverage
   clean, rubocop 656/0 offenses, parser/codegen parity 40/40 and 8/8, real

   14/22 (the pre-existing Rust-runtime-projection-gap baseline) when this
   item was first verified; PR #433, merged the same day into this same
   release, closed that gap for real (`ProjectedFieldSpec`/`seeded_
   projections`/`SetProjectedField`, `rust/src/kernel/reference_lookup.rs`

   doesn't.~~ **Resolved, 2026-08-27.** `bin/fuzz --adapter sqlite|postgres`

   reference-hop query field (`owner/field`) can be *queried*, not just
   indexed, against a SQL adapter — turned out not to be a gap at all:
   `Runtime::ReferenceHop.apply` folds a hop where-clause into a synthetic
   local `in:` clause *before* any adapter ever sees it, for every engine
   alike, and `order_by` on a hop is refused at DSL-seal time regardless of

## Known gaps at 1.0

Passing the ADR 0025 gate is not the same claim as "no gaps exist." Three
are known, named here on purpose rather than left for someone else to
find later — see "Why this doc exists" below for why that matters more
here than in most projects:

1. ~~**Cross-tenant boot isolation was unwired at the 1.0.0 tag
   itself.**~~ **Resolved in 1.0.1.** `Runtime::TenantCheck
   .refuse_unless_tenant_capable!` existed and was directly tested
   (`spec/tenant_isolation_spec.rb`), but nothing called it — a second
   `Hecks.boot` of the same directory for a second tenant, bound to a
   non-`tenant_capable?` adapter (plain Postgres, no schema story), was
   not refused; both boots shared tables. Closed by wiring the check
   into `Bluebook::ProjectRegister#register`, the actual point where
   more than one tenant boot of a directory converges into one shared
   route table: a directory's SECOND registration is refused — its
   first never is, so an ordinary single-tenant deploy on a plain
   adapter is unaffected — before that second boot's routes ever merge
   in, so a leaking tenant's requests are never reachable through
   `Router#resolve` at all.
2. **Read models have no cross-engine agreement gate.**
   `ReadModelInterpreter#project` still silently forks between native
   SQL pushdown and an in-process Ruby loop, switched by declaration
   details (e.g. `group_by`) rather than checked for agreement. This is
   the layer that produces dashboard/query numbers; a divergence here
   doesn't refuse or crash, it just renders a wrong number.
3. **ADR 0037 Findings 3–5 are still `pending:`**, including a
   dangling-reference gap where `SafeDepositBox.Rent` refuses in Ruby
   but succeeds in Rust — a silent data-integrity divergence between
   the two runtimes a projection to WASM/Lambda would carry forward.

## Why this doc exists

Because the pattern that produced it — a status doc calling something fixed
that wasn't (the fuzzer/Memory-adapter gap), sitting next to a *different*
finding (H1, entity argument gate) that stayed silently broken past a point
its own audit narrative implied otherwise — is exactly the failure mode a
project whose whole thesis is "specification drift should be mechanically
impossible" can least afford to ship 1.0 with. One doc, updated when the
gate state actually changes, beats inferring readiness from five files that
each drift independently.
