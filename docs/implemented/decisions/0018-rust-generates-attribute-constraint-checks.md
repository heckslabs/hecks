# `admits:`/`pattern:` attribute constraints are generated, with a hand-rolled matcher for `pattern:`

**Status:** Accepted — implemented. `rust/project/constraints.rb`, `rust/src/kernel/pattern.rs`, branch `feat/rust-projection`. Closes two of the three distinct gaps 0017's own investigation surfaced (a closed-set `admits:` subset accepting an out-of-set member, and a `pattern:` regex constraint not checked at all) — the third (an `Integer` field accepting a non-numeric JSON string) turned out to be a real bug, not a missing feature, and was fixed separately (see Consequences).

## Context

Ruby's `Value.for_attribute`/`Value.build` coercion checks two attribute-level constraints neither prior slice generated: `admits:` (an attribute's value must be a member of a closed set declared *elsewhere*, named by a qualified string like `"Account::LedgerDirection"`) and `pattern:` (a scalar String attribute's value must match a declared regex source string). Both are declared on the SAME `IR::Attribute` shape wherever `attribute(...)` is called — a value object's own field (`EmailAddress.address, pattern: ...`) or an aggregate/command's own usage-level attribute (`ExternalTransfer`'s `direction, MovementDirection, admits: "Account::LedgerDirection"`) — and Ruby checks BOTH doors independently (`admission.rb`'s `check_admitted`/`check_patterns`, called from `Value.build` for a VO's own field; `admit_declared_set`, called from `coerce_declared_arguments`, for a command/entity-command argument's own usage).

## Decision

**`rust/project/constraints.rb`** is the shared module both doors call into: `scalar_field_expr` unwraps an attribute's value expression down to the scalar `admitted_scalar`/`check_patterns` actually operate on (bare already for a `String`-typed attribute, or the sole field of a single-field value object — Ruby's own "one-field holder" reading); `admitted_set_members` resolves `"Aggregate::SetName"` against the FULL domain IR (any aggregate, not just the current one — matching Ruby's own `chapter_of`/lazy same-chapter resolution, reusing `domain_generator.rb`'s existing `aggregates_by_name` table built for 0017's reference checks); `emit_admits_check`/`emit_pattern_check` emit the actual guard, with wording matching Ruby's `RefusalWording` templates exactly (`"{name} admits {admits} — {admitted} — got {offered}"`, `"{type}.{field} must match {pattern}, got {offered}"`).

**Corrected in place (V3, refusal arguments rendered from the vocabulary).** "Matching exactly" used to mean *reproduced*: both emitters baked a `tmpl_prefix_text` — the template's own words with every argument but the last already substituted, the member list already `.inspect`-quoted and joined — straight into the generated `format!`. That is the same hand-formatting BUG#134 was an instance of, one site over. Neither emitter spells the wording now: each hands its declared arguments to the site's own generated `<Variant>Args::render_args` (`InvariantViolationAdmitsDeclaredSetArgs`, `TypeMismatchPatternMismatchArgs` in `rust/src/kernel/vocab/refusal_template.rs`), which reads the template AND each argument's formatting rule — the member list's quoting and `", "` join included — off `Vocabulary::RefusalTemplate`/`Vocabulary::RefusalSiteArgument`, the same two tables Ruby's own `RefusalWording.render_site` reads. Leaving an argument out is now a Rust compile error rather than a silently short sentence.

Both doors call these: `types.rb`'s `emit_check_invariants` (the value-object's-own-field door) and `commands.rb`'s new shared `invariant_checks_for` (the command/entity-command-argument door, now used by both `emit_command` and `emit_entity_command` — previously near-identical duplicated logic). A LIST-typed attribute carrying `admits:`/`pattern:` — no real command in this corpus declares one — is skipped loudly (`constraint_list_problems`, wired into `command_skip_reason`) rather than silently dropping the constraint for that shape.

**`pattern:` needed a matcher, not just a data table** — a hand-rolled recursive-backtracking regex engine, `rust/src/kernel/pattern.rs`, zero Cargo dependencies (the same constraint `json.rs`/`expr.rs` already hold themselves to, per 0012). This is smaller than it sounds: `Hecks::Bluebook::PatternSubset` already REFUSES backreferences, Perl/POSIX classes, lookaround, atomic groups, and possessive quantifiers at bluebook-LOAD time, so by construction no pattern that ever reaches this matcher needs any of those — a plain recursive backtracking matcher over literals, `.`, `^`/`$`/`\A`/`\z` anchors, `[...]`/`[^...]` classes with explicit ranges, `*`/`+`/`?`/`{n}`/`{n,}`/`{n,m}` quantifiers, `(...)` groups, and `|` alternation covers the ENTIRE admitted dialect, not just the one pattern (`EmailAddress.address`'s own `^[^@ ]+@[^@ ]+\.[^@ ]+$`) the live corpus happens to declare.

## Consequences

- Verified on the full corpus: matching instances held at 31/35 (0017's own count), but the SPURIOUS-record count ("only in rust" — records Ruby refused that Rust wrongly created) dropped from 2 to 0 — `Banking::ExternalTransfer#ext-admits` (the `admits:` fix) and `Banking::Customer#CUST-0009/0010/0011` (the `pattern:` fix) are now correctly refused in Rust too.
- **The third 0017-surfaced gap — an `Integer`-typed JSON value (`DailyLimit.cents: "lots"`) accepted instead of refused — was NOT this kind of gap at all.** Investigating it found `scalar_from_json_expr`'s `default:` fallback branch conflated "key absent from JSON" with "key present but the wrong shape": `v.get(key).and_then(accessor).unwrap_or_else(|| default)` silently defaulted a wrong-typed value the same as a missing one. Fixed directly in `json_codec.rb` (a `match` on presence FIRST, so only the true-absent case ever reaches for the default) — a real bug fix, not new generated surface, and not written up as its own ADR since it's a one-line correction to existing 0014 machinery.
- The pattern engine's dialect coverage was verified against the ADMITTED synthetic test cases from `spec/corpus/fixtures/patterns.json` (`PatternSubset`'s own regression fixture) in addition to the live corpus's one real pattern — bounded repetition, optional groups, alternation, and `\A`/`\z` anchors all covered, not just what banking happens to use today.
- Full `bundle exec rspec` (1072 examples) and `bin/model_check` green; WASM artifact rebuilt and diffed against the Ruby oracle on the pinned CI fixture — same two pre-existing cosmetic gaps only (event payload formatting, refusal wording), no new ones.
- Role checking remains the one item left from 0014's original pair.

## Rejected alternatives

- **A `regex`-crate dependency.** Rejected on the same zero-Cargo-dependency precedent 0012 already set for `json.rs` — and unnecessary once `PatternSubset`'s own load-time restriction is taken seriously: the admitted dialect has no construct that needs backtracking-avoidance or a compiled NFA/DFA to handle correctly.
- **Hard-coding a check for the one live pattern (`EmailAddress.address`) instead of a general matcher.** Rejected as dishonest relative to what the IR actually declares — `pattern:` is a real, general mechanism; special-casing one instance would silently under-generate for the next bluebook author who writes a new one, exactly the failure mode `command_skip_reason`'s own "loudly, by name and reason" convention exists to avoid.
