# Entity commands, policies, and process managers/sagas join the Rust generator

**Historical:** the `rust/project/*.rb` generator and the `bin/project_*` scripts named below are gone; `docs/tools.md` maps each retired script to its `hecks` verb, and Rust generation now lives in `rust/codegen` (ADR 0086).

**Status:** Accepted — implemented. `rust/src/kernel/orchestrate.rs`, `rust/project/{commands,json_codec,reactions}.rb`, branch `feat/rust-projection`. Extends [0011](0011-rust-compiles-types-interprets-dispatch.md)'s "compile shapes, interpret behavior" split to three subsystems §8 explicitly left ungenerated.

## Context

§8's own "what this still does not generate" list named entity commands outright ("an entity's own commands... nothing here generates that addressing"). Policies and process managers/sagas weren't on §8's radar at all — the Rust generator only ever covered `CommandInterpreter`'s own `DISPATCH_ORDER`, not `Dispatcher`'s reaction plumbing (`PolicyInterpreter#react`, `SagaInterpreter#advance`) sitting one layer above it. The [0012](0012-wasm-via-wasi-stdio.md) WASM pass surfaced exactly how much this mattered: running `spec/corpus/banking.json` — the corpus explicitly designed to "exercise every declared banking command and query, including entities, read models, process managers, policies" — through the compiled artifact diverged on roughly half the corpus's aggregates, because Transfer/ScheduledPayment/OnboardingCase's own state never advances without a saga running, and `Account::LedgerEntry`/`ATMCard::Withdrawal`'s own commands didn't dispatch at all.

## Decision

**Port all three the same way [0011](0011-rust-compiles-types-interprets-dispatch.md) already ported command dispatch: compile the declared shape into generated data, walk it with a small hand-written, generic kernel function.**

**Entity commands** — `kernel::dispatch_entity` (`dispatch.rs`) is `EntityInterpreter#call`'s own, shorter `DISPATCH_ORDER`, generic over the parent record type `T` and the entity type `E`: no `Hydrate` branch (an entity command never creates), a `matches` closure in place of a bare `id` (an entity's own `identity()`, generated the same dotted-path-join convention `extract_id` already uses, just reading `self.` fields instead of JSON), copy-on-write element mutation, save/emit landing on the PARENT record (`docs/implemented/guides/entities.md`: "the SAME event log the parent's own commands write to"). `commands.rb`'s `emit_entity_command` mirrors `emit_command` closely enough to reuse `command_skip_reason`/`emit_mutation_line`/`lifecycle_transition_for` directly, passing the `entity` node in place of `aggregate` (same six-key IR shape) — the one real divergence, entity mutations writing into NON-`Option`-wrapped fields, is a new `optional:` parameter on `emit_mutation_line`, not a fork of it.

**Policies and process managers/sagas** share one mechanism — `kernel::orchestrate`, a direct port of `Dispatcher#dispatch`'s own reaction loop: dispatch a verb, and for every event it announces, recursively re-enter dispatch for whatever a matching policy or process-manager handler fires, bounded by the same `MAX_REACTION_DEPTH` Ruby enforces. `PolicyRule`/`ProcessManagerDef`/`Handler`/`DispatchSpec`/`WithValue` (`orchestrate.rs`) are the generated data; `reactions.rb` emits them from `ir[:policies]`/`ir[:process_managers]`, re-deriving `event_qualifier`/`event_name` from `on_event` the identical way `IR::Policy` does at Ruby's own runtime (`Naming.qualifier`/`Naming.unqualified`), and turning each `with:` binding's `IR.render_value`-spelled wire form back into either a `WithValue::Ref` (a Symbol) or a one-off generated `fn() -> Json` literal (`Marks.read`, the same inverse `bridging.rb` already trusts for a `then_set append:` literal).

## Consequences

- Verified on the full `spec/corpus/banking.json`: matching instances went from 0 (before any of this branch's work) to 28/35 — every remaining mismatch traced to a genuinely separate, pre-existing gap (below), not a defect in what this decision built. The Transfer settlement saga (request → debit → credit → settle) and its compensation leg (frozen destination → reverse) both reproduce Ruby's documented traces exactly, including balances.
- **Three real bugs surfaced only by actually running a saga, fixed as part of this work, not scoped out:**
  - `Json::dig` — a tolerant dotted-path walk (`json.rs`): a `Reference<X>` argument (Transfer's own `source`/`destination`) forwards as a bare string, not the wrapped `{"value": ...}` shape `identified_by` expects; Ruby's `Value.for_attribute` coerces this implicitly, so `extract_id`/`correlates_by` resolution needed to as well.
  - Default-value fallback in `from_json` (`json_codec.rb`): `PositiveMoney.currency` has a declared default (`"USD"`); `Transfer`'s own `amount` type has no currency field at all, so a saga leg forwarding it needs the TARGET type's default filled in, the same way `Value.build` does.
  - `extract_id`'s THREE-tier identity resolution and a generated `reference_key_for_aggregate` table, both porting `CommandInterpreter#hydrate`'s real chain (`identity_of || identity_from(:id) || identity_from(reference_key(command))`) and `Correlation#saga_correlation`'s own fallback tiers — `Transfer.Debited`/`.Credited`/`.Settle` all address themselves through a `transfer:` argument (`Naming.reference_key`), not `identified_by`'s own `reference` field, and the events they announce carry only `transfer:`, so downstream correlation needs the identical fallback.
  - `Event.payload` moved from a per-command `args.to_json()` to the router's own raw, unfiltered `args_json` (`registry.rb`'s `stamp_payload`) — closes 0012's own residual payload gap for free AND is load-bearing here: a saga leg forwarding an undeclared identity argument (`Account.Credit`'s `number:`) needs it to survive onto the announced event for a LATER leg to read.
- Entity commands, policies, and process managers do NOT get a reaction/saga LOG (`reaction_log`/`saga_log`) — nothing in `bin/rust_conformance`'s comparable surface (`instances`/`events`/`refusals`) reads it, so it was deliberately not built. A real, separate gap if a future need wants to inspect it.
- `Correlation#saga_correlation`'s middle tier (an explicit `event.correlation` stamp `Dispatcher#reenter` writes when `saga_correlation:` is passed) is NOT ported — only tiers 1 (current event's own payload) and 3 (`reference_key_for_aggregate`) are. No handler in either example domain needs the middle tier; a future one might.
- Cross-domain policies (`across` a domain this single-domain `Store` never generated) are omitted from the generated table entirely, not represented-and-refused — verified this matches Ruby's own observable behavior for this corpus specifically (no `Compliance`/`Notifications` bluebook exists anywhere in the repo, so Ruby's own `PolicyInterpreter#deliver` already refuses these the same way).
- **Two known, pre-existing gaps remain, both surfaced (not introduced) by finally running the full corpus:** an empty list attribute round-trips as `[]` in the generated JSON, where Ruby's own record state can hold `nil` for one never appended to; and `refuse_unknown_arguments`/`refuse_absent_arguments` (§8's kernel comment: "structurally impossible" for a compiled Rust args struct) is genuinely bypassed at the JSON boundary specifically, since `from_json` silently ignores an extra key rather than refusing the whole command the way Ruby's dynamic hash-shaped args do.

## Rejected alternatives

- **A second, bespoke Rust function per command/policy/handler shape**, the same 0011 already rejected for ordinary commands. Not reconsidered here — the generic-kernel-plus-generated-data split converged on the first real domain (Banking, not a toy) exactly the way 0011 predicted it would for anything shaped like `DISPATCH_ORDER`.
- **Reproducing the reaction/saga log byte-for-byte.** Would have roughly doubled the surface area of `orchestrate.rs` for data nothing in the differential harness reads. Deferred, not rejected — a real future need should build it, not work around its absence.
