# Unknown/absent-argument checking joins the JSON boundary

**Historical:** the `rust/project/*.rb` generator and the `bin/project_*` scripts named below are gone; `docs/tools.md` maps each retired script to its `hecks` verb, and Rust generation now lives in `rust/codegen` (ADR 0086).

**Status:** Accepted — implemented. Historical: `rust/project/` is gone; generation lives in `rust/codegen` (ADR 0086). `rust/src/kernel/json.rs`, `rust/project/json_codec.rb`, branch `feat/rust-projection`. Closes one of the two gaps [0013](0013-rust-generates-entities-policies-sagas.md) flagged as still-open; the other (empty-list-vs-nil) turned out to be the SAME root cause as a new gap this pass found, not independently fixable — see below.

## Context

0013's own Consequences named this directly: "`refuse_unknown_arguments`/`refuse_absent_arguments` (§8's kernel comment: 'structurally impossible' for a compiled Rust args struct) is genuinely bypassed at the JSON boundary specifically, since `from_json` silently ignores an extra key rather than refusing the whole command." Running the full `spec/corpus/banking.json` against this gap live surfaced two real, separate bugs, plus one bigger gap this pass chose NOT to reach into.

## Decision

**Port `CommandInterpreter::ArgumentGate#refuse_unknown_arguments` to the one layer where a JSON payload genuinely has no static shape yet: `from_json`, before it builds the typed struct that already makes an extra field structurally impossible.**

`Json::unknown_keys` (`json.rs`) is the mechanical check; `json_codec.rb`'s `command_argument_allowlist` re-derives Ruby's own allowlist exactly — declared attributes, plus `:id`, the aggregate's own `identity_heads`, the command's own `reference_key` (`Naming.reference_key(command.references)`), and every process manager's `correlation_head` in the domain (`argument_gate.rb`, read directly, not re-derived from guesswork). Two new `Refusal` variants, `UnknownArgument`/`AbsentArgument`, exist now — only ever raised at this JSON boundary, never inside a generated `dispatch_*` (kernel/mod.rs's own updated comment). Applied to AGGREGATE commands only: entity commands run no such check in Ruby either (`EntityInterpreter::DISPATCH_ORDER` has no `refuse_unknown_arguments` step at all), so none was added there.

Running this against the full corpus surfaced a second, unrelated bug in the same pass: `Json::as_i64` silently truncated a fractional number (`25.5` for an `Integer`-typed field) instead of refusing it — Ruby's own `Value.for_attribute` coercion treats that as a type mismatch, not "close enough." Fixed the same way: `as_i64` now returns `None` for anything with a non-zero fractional part.

## Consequences

- Verified on the full corpus: matching instances went from 28/35 (0013's own count) to 29/35 — `Banking::Account#acct-3`, which carried BOTH bugs in sequence (an unknown `colour:` argument, then a fractional `cents: 25.5`), now matches exactly.
- **A genuinely bigger gap was found and deliberately NOT chased into:** `optional: true` attributes are not modeled with `Option<T>` ANYWHERE in the generator — not command Args structs, not entity fields, not value objects. `SafeDepositBox.LogVisit`'s own `note:` argument (declared `optional: true`, no default) is REQUIRED in the generated `LogVisitArgs` struct, so a real corpus call omitting it fails with a manufactured refusal Ruby never raises — this is what caused `Banking::SafeDepositBox#DOWNTOWN:12`'s mismatch, not an entity-command bug. The SAME root cause explains `CardPayment.Authorize`'s `tags:` (an `optional: true` LIST argument the caller omits): Ruby leaves it `nil` when omitted; the generated struct defaults it to an empty `Vec` instead, because there's nowhere to put "absent" once the field isn't `Option`-wrapped. **A to_json heuristic (empty list -> `Json::Null`) was tried, built, and reverted** — it fixed `tags` but broke `Account.ledger` (legitimately `[]` in Ruby too, since it's populated by `append` rather than a caller-supplied argument), because the real distinction Ruby carries — was this list attribute ever a MATCHED creating-command argument at all, versus computed via `default_for` — isn't represented in the generated Rust type today. Properly fixing this means Option-wrapping optional attributes end-to-end (struct fields, `Fielded`, `to_json`, `from_json`, AND the invariant-check/mutation-application code in `commands.rb` that currently assumes every args field is always present) — comparable in size to 0013's own saga work, not a quick follow-on. Flagged here, not attempted.
- The remaining corpus mismatches (`CardPayment` x4, `Account#acct-8`, and the "only in native" extra records — `xfer-ghost`, `ext-admits`, three `Customer` records, `acct-6`) all trace to ONE cause each: the `tags` gap just described, and the still-separately-deferred reference-existence checking (§8's own original gap — a `Transfer.Request` to a never-opened account succeeds in Rust and its saga runs to a refused, compensated end, where Ruby refuses the whole command before any saga starts at all). Neither is new.

## Rejected alternatives

- **The empty-list-to-`Json::Null` heuristic**, described above — built, verified against the corpus, found to regress more than it fixed, reverted in the same pass rather than left in with a caveat. A wrong fix that happens to pass its own narrow test is worse than no fix, once a broader corpus check exists to catch it — which is exactly what 0013's CI wiring was for.
