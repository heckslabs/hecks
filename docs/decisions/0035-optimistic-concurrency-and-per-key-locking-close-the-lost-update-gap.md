# Optimistic concurrency (CAS + retry) and per-key in-process locking close the dispatch-level lost-update gap

> Historical: `bin/` is gone (removed in 3.0.0; its scripts are commands now: `bin/model_check` is `exe/hecks model_check_run.model_check!`; the rest in `docs/tools.md`); paths below name what existed when this was decided.

**Status:** Accepted — implemented. New: `lib/hecks/runtime/aggregate_lock.rb` (`Runtime::AggregateLock`, a process-wide striped `Mutex` registry). Changed: `lib/hecks/runtime/instance.rb` (`Instance#version`, out-of-band); `lib/hecks/ports/persistence/execution.rb` (`Outcome::STATUSES` gains `:stale`); `lib/hecks/runtime/errors.rb` (`StaleWrite`, deliberately outside `DOMAIN_REFUSALS`); `lib/hecks/ports/persistence/append_only.rb` (`AppendOnly#save` takes `expected_version:`, now returns an `Outcome`, not a bare `Instance`); `lib/hecks/runtime/identity.rb` (`Identity.best_effort`, a never-raising lock-key derivation); `lib/hecks/runtime/interpreting.rb` (`run_dispatch_order_with_isolation`, the shared lock-vs-CAS split); `lib/hecks/runtime/command_interpreter.rb` and `lib/hecks/runtime/entity_interpreter.rb` (`#call` resolves the repository once and retries the whole dispatch on `StaleWrite`, capped at `MAX_STALE_WRITE_RETRIES = 5`; `step_save` passes `expected_version:` and raises `StaleWrite` on a `:stale` outcome); `lib/hecks/adapters/driven/postgres.rb` + `postgres/schema_builder.rb` (a `hecks_version` column, self-healing via `ADD COLUMN IF NOT EXISTS`; `persistence_capabilities` gains `:optimistic_concurrency`; `project` does real CAS via `INSERT ... ON CONFLICT DO UPDATE ... WHERE hecks_version = $N RETURNING hecks_version`; `find`/`all`/`execute_query` stamp `.version` on every `Instance` they build). Un-pended: `spec/adapters/driven/postgres_concurrent_dispatch_spec.rb` — the example this ADR was written to fix now passes for real. New: `spec/adapters/driven/in_process_concurrent_dispatch_spec.rb` (the Heki/Memory cousin, real `Thread`s, one process). Fixed one now-stale assertion: `spec/adapters/driven/postgres_atomic_put_spec.rb`'s capability-list expectation.

## Context

PR #378 (merged; see its own commit and the concurrency-model investigation it carries) traced `CommandInterpreter`'s dispatch pipeline and found a real, unguarded lost-update window: `step_hydrate` reads an aggregate's current state (`repository.find`), later steps evaluate every `given` against that read, and `step_save` writes the mutated result back — with no lock, transaction span, or version check anywhere between the read and the write. `Postgres#atomic_put` (the `creates?`/complete-state/state-independent fast path) takes a `pg_advisory_xact_lock`, but the far more common path — any command with a `given` or a mutation that reads prior state (`decrement`, `increment`, a lifecycle guard, ...) — runs through `DependencyPlanning::Plan::TRANSACTIONAL_FALLBACK` and `AppendOnly#save`, which has never taken any lock at all. `spec/adapters/driven/postgres_concurrent_dispatch_spec.rb` was committed alongside that investigation as a `pending` example demonstrating the gap concretely: two concurrent `Debit`s against one $10,000 account, each individually satisfying `given("the balance covers it")` against the balance it read, both admitted, together overdrawing the account.

The semantic guarantee this ADR delivers, exactly as specified going in:

> A state-dependent command must commit atomically with respect to the aggregate state against which its conditions (`given`s) were evaluated.

Two concurrent dispatches against the same aggregate must never both succeed when a `given` should have refused the second one once the first one's effect is visible.

Two further facts, confirmed by reading the code before designing anything here (not assumed):

- `ctx.repository` in `CommandInterpreter`/`EntityInterpreter` is a `Ports::Persistence::AppendOnly` wrapper. `AppendOnly#save` calls `@adapter.append`/`@adapter.project` directly — it never calls an adapter's own hand-rolled `save` (e.g. `Postgres#save`, which wraps append+project in one transaction). That adapter-level `save` is dead code from the perspective of ordinary command dispatch; this ADR does not touch it, and does not fix that it's unreachable — a separate, pre-existing oddity, out of scope here.
- Heki and Memory are confirmed process-local: `Adapters::Memory.tenant_capable?`'s own comment states two `Runtime.boot` calls get two entirely separate `Memory` instances — there is never a second process writing the same Heki file or Memory `Hash`, only possibly other threads within one process.

## Decision

The mechanism lives entirely in the runtime/adapter layer, split by what each adapter can actually do:

**Postgres — optimistic-concurrency CAS, plus a bounded retry that re-checks `given`s for real.**

- `Instance` gains `version` (`attr_accessor`, defaults `nil`), out-of-band adapter bookkeeping — absent from `to_h`, `[]`/`[]=`/`method_missing`, and every domain-facing surface. A domain author never declares anything about it; `dup` carries it forward for free via `Object#dup`'s ordinary ivar copy (verified empirically, not assumed).
- Postgres's aggregate table gains a `hecks_version bigint NOT NULL DEFAULT 1` column — adapter bookkeeping only, never added to `persisted_fields`, so it never reaches `decode`'s domain-state hash. Self-healing via an unconditional `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, the same idiom `ensure_indexes!` already uses, since `CREATE TABLE IF NOT EXISTS` doesn't retroactively add a column to an already-live table.
- `Postgres#project(entry, expected_version: nil)` does real compare-and-swap: `INSERT ... ON CONFLICT (id) DO UPDATE SET ..., hecks_version = hecks_version + 1 WHERE hecks_version = $N RETURNING hecks_version` when `expected_version` is given. A genuinely new row still inserts unconditionally (the `WHERE` only gates the conflict branch); zero rows returned means the version had already moved, and `project` returns `nil` for that case. `find`/`all`/`execute_query` stamp `.version` from the row on every `Instance` they build.
- `Ports::Persistence::Outcome` gains a `:stale` status — distinct from `:conflicted` (a `creates?` command's identity already exists, a genuine business refusal, `AlreadyExists`). `:stale` means "an optimistic version check failed", never a domain refusal.
- `AppendOnly#save(instance, expected_version: nil)` requests CAS only when both `expected_version` is non-nil AND the adapter declares `:optimistic_concurrency`; every other case (a caller that doesn't want CAS, or an instance never read from storage) falls straight through to the same plain, unconditional `project` call this method has always made. Its return type changes from a bare `Instance` to an `Outcome` — every call site (`CommandInterpreter`/`EntityInterpreter`'s `step_save`, `RebuildSweep#refresh`) was checked and updated or confirmed unaffected.
- A new internal-only error, `Runtime::StaleWrite`, deliberately outside `DOMAIN_REFUSALS` and never touching `vocabulary.bluebook`. `step_save` raises it on a `:stale` outcome with a plain, informative message (not a `RefusalWording.render` call — this is not a declared vocabulary refusal).
- `CommandInterpreter#call`/`EntityInterpreter#call` resolve `ctx.repository` once, before dispatch starts (memoized by `Registry#repository`, safe to call once and reuse), and wrap the whole method body in a bounded retry: on `StaleWrite`, retry the ENTIRE dispatch — fresh `Context`, fresh hydrate, so `enforce_givens` re-evaluates against the now-current state — capped at `MAX_STALE_WRITE_RETRIES = 5`. In the ordinary two-writer race, this resolves in exactly one retry: the loser's retried hydrate reads the winner's committed balance, and its own `given` refuses for real, raising `GivenNotMet` — not `StaleWrite`. The retry cap is a last-resort safety valve for pathological contention (many concurrent writers on one hot aggregate), not the expected shape of a two-writer race.

**Heki and Memory — a per-key in-process lock, no schema, no retry.**

Both are confirmed process-local (see Context). A `Mutex` held for the full hydrate-through-save critical section closes the identical gap with no version column and no CAS protocol:

- `Runtime::AggregateLock` — a process-wide, striped registry of `Mutex` objects keyed by `[domain, aggregate.hecks_name, id]` (or `[domain, aggregate.hecks_name]` alone when `id` is unresolved — coarser, still correct). The registry `Hash` is guarded by its own top-level `Mutex` only for the moment a new per-key `Mutex` is created, so two threads locking different keys never block each other.
- `Runtime::Identity.best_effort` derives a lock key the same way `hydrate_existing`/`parent` already derive the real identity (`route&.aggregate || Identity.of(...) || Identity.from(..., :id) || Identity.from(..., reference_key)`), but wrapped to never raise — choosing which `Mutex` to hold must never itself become a crash. It runs against the raw, pre-normalized payload (before `normalize_args`/`resolve_references`), so it is explicitly best-effort: a resolution failure or an imprecise match only ever makes locking coarser, never incorrect.
- `Interpreting#run_dispatch_order_with_isolation` is the shared split both interpreters call: a repository that declares `:optimistic_concurrency` runs the dispatch order directly (Postgres's own CAS+retry already covers it — an extra lock here would be pointless overhead, not incorrect, so it's skipped for clarity); every other repository runs the same dispatch order inside `AggregateLock.for(domain, aggregate, lock_key_id).synchronize { ... }`.

**Why this lives below Bluebook/PrimalIR entirely.** Nothing here is a grammar concept, a vocabulary word, or a declared refusal. A domain author writes `given`/`sets`/`decrement` exactly as before; the runtime that turns "this command was admitted" into "this command's effect is durably true" is responsible for making that admission mean something under concurrency, the same way it is already responsible for coercion, identity resolution, and append-then-project ordering. `StaleWrite` is not in `DOMAIN_REFUSALS` and never reaches `vocabulary.bluebook` — a caller who wants to distinguish "the domain genuinely refused" (`GivenNotMet`) from "the system could not settle this write under contention" (`StaleWrite`, only after retries are exhausted) rescues them separately, exactly as `spec/adapters/driven/postgres_concurrent_dispatch_spec.rb` already does.

## Consequences

**Covered, and verified with a real failing-without-the-fix demonstration:**

- **Postgres** — `spec/adapters/driven/postgres_concurrent_dispatch_spec.rb`'s `pending` line is removed; the example passes for real, across repeated runs with different random seeds, with the second debit refused via a genuine `GivenNotMet` (its `given` re-evaluated against the first debit's committed balance, not a loosened assertion accepting `StaleWrite`).
- **Heki and Memory** — a new spec, `spec/adapters/driven/in_process_concurrent_dispatch_spec.rb`, demonstrates the same two-concurrent-writers race with real `Thread`s inside one process (these adapters have no second process to model). Confirmed genuinely exercising the lock: the lock was temporarily reverted, both examples went red (`[:succeeded, :succeeded]`, the exact lost-update shape), and reinstating the fix turned them green again.
- Every adapter/call site touched by `AppendOnly#save`'s changed return shape (`CommandInterpreter`, `EntityInterpreter`, `RebuildSweep#refresh`, and one stale capability-list assertion in `spec/adapters/driven/postgres_atomic_put_spec.rb`) was checked and is either updated or confirmed unaffected.
- Full test suite green: default run, `--tag io`, and `--tag fuzzing`, across every real example domain (banking, pizzas, compliance, roster, chess) this change's dispatch-path edit touches. `rubocop` clean project-wide. `bin/model_check` clean (no grammar/domain declaration changed, confirmed rather than assumed).

**Explicit, deliberate gaps — not silently narrower coverage than implied:**

- **`Sqlite`** does not get `:optimistic_concurrency`. It still declares only `:atomic_put`, so a state-dependent command against a Sqlite-backed aggregate falls back to the same per-key `AggregateLock` path Heki/Memory use — correct (Sqlite is also process-local, one file, no second process), but not the CAS mechanism this ADR built for Postgres. A future ADR can port the identical `INSERT ... ON CONFLICT DO UPDATE ... WHERE` + `changes()` pattern if Sqlite's own concurrency profile ever needs it to be lock-free.
- **`PostgresEra`** is untouched. It carries its own lineage/era machinery on top of plain Postgres storage, and extending CAS into that shape (per-era `hecks_version` semantics, interaction with `LineageManager`, view chains) is real, separate design work this ADR did not attempt. It falls back to `AggregateLock` today, which is CORRECT (still process-local from Ruby's perspective — the lock is per this-process, and there is exactly one process per bound adapter instance the same as Heki/Memory) but coarser than a CAS-capable path would be, and does not benefit from Postgres's own cross-process guarantee the way plain `Postgres` now does. Chess (`examples/chess`) is bound to `PostgresEra`; it has no committed persistent data files, so there's no migration-safety concern blocking a future attempt — this is a deliberate scope cut for THIS ADR, not a technical blocker.
- The `AggregateLock` fallback for Sqlite/PostgresEra means a state-dependent command against either is safe only when every writer lives in the same Ruby process instance the lock's registry lives in — true for every deployment shape this corpus's specs exercise today, but worth stating plainly: two separate OS processes both writing Sqlite or PostgresEra directly would reopen the exact gap this ADR closes for plain Postgres. Recorded here rather than implied to be covered.

## Rejected alternatives

- **A single global lock around every dispatch.** Rejected — serializes every aggregate against every other, discarding all real concurrency for a correctness property that only needs to hold per-record. `AggregateLock`'s striping (down to `[domain, aggregate, id]`) gets the same correctness at a fraction of the contention cost.
- **CAS everywhere, including Heki/Memory** (a version field written into the file/Hash record itself). Rejected — both are confirmed process-local; a `Mutex` gets the identical guarantee with no schema change, no retry loop, and no risk of the version field ever leaking into `to_h` through a less-careful adapter than Postgres's own `persisted_fields` exclusion.
- **Row-level `SELECT ... FOR UPDATE` instead of optimistic CAS for Postgres.** Rejected — would require holding a transaction open across the entire hydrate-through-save dispatch (multiple round trips, arbitrary domain logic in between), a much larger blast-radius change to how `AppendOnly`/adapters relate to Postgres transactions than the append-then-project boundary this codebase deliberately keeps thin. CAS-on-write plus a bounded retry gets the same correctness without ever holding a lock across application-level work.
- **Loosening `postgres_concurrent_dispatch_spec.rb`'s assertion to accept `StaleWrite` as a passing outcome for the second debit.** Rejected outright. Retrying only `step_save` on a `:stale` outcome (rather than the whole dispatch) would have made `StaleWrite` the normal outcome of the two-writer race, not a last resort — the loser's `given` would never get re-evaluated against the winner's committed state at all. Retrying the WHOLE method body — fresh `Context`, fresh hydrate — is what makes the loser's second attempt see real, current state and refuse for the right domain reason (`GivenNotMet`), which is what the spec correctly insists on.
