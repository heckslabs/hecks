# Self-host the closed expression grammar — close the gap 0009 named and declined

> Historical: `bin/` is gone (removed in 3.0.0; its scripts are commands now: `bin/project_kernel_capabilities` is `exe/hecks kernel_run.project_kernel_capabilities!`, `bin/rust_kernel_coverage` is `exe/hecks kernel_run.measure_kernel_coverage!`; the rest in `docs/tools.md`); paths below name what existed when this was decided.

**Status:** Accepted — implemented. `lib/hecks/grammar/expression.bluebook` and `expression_operators.json` (the admission ledger), `spec/operator_conformance_spec.rb` (holds Ruby's `Evaluator`/`Resolver` tables equal to the ledger, both directions), `bin/project_kernel_capabilities` (generates `rust/src/kernel/expression_operators/mod.rs` from `Grammar.admitted_operators`), `bin/rust_kernel_coverage` (fails the build if an admitted capability has no corresponding hand-written Rust file). Goes further than this ADR proposed: Rust's operator enum is *generated from* the shared grammar, not merely checked against it. Extends [0009](../implemented/decisions/0009-language-describes-shape-not-interpreter-or-io.md) and [0011](../implemented/decisions/0011-rust-compiles-types-interprets-dispatch.md); does not supersede either.

## Context

[0009](../implemented/decisions/0009-language-describes-shape-not-interpreter-or-io.md) drew a deliberate boundary: the self-hosted Bluebook language describes *shape* — what constructs exist, what attributes they carry — and permanently does not describe the interpreter (how a `given`/`ensures` predicate gets evaluated against a real record) or IO. Both stay hand-written Ruby. That ADR's own "Rejected alternatives" section named the natural next question and declined to answer it there: *"A proposal to have the self-hosted language also describe evaluation semantics — e.g., representing `given` bodies as a self-hosted expression AST the meta-domain could itself evaluate ... would be a deliberate, scope-expanding decision, not an incremental extension. It should get its own ADR rather than accreting silently into this one."* This is that ADR.

[0011](../implemented/decisions/0011-rust-compiles-types-interprets-dispatch.md) already tried, and rejected in practice, the naive version of "make Rust follow Ruby's behavior": compiling each `given`/`ensures` clause into hand-written or generated Rust *source*, one case per command shape. It didn't converge — "needed a new hand-written case in the generator... the same failure mode [as] the retired Rust runtime, one level down." What shipped instead, and works, is narrower and better: `given`/`ensures` text is parsed once in Ruby via the real parser (`Bluebook::Expression::Evaluator.parse`) and emitted as Rust *data* (`Expr::Compare{...}`, `Expr::And{...}`, etc.), walked at runtime by one small, hand-written, never-regenerated interpreter (`rust/src/kernel/expr.rs`) — a direct structural port of Ruby's `Evaluator`/`Resolver` node kinds. Every real corpus shape converged under this design without further architecture changes.

That leaves one precise, narrow gap, not the sprawling one this ADR could have proposed. `rust/src/kernel/expr.rs` is a hand-port of Ruby's `Evaluator`/`Resolver` — two independently authored implementations of the same small, *closed* grammar (the fixed node-kind set `spec/operator_conformance_spec.rb` already holds Ruby to: comparisons, boolean combinators, arithmetic, membership, sign tests — nothing open-ended). They're kept honest today by that spec constraining Ruby's side and by 0011's own port being "thoroughly-covered," but nothing ties the two implementations to one shared source of truth — a new node kind added to Ruby's evaluator has no structural mechanism forcing `kernel/expr.rs` to learn about it beyond a human remembering to port it, the same class of silent-drift risk 0010's differential harness exists to catch, just not yet aimed at this specific boundary.

This gap is real but intentionally small. A broader review of hand-written-vs-generated boundaries elsewhere in the stack — informed by watching a predecessor project (`~/Projects/hecks`) build a considerably more ambitious version of this idea, prove a genuine Futamura second-projection fixed point for one routing table, and then retire the machinery once its one-time verification purpose was served, judging the ongoing legibility cost not worth it for something that rarely changes — argues strongly against re-attempting anything like "compile the whole language." That ambition was tested by that project and by 0011's own rejected first attempt; both converge on the same lesson: structure (shape, routing, closed grammars) tolerates this kind of derivation; open-ended semantics (arbitrary domain logic, `validator_checks.rs`-style per-construct hand-written rules) does not, and trying to force it produces machinery whose maintenance cost exceeds its benefit. The expression-node grammar is specifically on the tolerant side of that line: closed, small, already spec-bounded, and already proven (by 0011's shipped design) to be the right unit to interpret generically rather than compile per-instance.

## Decision

Describe the closed expression-node grammar — the fixed set of node kinds `operator_conformance_spec.rb` already bounds (`Compare`, `And`, `Or`, `Not`, arithmetic, membership, sign tests) — as a self-hosted shape in the Bluebook meta-language, the same way `projection.bluebook` and its siblings already describe other language constructs. Concretely, this means:

- A new self-hosted description of "what node kinds exist and what fields each carries" (e.g., a `Compare` node has `op`, `left`, `right`), read the same generic way `Judge`/`MetaValidator`'s existing machinery reads any other declared shape.
- Ruby's `Evaluator`/`Resolver` and Rust's `kernel/expr.rs` — and any future runtime's own expression walker — become things that can be *checked against* this one shared description at minimum, and ideally eventually *derived from* it, rather than two (or more) independently hand-authored implementations of the same grammar kept honest only by a spec file on one side and a human port on the other.
- This does **not** touch `given`/`then_set`/`ensures` *usage* anywhere in a real bluebook — those stay exactly as they are: canonical text, parsed once by Ruby, emitted as data per 0011. Only the interpreter-of-that-data's own node semantics move from "hand-ported twice" to "declared once, implemented against."
- Explicitly out of scope, matching 0009's boundary exactly and not reopening it: anything outside the closed grammar — custom helper methods called from within a `given`, reference-hop resolution beyond what's already a declared `QuerySpecification::HopPath` shape, any IO. Those stay hand-written on every runtime, permanently, per 0009's own decision, unchanged by this one.

## Consequences

- A new node kind added to the expression grammar (should one ever be needed — the current set has been stable enough that `operator_conformance_spec.rb` treats it as closed) gets declared once; every runtime's own walker either derives its handling mechanically or, at minimum, fails loudly against a shared conformance check rather than silently diverging until a fuzz run or a real bluebook happens to exercise the gap.
- Does not reduce the hand-written surface for `given`/`ensures`/`then_set` *authoring* — that was never the target. The target is the small, already-converged interpreter layer underneath it.
- Whether this is worth building at all depends on how often the node-kind set actually changes. If it's genuinely closed and has been for a long time, the ongoing drift risk this closes may be small enough that — per the `~/Projects/hecks` precedent of retiring exactly this kind of machinery once it had proven itself and the maintenance cost stopped paying for itself — the right call could be "verify once, by hand, that the two implementations agree today, and don't build standing machinery for a boundary that isn't actually moving." That determination is not made by this ADR and should precede any implementation work.
- Not yet investigated: whether the *existing* corpus's `given`/`ensures`/`then_set` clauses across every real domain (Banking, Pizzas, ConsoleSettings, BurningManPrep, etc.) already fit entirely within the grammar `operator_conformance_spec.rb` bounds, or whether some rely on something wider that would need auditing or rewriting first. This is flagged here as unverified, not assumed either way, and is the natural first step before any implementation.

## Rejected alternatives

- **Compile `given`/`ensures` clauses to per-construct Rust (or any target) source.** Already tried and rejected in practice by [0011](../implemented/decisions/0011-rust-compiles-types-interprets-dispatch.md) — didn't converge, reintroduced the retired Rust runtime's own failure mode one level down. Not reconsidered here.
- **Self-host evaluation semantics broadly — the full interpreter, not just the closed expression grammar.** This is what [0009](../implemented/decisions/0009-language-describes-shape-not-interpreter-or-io.md) already declined, for good reason: IO and arbitrary domain logic are open-ended, not closed grammars, and a predecessor project's own real, documented experience (`~/Projects/hecks`, i51 arc) shows this class of thing resists exactly this kind of derivation — semantic content stayed hand-written no matter how far self-hosting was pushed there. This ADR deliberately stays inside the one slice — the closed expression-node grammar — that's structurally different from that open-ended case.
- **Do nothing; leave `Evaluator`/`Resolver` and `kernel/expr.rs` as an accepted, permanent hand-port.** A live option, not obviously wrong — see the Consequences section above. This ADR records the gap and the reasoning for closing it as a real option; it does not itself decide that the cost is worth paying.
