# A Ruby self-correctness track, separate from Rust parity

**Status:** Investigated in full; one real, scoped piece shipped (`:set` closes in `mutations_match_recompute`); the rest of this document is a plan for what remains, prioritized.

## The gap, in the user's own words

> Differential fuzzing against Rust can't do this — it only ever surfaces places where Ruby and Rust *disagree*, and since Rust's codegen is derived from Ruby's own DSL declarations, a bug in Ruby that Rust's generated code faithfully reproduces would leave both engines agreeing while both are wrong, completely invisible to that method no matter how much of it you run. Finding Ruby's own bugs needs a genuinely different kind of check, not more of the same one.

Four named approaches: (1) property/invariant testing independent of Rust, (2) testing against the bluebook's own declared semantics (spec-conformance, not parity), (3) exhaustive/model-checked testing of individual constructs in isolation, (4) external review reading Ruby against the DSL's own documented intent.

## Phase 1 — what already exists, read in full, file:line

### `lib/hecks/fuzzing/self_consistency.rb` — persistence round trip, NOT a mutation-application check

Confirmed precisely, not merely quoted from its own header: hecks is not event-sourced at the aggregate level. `Ports::Persistence::AppendOnly` stores the FULL state after each command (`self_consistency.rb:32-52`'s own header). `check_rehydration` (`self_consistency.rb:90-102`) takes `live = snapshot(repository)` — the record `CommandInterpreter#step_apply_mutations` (`command_interpreter.rb:158-175`) or `EntityInterpreter#step_apply_mutations` (`entity_interpreter.rb:279-287`) already computed and saved — and folds the SAME already-computed `entries` through a second `Adapters::Heki` instance, comparing the two. Both sides trace back to the identical single `apply`/`apply_to_element` call; the fold is a JSON serialize/deserialize round trip (`Value#to_json` → `Value.build`), not a re-derivation. `check_idempotency` (`self_consistency.rb:104-122`) is the same fold run twice against the same durable store — a leaked-state check, still downstream of the one computation. `check_value_object_round_trip` (`self_consistency.rb:157-187`) round-trips every `Runtime::Value` the sequence built through `to_json`/`Value.build` — again a serialization check, not a semantic one.

**Verdict, confirmed by direct code reading and by `spec/fuzzing/mutation_set_self_correctness_spec.rb` (new, this PR):** `SelfConsistency.check` can catch a serialization/coercion round-trip bug (and does — `spec/fuzzing/self_consistency_spec.rb`'s own three `describe` blocks each break a different real code path and confirm the corresponding check fires). It structurally CANNOT catch a bug in the mutation-application logic itself, because a wrong value computed once by `apply`/`apply_to_element` is baked into both the "live" and "rehydrated" sides before either one runs. `saga_rehydration`/`saga_redelivery_idempotency` (checks 4-5, `self_consistency.rb:230-339`) are the same shape one level over, for saga checkpoints — same verdict.

### `lib/hecks/fuzzing/properties.rb` and `lib/hecks/fuzzing/properties/*.rb` — a real, substantial down payment on approach #1, already shipped

Fourteen properties, `properties.rb:212-231`. Characterized individually:

- **Genuinely independent re-derivations (approach #1/#3, real signal, not a parity check):**
  - `dispatch_binding_fidelity` (`dispatch_and_mutations.rb:78-125`) — `resolve_dispatch_binding`/`resolve_trigger_binding` independently reproduce `SagaInterpreter#dispatch_args`/`PolicyInterpreter#trigger_args`'s own resolution, never calling either again.
  - `mutations_match_recompute` (`dispatch_and_mutations.rb:167-330`, extended by this PR) — `recompute_append`/`recompute_remove`/`recompute_multiply`/`recompute_clamp`/`recompute_set` (new) independently reproduce `EntityElement#appended_to_element`/`#removed_from_element`/`#apply_to_element`'s own arithmetic and `:set` branches. This is, precisely, a small independent mutation-IR interpreter for the ops it covers — see Phase 3.
  - `aggregation_matches_recompute`/`group_by_matches_recompute` (`invariants_and_aggregation.rb:214-299`) — independently reproduce `ReadModelInterpreter`'s FK-join/count/median/group-by, reusing only `Ports::Query::InMemory.comparable`/`.holds?` and `FieldPath.dig` (the same two primitives the interpreter itself calls, a DELIBERATE, documented coupling — see that method's own comment — so this cannot catch a bug in "what does a field read/hold clause mean," only in the reduction built on top of it).
  - `paging_offset_partitions_correctly` (`querying.rb:86-113`) — the offset/limit slice is independently reproduced in plain Ruby; only `Ports::Query::Ordering.apply` is reused (same documented coupling).
  - `lifecycle_guard_and_given_violations_are_refused` (`guards.rb:340-350`) — calls `Admissibility#enforce_givens` directly against a pre-dispatch snapshot, a genuine SECOND independent invocation of production's own guard-checking code, compared against what the real dispatch actually did. Not calling a from-scratch reproduction, but a real, false-negative-catching second call: a call site that stopped invoking `enforce_givens` would be invisible to `guard_refusals_are_declared` (below) but caught here.
- **Spec-conformance checks against declared IR (approach #2), not independent oracles, but real:**
  - `lifecycle_values_are_declared`, `saga_advances_follow_declared_handlers` (`lifecycle_and_replay.rb:23-73`) — a real run's own values checked against the FULL declared set (`Bluebook::ModelCheck.full_states`), not merely the tested-happy-path subset.
  - `guard_refusals_are_declared` (`guards.rb:119-139`) — a refusal's quoted text checked against the refusing command's OWN declared `given`/`ensures` descriptions. Catches stale wording, a rule firing against the wrong command, wording drift — but only for a refusal that ALREADY happened (its own header names `lifecycle_guard_and_given_violations_are_refused`, above, as its "did a guard silently stop firing" complement).
  - `stored_records_satisfy_declared_invariants` (`invariants_and_aggregation.rb:52-100`) — every FINAL stored record re-checked against its own aggregate's declared invariants via `Bluebook::Expression::Evaluator.call` — the SAME evaluator class production's own `Admissibility#enforce_invariants` calls. This is a real, valuable check (catches "a call site stopped calling `enforce_invariants`," or a translation/backfill that wrote around it) but shares the evaluator itself with production — a bug in `Evaluator.call`'s own semantics would pass both. `outbox_rows_match_reactions`, `corrections_reference_an_emitted_event`, `authorize_scopes_or_refuses`, `commands_respect_tenant_scope` are the same shape: real, declared-semantics checks, with the same "shares a primitive with production" caveat where noted in each file.

**`FEATURE_COVERAGE`/`GUARANTEED_BY_CONSTRUCTION`** (`properties.rb:74-207`) are themselves a real, load-bearing part of this track — every grammar construct is either claimed by a named property, or the SPECIFIC enforcing code path is cited and the violation is proven unreachable by construction (never a blanket exemption).

### `lib/hecks/fuzzing/persistence_parity.rb` — a second differential axis, NOT independent of the shared computation

Confirmed by reading `diff` (`persistence_parity.rb:78-89`): both `left_result`/`right_result` call `Replay.call` with the SAME `domain_path`/`steps`, only `adapter:` differs. Both sides dispatch through the identical Ruby `CommandInterpreter`/`EntityInterpreter` — the SAME `apply`/`apply_to_element` computation this whole investigation is about — before either adapter ever sees a value to store. This catches adapter-specific bugs (SQL compilation, rekey, query pushdown — `directory.world`'s own `compute`/`rekey` edge, per that file's own header) genuinely invisible to a Memory-only fuzz pass. It does NOT close the gap this document is about; it is a third axis on the SAME "compare two things downstream of one computation" family as `self_consistency.rb`, just at a different layer (adapter, not serialization).

### `lib/hecks/fuzzing/bounded_exhaustive_expressions.rb` — a real, partial answer to approach #3, scoped narrowly and honestly

Already exactly what approach #3 asks for, but for ONE sublanguage only: `Hecks::Bluebook::Expression::{Evaluator,Resolver}` (the `given`/`invariant`/`ensures` boolean expression grammar), type-directed generation up to `MAX_DEPTH = 3`, checked via `#check` (`bounded_exhaustive_expressions.rb:539-546`). Its own header is explicit and correct about its limit: this proves CRASH-FREEDOM on well-typed input ("interpreting a well-typed expression must never raise anything OTHER than `EvaluationError`"), never SEMANTIC correctness — "this does NOT prove the interpreter computes the semantically right answer... only that it never crashes." It does not touch mutation ops, command dispatch, admissibility, or anything outside the expression sublanguage.

### Hand-written domain-behavior specs — approach #2 is NOT a zero-coverage gap

`spec/runtime/*.rb` (64 files) boot real domains (banking, chess, nested_pieces, safe_deposit_box, etc.) through the actual Ruby runtime and assert real dispatch results against hand-read bluebook declarations — genuine spec-conformance tests, entirely independent of Rust (`spec/runtime/safe_deposit_box_spec.rb:29-45` is one example among many: dispatches `Rent`, asserts the declared `Reference<Customer>` type and the stored `:customer` value directly). The gap here is NOT "zero coverage" — it is that the QA PRACTICE (the rotation, the sweep) does not systematically audit or extend this coverage the way it does parity coverage. There is no dial, no rotation entry, no "is this construct's own spec-conformance suite still exercising a real refusal AND a real success" gate the way `spec/fuzzing/meta_domain_coverage_spec.rb`'s `FEATURE_COVERAGE` enforces for properties.

### The IR JSON's mutation shape (`{target, op, sign, source|fields}`, `command.rb:9-46`) — a genuine, independent mutation-IR interpreter is feasible, and partially already exists in a different shape

`Bluebook::Command::Mutation` (`command.rb:9-46`) emits exactly the shape named in the task: `target`, `op`, `sign` (table-driven off `Vocabulary::MutationOp`, `command.rb:28-30`), and either `source` (a classified `{kind:, ...}`) or `fields` (for `append`/`delegate`/`corrects`). A standalone interpreter reading this JSON and applying `set`/`append`/`remove` (and, with real additional work, `multiply`/`clamp`/`increment`/`decrement`) against a plain-data record, entirely outside the Ruby runtime's own class hierarchy, is a real, buildable project — but `mutations_match_recompute`'s own `recompute_append`/`recompute_remove`/`recompute_multiply`/`recompute_clamp`/`recompute_set` ALREADY do the equivalent thing against the Ruby `Mutation` STRUCT directly (not the exported JSON), for five of the seven ops, and are already wired into the standing property battery. Building a SECOND interpreter that reads the exported JSON instead of the live Ruby objects would mostly re-prove "the JSON export matches the Ruby object," a narrower and already-well-tested claim (`spec/golden/ir/*`), not a new source of Ruby self-correctness signal. **Recommendation: do not build this as a second interpreter under the live Ruby objects; the value is already captured by `mutations_match_recompute`.**

## Phase 2 — the plan, all four categories, prioritized

| # | Approach | What exists | Remaining gap | Design | Size |
|---|---|---|---|---|---|
| 1 | Property/invariant testing, independent of Rust | `Properties` module, 14 properties, several genuinely independent re-derivations (above) | `:increment`/`:decrement` still unrecomputable in `mutations_match_recompute` (`CommandRules::Arithmetic#arithmetic`'s own VO-vs-scalar branching + INT64_RANGE overflow checks, materially larger than the other five ops combined) | Add `recompute_increment`/`recompute_decrement` mirroring `EntityElement#apply_to_element`'s own `:increment`/`:decrement`/`arithmetic` branches, including the overflow/VO-shared-field cases | Medium — a few hours, same shape as this PR's `:set` work, once through carefully for the VO branch |
| 1b | " | `aggregation_matches_recompute`/`group_by_matches_recompute`/`paging_offset_partitions_correctly` share `Ports::Query::InMemory.comparable`/`.holds?`/`Ordering.apply` with production (documented, deliberate) | A bug in those THREE shared primitives passes both production and these properties | A from-scratch, hand-written re-implementation of "does a where clause hold" / "compare two field values" / "apply an order_by" for the property's own oracle only | Medium-large — real risk of the reproduction itself drifting from what these primitives are FOR; lower priority than #1 above because the shared surface is small and well-covered by `spec/ports/query/*` on its own |
| 2 | Spec-conformance against the bluebook's own declared semantics | 64 files under `spec/runtime/*.rb`, real and substantial | No systematic audit — the QA rotation checks parity coverage breadth (`FEATURE_COVERAGE`) but has no equivalent gate over `spec/runtime/` coverage | A `spec/runtime_coverage_spec.rb` in the same shape as `meta_domain_coverage_spec.rb`: for each grammar construct, does at least one `spec/runtime/*.rb` example dispatch it to both a real refusal AND a real success, independent of any Rust binary | Small-medium — mostly enumeration + a coverage table, no new runtime code |
| 3 | Exhaustive/model-checked testing of individual constructs | `BoundedExhaustiveExpressions`, scoped to the expression sublanguage's crash-freedom only | No equivalent exists for mutation ops, admissibility ordering, or lifecycle transitions | A bounded-exhaustive harness over `Vocabulary::MutationOp` × a small synthetic attribute palette (mirroring `SYNTHETIC_ATTRS`), checking crash-freedom of `apply`/`apply_to_element` on well-typed input the same way the expression harness does for `Evaluator`/`Resolver` | Medium — the hard part (type-directed generation, `TYPE_LEAVES`/`SYNTHETIC_ATTRS` palette) is already a proven pattern to copy from `bounded_exhaustive_expressions.rb`, but a mutation needs a full synthetic AGGREGATE/ENTITY (not just a Hash of scalars) to dispatch against |
| 4 | External review against the DSL's own documented intent | Nothing — genuinely zero infrastructure, by construction (parity/self-consistency cannot perform this at all) | Formalize as a periodic step | See Phase 3 below — deliberately NOT built this pass; recommend as the SECOND priority after closing `:increment`/`:decrement` |

**Priority, and why:** #1 (closing `:increment`/`:decrement` in `mutations_match_recompute`) is the highest-value next step — it is the same proven pattern this PR ships, cheap, and closes the LAST unrecomputable mutation op. #2 (a `spec/runtime/` coverage gate) is second — genuinely cheap (an enumeration + table, no new runtime code) and turns an already-substantial, already-shipped 64-file investment into something the QA rotation can systematically hold to, the same way `FEATURE_COVERAGE` already does for properties. #4 (external review) is third: zero infrastructure to START, but the value of any one pass is bounded and non-repeatable in the way a property is — worth formalizing as a `hecks_qa` rotation step once #1/#2 are in, not before. #3 (a full mutation-op exhaustive harness) is last: real, but the most expensive of the four, and its crash-freedom claim is a narrower kind of signal than #1's semantic-correctness claim.

## Phase 3 — what shipped this pass

**`mutations_match_recompute` now covers `:set`** (`lib/hecks/fuzzing/properties/dispatch_and_mutations.rb`, `RECOMPUTABLE_MUTATION_OPS`, `#recompute_set`) — the single most common mutation op in the corpus (every plain field assignment on an entity), previously entirely unrecomputable ("out of scope on purpose"). `#recompute_set` reproduces `EntityElement#apply_to_element`'s own `:set` branch exactly (confirmed against the real code, not `MutationApplier#apply`'s aggregate-level twin — `mutations_match_recompute` can only ever see entity-owned traces, since `Replay#build_mutation_trace` only captures those; an earlier draft of this method mirrored the wrong production method and false-positived on every real corpus site until caught by running it, not by inspection — see the method's own comment).

**The evidence** (`spec/fuzzing/mutation_set_self_correctness_spec.rb`, new): a defect planted directly in `EntityElement#apply_to_element`'s `:set` branch (the raw resolved value gets a `_CORRUPTED` suffix before coercion) leaves `SelfConsistency.check` — rehydration, idempotency, AND the value-object round trip — completely clean, because the corrupted value is a perfectly well-formed `BoardLabel`, just the wrong one; there is nothing for a same-process persistence check to ever disagree with. `Properties.mutations_match_recompute`, run against the identical broken replay, names the exact defect. This is not argued from reading the code alone — it is demonstrated, live, against a real domain (`qa/stress_domains/nested_pieces`, `Board.Label`).

**Unit coverage** (`spec/fuzzing/properties_spec.rb`, two new examples matching the existing append/clamp idiom) proves the property fires on a wrong `:set` result and passes a correct one, in isolation from any live replay.

**No new `hecks_qa` dial.** `mutations_match_recompute` is already unconditionally part of `Properties.check`'s standard battery (`properties.rb:212-231`) and already runs on every sweep against every domain in the rotation — extending its own `RECOMPUTABLE_MUTATION_OPS` needed no new wiring, no `qa/settings.yml` entry (`Hecks::Fuzzing::QaSettings`, PR #655, still open as of this writing — this change has no dependency on it either way, since it adds no new mode to dial).

## What this pass deliberately does not do

- **`:increment`/`:decrement`** stay unrecomputable — scoped out for the reason in the Phase 2 table (materially larger reproduction, including `INT64_RANGE` overflow and the VO-shared-numeric-field branch). Real, tracked follow-up, not forgotten.
- **No `spec/runtime/` coverage gate** — Phase 2's #2 slot, recommended next, not built this pass; this document is not a substitute for that gate, only the plan for it.
- **No exhaustive mutation-op harness** (Phase 2's #3) — a real, larger project, correctly estimated above as the most expensive of the four remaining slots.
- **No external-review mode/script** (Phase 2's #4) — deliberately left as a recommendation, not built, since it needs no new infrastructure to start whenever the team chooses to and building a throwaway "mode" around it this pass would be scaffolding without a proven cadence yet.
- **No standalone mutation-IR JSON interpreter** — considered and explicitly rejected above: the value is already captured by `mutations_match_recompute`'s own re-derivation against the live Ruby `Mutation` objects; a second interpreter over the exported JSON would mostly re-prove IR-export fidelity, a claim `spec/golden/ir/*` already covers.
