# Eras become a registered boot gate, not a hardcoded loader step

**Status:** Accepted — implemented. New: `lib/hecks/runtime/boot_gates.rb` (`Runtime::BootGates`, instantiated per boot — not a module-level singleton, since one process boots many registries with different capability profiles; see file comment). Changed: `lib/hecks/runtime/loader.rb` (`Loader.boot`/`boot_files` replace the two hardcoded calls with `run_boot_gates!`, a new private-ish class method); `lib/hecks/runtime/era_check.rb` (split `check!` into `check_compute_rules_for_registry!` — domain-agnostic, always runs, unchanged from before — and `check_lineage!` — the capability-gated half, now the registered `:era_check` gate — plus a new `lineage_capable_registry?` registration predicate). New spec: `spec/runtime/boot_gates_spec.rb`. One correction from the original design during implementation: `EraCheck.check_bluebook!`'s `check_compute_rules!` call is domain-agnostic (a compute rule requires Postgres whatever adapter is bound) and must run for every registry regardless of lineage capability — it could not become part of the conditionally-registered gate without silently dropping a real, contract-pinned refusal for a non-lineage domain with an errant compute rule. It stays a third unconditional call alongside `verify!`; only the drift-checking half is capability-gated.

## Context

An **era** is a schema-evolution/lineage concept: an immutable, numbered snapshot of a bluebook's storage shape, plus a translation edge (rename/move/convert/drop/retype/compute/rekey/backfill) describing how data from the previous shape maps onto the new one. It exists so a running Postgres-backed domain survives a schema change without a conventional migration tool — every past era's data is read through a compiled view chain that translates it on the fly.

Era logic is scoped to one adapter already — `Adapters::PostgresEra` (`lib/hecks/adapters/driven/postgres_era.rb` and its `postgres_era/`, `lineage/` subdirectories) carries all of it; the plain `Adapters::Postgres` has none (`docs/implemented/postgres-era-adapter-split-plan.md`). But the code that decides whether to run era-checking at all is not scoped the same way — it's a fixed, unconditional call inside `Runtime::Loader`:

- `Runtime::Loader.boot`/`boot_files` (`lib/hecks/runtime/loader.rb:33-61,85-103`) run a fixed sequence: load steps, then `EraCheck.check!(registry, directory)` (line 49 / 98), then `registry.verify!` (line 50 / 99), then `registry.rehydrate_sagas!` (line 58 / 100), then dispatcher construction. Every one of these runs on every boot, regardless of what's bound.
- Inside `EraCheck`, the actual "does this adapter care about eras" question is already a clean capability check — `adapter_class.respond_to?(:lineage_capable?) && adapter_class.lineage_capable?` (`lib/hecks/runtime/era_check.rb:128-133`) — but the *caller* of that check is not itself registrable. It's a name, hardwired into the loader.
- `registry.rehydrate_sagas!` (`lib/hecks/runtime/registry/saga_persistence.rb:33-42`) has the identical shape to `EraCheck.check!` in miniature: an unconditional call that internally degrades via capability-checking (`resolve_saga_persistence` falls back to `Ports::Persistence::NULL_SAGA_STORE` when the bound adapter doesn't respond to `save_saga`) rather than being absent from the call graph. `registry.verify!` (`lib/hecks/runtime/registry/verification.rb:13-47`) is different in kind — it's domain-agnostic (binds/verbs/roles checking applies to every domain regardless of adapter) and has no capability-conditional shape to generalize.
- `Runtime::EraGuard`/`Runtime::EraTamper` reach directly into `Bluebook::MetaValidator` and several DSL builder internals (`value_object_builder.rb`, `attribute_collector.rb`, `translation_builder.rb`, `identity_declaration.rb`) to shadow-parse historical bluebook text under old grammar defaults — machinery a non-lineage adapter's boot has no business depending on. The dependency also runs backward: `PostgresEra::LineageManager::CoverageCheck` calls back *up* into `Runtime::EraGuard` (`era_tamper.rb:13-19`'s own comment flags this as the exact shape that has caused trouble in this codebase before).
- Rust's boot gate (`rust/host/src/main.rs`) already has everything it needs to make the same distinction and doesn't use it: `ir.json` already carries a `lineage.capable_aggregates` list (`lib/hecks/projector/exporter.rb:33-41`, merged in `bin/project_rust:166`), Rust already parses it (`rust/host/src/ir.rs:50-67`) and already loads it at boot (`main.rs:191`) — but nothing branches on it being empty; the mint/audit sequence (ADR [0030](0030-rust-mints-its-own-eras-at-boot.md)) runs unconditionally today regardless of whether any aggregate is lineage-capable.
- This codebase already has one deliberate, named extension point — the Projector registry (`lib/hecks/projector.rb`, ADR [0027](../implemented/decisions/0027-canonical-ir-and-the-projector-framework-are-the-seam.md)): `register(name, projector)`/`call(name, ...)`, with a target declaring `projects_as :key, requires: SomeCapability`. It is the wrong shape for eras: explicitly IR-in/artifact-out, no bindings, no live-state mutation — era-checking gates boot and era-minting writes to the database, both disqualified by the Projector module's own taxonomy (the header comment of `lib/hecks/projector.rb`). No generic register/call mechanism exists anywhere in `lib/hecks/runtime/` today; the closest thing, `Registry#add_adapter` (`lib/hecks/runtime/registry.rb:84`), is a bare name-keyed hash write, not a dispatch idiom.

No prior ADR discusses extracting eras or building a generic boot-time extension mechanism. This is new ground.

## Decision

Introduce **`Runtime::BootGates`** (`lib/hecks/runtime/boot_gates.rb`) — a small, phase-tagged registry, purpose-built for this one seam rather than forced to share code with Projector:

- A gate is anything responding to `call(registry:, directory:)`, registered under a name and a **phase** (`:pre_verify` or `:post_verify`) — e.g. `Runtime::BootGates.register(:era_check, Runtime::EraCheck, phase: :pre_verify)`. The register/call primitive underneath is a private implementation detail of `BootGates` itself — not extracted into a shared, reusable module. A shared abstraction (e.g. something Projector could also sit on) is justified once a third consumer actually wants it, not speculatively for two.
- **Registration is conditional on the bound adapter's capability, not global.** `:era_check` registers only when `adapter_class.respond_to?(:lineage_capable?) && lineage_capable?` — exactly `EraCheck`'s existing internal check, just moved to gate *whether the call happens at all*. A domain bound to `Adapters::Memory` or plain `Adapters::Postgres` never registers it — structurally absent from that boot's call graph, not run-and-skipped.
- **`Loader.boot`/`boot_files` replace two hardcoded calls with three**, preserving today's exact ordering: `BootGates.run!(:pre_verify, registry:, directory:)` → `registry.verify!` → `BootGates.run!(:post_verify, registry:, directory:)`. `registry.verify!` itself stays a hardcoded, unconditional call — it's domain-agnostic, not adapter-conditional, so it doesn't belong in a capability-gated registry.
- **Two gates ship together, not one**, to actually demonstrate this is a category and not a bespoke wrapper around one adapter's special case:
  - `:era_check` (phase `:pre_verify`) — `Runtime::EraCheck`, unchanged in what it does.
  - `:saga_rehydration` (phase `:post_verify`) — wraps today's `registry.rehydrate_sagas!` body, now registered only when the bound adapter `respond_to?(:save_saga)`. This is a genuine behavior change, not just a refactor: today a non-saga adapter's boot calls `rehydrate_sagas!` and gets a silent no-op via `NULL_SAGA_STORE`; after this change, it never calls it at all. The two are equivalent by construction (`NULL_SAGA_STORE` is a documented no-op), so this is verified by an assertion spec — "gate registered iff adapter responds to `save_saga`" — not a differential before/after comparison.
- `Runtime::EraGuard`/`Runtime::EraTamper`'s reach into `MetaValidator`/DSL-builder internals, and `PostgresEra::LineageManager::CoverageCheck`'s call back up into `Runtime::EraGuard`, are **out of scope for this ADR**. That coupling is real and worth fixing, but it's a separate decision with its own risk profile (touches DSL/parsing internals) and gets its own future ADR.
- The Rust-side mirror (skip the mint/audit sequence entirely when `ir::lineage_capable_aggregates` is empty, instead of running it unconditionally) is **not a separate ADR** — the data already exists and is already loaded; this is a plain control-flow branch with no design choice left to record. It's listed below as a follow-on implementation task under this ADR.
- `lib/hecks/projector/exporter.rb`'s direct `EraCheck.adapter_for`/`.lineage_capable?` calls are unaffected — that's export-time IR shaping, a different seam, not boot gating.

## Consequences

- A domain bound to a non-lineage, non-saga adapter has zero era- or saga-persistence-related code in its boot call graph, structurally — matching how the adapter/port system already treats optional capabilities elsewhere (e.g. `query` falling back to `Ports::Query::InMemory` when unbound).
- Adding a future boot-time gate means registering another named, phased entry — not editing `Loader.boot` again.
- This does not reduce the total amount of era code or its inherent complexity — the mint/audit/translation machinery is unchanged. It relocates *who calls what*, so a non-lineage domain's boot path, `Runtime::` itself, and (once the follow-on ADR lands) the DSL/parsing internals are no longer coupled to concerns only one adapter has.
- The "refuse to boot until a human authors and approves a translation edge" guarantee ([0030](0030-rust-mints-its-own-eras-at-boot.md)) must not become skippable by mis-wiring. This needs a spec asserting a domain bound to `PostgresEra` always ends up with `:era_check` registered, and a domain bound to an adapter supporting sagas always ends up with `:saga_rehydration` registered — mirroring `spec/projector_seam_spec.rb`'s registration-completeness enforcement, scaled down to two hand-registered gates rather than a directory of files.
- **Follow-on tasks, not separate decisions:**
  - ~~Rust: change `main.rs`'s boot gate to skip the mint sequence when `ir::lineage_capable_aggregates(ir)` is empty~~ — **withdrawn, on investigation, not implemented.** `mint::decide_boot_action` (the hold-first/use-existing/mint-next/refuse decision) takes only `held`/`my_label`; it never consults `aggregates` at all. `dispatch.rs`'s `handle()` requires `LineageConfig` (which carries the era number) unconditionally and journals *every* mutation the WASM kernel reports through `journal::append_lineage_mutation`, for every aggregate, with no branch on lineage-capability. Real domains prove this is load-bearing, not incidental: `examples/pizzas/bluebook/pizzas.hecksagon` binds `Order` to `PostgresEra` but `Governance::RoleAssignment`/`RoleTransition` to plain `Memory` — both are dispatched through the same Lambda host and journaled through the one domain-wide era number. On the Rust side, "era" is the journal's own version number, required for every dispatched aggregate regardless of which ones are shape-audited — it was never a valid gate for skipping the mint/hold sequence. `aggregates` only scopes which aggregates get partition/view/grant provisioning and shape-drift auditing *within* that always-running era system. Skipping the sequence when empty, as originally written here, would have left `LineageConfig.era` unresolved for a domain exactly like Pizzas. This was the same kind of false Ruby-side-symmetry assumption [0032](0032-delete-eraguards-unwired-file-store-driver.md) corrected for `era_tamper.rb`'s placement — recorded here rather than silently dropped.
  - A follow-on ADR (separate from this one) to resolve `EraGuard`/`EraTamper`'s reach into `MetaValidator`/DSL-builder internals and `CoverageCheck`'s call back up into `Runtime::EraGuard` — landed as [0032](0032-delete-eraguards-unwired-file-store-driver.md), which found a different, real problem instead (an unwired duplicate driver) and corrected this ADR's own premise about the calling direction along the way.
- This is additive and mechanical enough to land in one pass: `BootGates` + conditional registration for both gates + the `Loader` sequencing change + the assertion spec.

## Rejected alternatives

- **Leave era-checking (and saga-rehydration) as unconditional `Loader.boot` steps.** Correct today only because every currently-shipped domain either uses the relevant adapter or tolerates the no-op silently — but it means the loader and `Runtime::` internals carry code that exists for one adapter's sake, with nowhere for a second capability-gated concern to plug in without editing `Loader` by hand.
- **Model era extraction on the Projector registry directly, or extract a shared `register`/`call` primitive both use immediately.** Rejected on both counts for the same reason: Projector's contract (IR-in/artifact-out, no bindings, no live-state mutation) doesn't fit boot-gating, and building a shared abstraction for a mechanism with exactly one consumer (`BootGates`) is speculative generality ahead of a second real need — Projector stays exactly as it is until a third consumer actually wants to share code with it.
- **Ship `BootGates` proving the category with only `:era_check`.** Rejected — a registry with one entry doesn't demonstrate it's a category rather than a bespoke wrapper. `:saga_rehydration` was folded in specifically because it already has the identical shape at effectively no added design cost.
- **Collapse `:era_check` and `:saga_rehydration` into a single unordered `run_all!` call.** Rejected — they currently straddle `registry.verify!` (era-check before, saga-rehydration after) and nothing confirms that ordering is safe to collapse. The phase tag preserves today's exact ordering with certainty instead of gambling on it.
- **A general-purpose middleware chain around `Runtime::Dispatcher`**, solving this and any future cross-cutting concern at once. Out of scope — no second use case has asked for one, and `Dispatcher`'s interpreters are a different seam (command dispatch, not boot gating). Building a generic chain speculatively repeats the mistake ADR [0022](0022-self-host-the-expression-grammar.md) exists to warn against.
- **A separate ADR for the Rust-side mirror.** Rejected once the facts were checked: `ir.json` already carries `lineage.capable_aggregates` and Rust already loads it (`main.rs:191`) — there's no design decision left, only a control-flow branch. Recorded as a follow-on task in Consequences instead of manufacturing a second ADR with nothing to decide.
- **Bundle the `EraGuard`/`EraTamper` namespace move and the adapter→runtime call inversion into this same ADR.** Rejected — real architectural risk (DSL/parser internals, a genuine bidirectional dependency to untangle) that deserves its own Context/Decision/Consequences, not a rider on the registry mechanism's coattails.
- **Give Rust its own boot-gate registry to mirror Ruby's.** Rejected — Rust has no domains needing more than one conditional gate today, and a registry there would be a runtime mechanism this crate has deliberately avoided elsewhere (compiled dispatch, not dynamic lookup — [0011](../implemented/decisions/0011-rust-compiles-types-interprets-dispatch.md)). A static conditional on already-loaded `ir.json` data gets the same result without it.
