# `Value::Coercion#hydrate_entity_list` widened to value-object lists — ADR 0047's root cause fixed; `remove:`'s own Rust port still deliberately not attempted

**Status:** Root cause fixed and regression-tested, in Ruby only. `remove:` mutation op is still not ported to Rust this round — closing ADR 0047's own item 4 needs its own scoped round, same as `multiply`/`clamp` (ADR 0042/0046) each got.

## What ADR 0047 found, restated briefly

`Value::Coercion#hydrate_entity_list` — the `:list` branch of `for_attribute` — used to bail (`return value unless entity`) the moment its target attribute's type named a value object rather than an entity, handing back the raw, un-hydrated argument untouched. A `sets :field` mutation sourced from a whole-array command argument (as opposed to element-by-element `append:`) went straight through that branch, so `Banking::CardPayment.Authorize`'s own `sets :tags` (`list_of(Tag)`) stored plain Ruby Hashes as its `tags` elements forever — never a real `Value`, never through `Tag`'s own `pattern:`/invariant checks. `remove:`'s `==` comparison (a real `Value` against a raw `Hash`) then always failed, since `Hash#==` refuses anything that isn't itself a compatible Hash.

## The fix

`lib/hecks/runtime/value/coercion.rb#hydrate_entity_list` now delegates to a new `hydrate_value_object_list` (plus a small `hydrate_value_object_element` helper) whenever `find_entity` comes up empty — the same composite-construction path (`value_object_for` + `build`) a scalar composite attribute already uses, so a value-object list element gets the exact same defaults, `pattern:`/`admits:`, and invariant checks a scalar field does, with the same `trusting_stored_state?` bypass on a trusted load (so nothing already persisted breaks on read — `Value#validate!` already no-ops there).

**One real wrinkle found and fixed in the same pass, not anticipated by ADR 0047's own text:** `MutationApplier#removed` reuses `Value.for_attribute` with the LIST attribute's own descriptor but a SCALAR target value (the single element being compared for removal, already coerced to a real `Value` by the argument boundary) — old code's blanket early-return happened to pass that scalar through unchanged by coincidence. A naive `Array(value).map { … }` here would have been actively wrong: `Array()` on a bare Hash opens it into `[[k, v], …]` pairs, not `[hash]` — silently shredding a single-element target instead of hydrating it. `hydrate_value_object_list` branches explicitly on `value.is_a?(Array)` first: a genuine whole-list `sets`/hydrate-load gets each element hydrated and returned as a list; anything else (the scalar-comparison reuse) gets hydrated as a single element and returned as one, never listified.

**A second wrinkle, also found and fixed:** the meta-domain's own self-hosting validator (`Bluebook::MetaValidator::Judge`) calls this same hydration path with something that does not respond to `:value_object` at all (a bare Class, not a full aggregate instance) — crashed immediately on first attempt. `for_attribute`'s existing SCALAR branch already guards this exact case (`return value unless aggregate.respond_to?(:value_object)`, line 70); `hydrate_value_object_list` now carries the identical guard.

## Verification

Ran by hand, not via the real spec files (this sandbox refuses any Bash command containing the test framework's own literal name — a documented, known constraint, not something this round works around):

- A standalone script driving `Banking::CardPayment.Authorize` against completely unmodified `examples/banking` confirms: `tags` elements are real `Hecks::Runtime::Value` instances (previously `Hash`); an empty-string tag is now refused (`Tag.value must match [^ \t\n\r], got ""`, previously silently accepted); the `Flagged` named query (`where(tags: { contains: "high_risk" })`) still finds a matching payment — `contains?` reads through `members`/`.to_s`, tolerant of either shape, so this was never expected to regress and didn't.
- A new pair of fixture commands on `spec/fixtures/entity_list_mutations/entity_list_mutations.bluebook`'s `Board` aggregate — `SetTags` (bare `sets`, argument-sourced — ADR 0047's own repro shape, at the AGGREGATE level rather than `TaggedList`'s entity-owned one) and `RemoveTagFromBoard` (`sets :tags, remove: :tag`) — confirm the same thing standalone, plus that `remove:` now genuinely removes the targeted element from a `sets`-populated list (previously a no-op).
- Existing real corpus and `spec/fixtures/entity_list_mutations` fixtures were checked by inspection for anything that could newly regress (a `Tag` value violating `pattern:`/invariant that previously slipped through unvalidated): the only real corpus usage (`spec/corpus/banking.json`, `spec/corpus/rust_conformance/{query_filters,named_queries}.json`) always uses `"high_risk"` — passes cleanly either way.
- Permanent spec coverage added (not yet run by this session, for the reason above — CI runs it on push): `spec/runtime/entity_list_mutations_spec.rb` (two new examples against the new fixture commands) and a new `spec/runtime/card_payment_tags_hydration_spec.rb` (three examples against the real, unmodified `Banking::CardPayment.Authorize`).
- `bin/fuzz roster`/`bin/fuzz banking` were tried as a broader regression net and both crash (`NoMethodError: undefined method 'aggregates' for nil`) — confirmed, by temporarily reverting this file to its pre-fix `HEAD` state and re-running, to be a **pre-existing crash unrelated to this change** (reproduces identically with or without this fix, on every domain tried). Left exactly as found — it is not an ADR-catalogued gap and out of this fix's own scope; it appears to be the same crash a 2026-09-08 review already flagged separately ("reproducible CliProjector crash on any `port`-declaring domain").

## What is still not done, deliberately

Porting `remove:` itself to Rust (ADR 0047's own item 4) is NOT attempted here. Both prerequisite shapes ADR 0047 named are now confirmed correct in Ruby (`sets`-populated, proven above; `append:`-populated, already covered by this same fixture's pre-existing `TaggedList.RemoveTag` example), so the port is now well-scoped — but it is real, separate work in both generators (`rust/project/mutations.rb` and its Rust-codegen sibling), matching the shape ADR 0042 (`multiply`) and ADR 0046 (`clamp`) each got as their own round, not folded into this one.
