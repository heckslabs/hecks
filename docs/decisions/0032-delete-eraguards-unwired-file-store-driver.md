# Delete EraGuard's unwired file-store driver; keep the primitives Postgres actually uses

**Status:** Accepted — implemented. Historical: `era_guard.rb` has since moved into the era persistence plugin (ADR 0033). Deleted from `lib/hecks/runtime/era_guard.rb`: `check!`, `check_bluebook!`, the `data/eras/*.bluebook` held-snapshot file I/O, and the now-dead `fileutils`/`naming`/`ports/persistence/lineage`/`era_check` requires. `spec/translation/language_spec.rb`'s `describe "EraGuard with the new rule kinds"` block rewritten (not deleted) to call the surviving primitives (`uncovered_attributes`/`unsafe_additions`/`refuse_uncovered!`/`refuse_unsafe_addition!`/`check_vanished_aggregates!`) directly over two in-memory registries — no file I/O, no tmpdir, all 6 examples pass unchanged in substance. Follow-on named in [0031](0031-eras-become-a-registered-boot-gate-not-a-hardcoded-loader-step.md)'s Consequences, which deferred "resolve `EraGuard`/`EraTamper`'s reach into `MetaValidator`/DSL-builder internals and `CoverageCheck`'s call back up into `Runtime::EraGuard`" to its own ADR. Investigating that named problem directly is most of what this ADR is — and it turns out to name the wrong problem, corrected below.

## Context

0031 characterized `PostgresEra::LineageManager::CoverageCheck` calling up into `Runtime::EraGuard` as a coupling shape worth reversing, citing `era_tamper.rb:13-19`'s comment as evidence it "has caused trouble here before." Rereading that comment in full corrects this:

> "LIVES HERE, NOT UNDER `Ports::Persistence` — `project` below directly calls `Runtime::EraGuard.shadow_parse`/`Runtime::StorageShape.project` (DSL-execution machinery), the 'an adapter/port reaches into the runtime instead of being handed already-computed data' shape that has caused trouble here before. A capability this dependent on the runtime is a runtime-owned one that the Postgres adapter CALLS, not a ports-level module that happens to reach sideways into it."

The shape the comment warns against is a *ports-level* module reaching into runtime internals while pretending to be adapter-owned code. The shape it endorses — `EraGuard`/`EraTamper` living in `Runtime::`, with the Postgres adapter calling into them as a client — is exactly what `CoverageCheck` already does. This is deliberate, already correctly placed, and not what needs fixing. **Moving `EraGuard`/`EraTamper` into `PostgresEra`'s own namespace, as 0031 suggested, would contradict reasoning already recorded in the code, so this ADR does not do that.**

Tracing every real caller of `Runtime::EraGuard` instead surfaces the actual problem:

- `Runtime::EraGuard.check!`/`.check_bluebook!` (`lib/hecks/runtime/era_guard.rb:27-63`) is a complete top-level driver: for each bluebook in a registry, read a held snapshot from `data/eras/#{name}.bluebook` (writing it on first sight), shadow-parse it, diff its shape against the current one, and refuse if the drift is uncovered — the same job `PostgresEra` does, independently.
- **No production code calls it.** `grep -rn "EraGuard\.check\b" --include="*.rb" .` outside `era_guard.rb` itself returns exactly two hits, both in `spec/translation/language_spec.rb`. `EraCheck.check_bluebook!` (the real boot-time dispatch, `lib/hecks/runtime/era_check.rb:82-102`) delegates straight to `registry.adapter_class(adapter_name).era_check!` — `PostgresEra`'s own method — and never touches `EraGuard.check!`. `PostgresEra.era_check!` → `LineageManager` keeps its held-shape state in the `hecks_eras` Postgres table, not the `data/eras/*.bluebook` file convention; a repo-wide search for that path (`data.*eras`, `held_path`) outside `era_guard.rb`/its own spec returns nothing.
- The module's own doc comment overclaims what's true in production: "Refuses at boot, before a command can run into the gap" — true for `PostgresEra` via its own, separate driver; not true via this module for anything, since nothing calls it outside a unit spec.
- `PostgresEra::LineageManager::CoverageCheck#check_coverage!` (`lib/hecks/adapters/driven/postgres_era/lineage_manager/coverage_check.rb:19-33`) reimplements the same per-aggregate walk — diff shape, check `uncovered_attributes`, check `unsafe_additions`, call `check_vanished_aggregates!` — independently, differing only in where it gets its comparison rules (`Lineage.from_declared(edge...)`, an already-chosen translation edge, vs. `EraGuard.check_bluebook!`'s `Lineage.for(registry, ...)`, a registry lookup) and in also checking identity-path re-keying (`check_identity_unchanged!`), which `EraGuard.check_bluebook!` doesn't.
- The *primitives* both would-be drivers share — `uncovered_attributes`, `unsafe_additions`, `refuse_uncovered!`, `refuse_unsafe_addition!`, `check_vanished_aggregates!`, `shadow_parse` — are real and load-bearing: `CoverageCheck` calls them directly, `PostgresEra::LineageManager:67` calls `shadow_parse` directly, and `Translation::Reattest` (`lib/hecks/translation/reattest.rb:64`) — a build-time authoring tool, not runtime — calls `shadow_parse` too. Three genuine, independent consumers.
- The DSL-builder forks that thread `MetaValidator.shadow_parsing?` through `value_object_builder.rb`, `attribute_collector.rb`, `translation_builder.rb`, and `identity_declaration.rb` exist to make `shadow_parse` correctly re-read historical bluebook text under old grammar defaults. That cost is inherent to the shadow-parsing feature itself and is paid regardless of which module calls `shadow_parse` — deleting the unwired driver does not remove or reduce it, and this ADR does not attempt to.
- No entry in `docs/future-features.md` or `docs/implemented/postgres-era-adapter-split-plan.md` names a second, non-Postgres lineage- or drift-aware adapter that would consume `EraGuard.check!`'s file-based convention if it existed.

## Decision

Delete the unwired top-level driver; keep everything real callers actually depend on.

- **Delete** `Runtime::EraGuard.check!`, `.check_bluebook!`, and `.check_vanished_aggregates!`'s registry-wide/per-bluebook orchestration wrapper, along with the `data/eras/#{name}.bluebook` held-snapshot file convention (`FileUtils.mkdir_p`, `File.exist?`/`File.write`/`File.read` against `held_path`) in `lib/hecks/runtime/era_guard.rb`.
- **Keep**, unchanged, as the surviving public surface of `Runtime::EraGuard`: `uncovered_attributes`, `unsafe_additions`, `refuse_uncovered!`, `refuse_unsafe_addition!`, `render_path`, `suggestion`, `shadow_parse`, `parse_bluebook` — every method `CoverageCheck`, `PostgresEra::LineageManager`, or `Translation::Reattest` actually calls today. `check_vanished_aggregates!` is kept as a plain per-bluebook method (its current signature already takes `registry, bluebook, held_bluebook` directly — no file I/O inside it), since `CoverageCheck` calls it too.
- **`Runtime::EraTamper` is untouched** — it already depends only on the surviving primitives (`shadow_parse`, `StorageShape.project`), never the deleted driver.
- **`spec/translation/language_spec.rb`'s `describe "EraGuard with the new rule kinds"` block is rewritten, not deleted.** Its `check_era!` helper currently exercises real, valuable, DB-independent coverage of rule-kind detection (rename/retype/move/drop/backfill/rekey) by round-tripping through the file-based driver. Rewritten, it builds both the "held" and "current" bluebooks directly from two scratch registries (no file I/O, no `shadow_parse` round-trip needed — the test already controls both source strings, so there's no historical-text problem to shadow-parse around) and calls `uncovered_attributes`/`unsafe_additions`/`refuse_uncovered!`/`refuse_unsafe_addition!`/`check_vanished_aggregates!` directly, per aggregate — the same shape `CoverageCheck#check_coverage!` already uses. This preserves the exact test coverage this ADR would otherwise cost: fast, DB-independent verification of rule-kind detection, not requiring a live Postgres connection the way `spec/adapters/driven/postgres_era/lineage_spec.rb` does.

## Consequences

- `Runtime::EraGuard`'s module doc comment stops overclaiming a boot-time guarantee ("refuses at boot... the file-store boot check here, or Postgres's mint path") that was never true for anything but `PostgresEra`'s own, separate driver. The rewritten comment describes it as what it now plainly is: the shared coverage-diff primitives `PostgresEra` and `Translation::Reattest` both call.
- No behavior changes for `PostgresEra` or any currently-shipped domain — nothing production-facing called the deleted driver, so nothing production-facing is affected by its removal.
- Rule-kind-detection test coverage stays fast and DB-independent (rewritten spec), rather than either disappearing or migrating into `spec/adapters/driven/postgres_era/lineage_spec.rb`'s slower, live-Postgres path.
- If a future non-Postgres adapter ever wants boot-time shape-drift detection without full lineage/mint machinery, it's rebuilt then, informed by `CoverageCheck`'s real orchestration (the one production implementation that has actually been exercised) rather than resurrecting a driver that was written once, never wired up, and never validated against a real adapter.
- This ADR does not touch the DSL-builder `shadow_parsing?` forks — that cost is real, orthogonal, and out of scope here; nothing in this decision reduces or increases it.
- Closes out [0031](0031-eras-become-a-registered-boot-gate-not-a-hardcoded-loader-step.md)'s named follow-on. No further ADR is implied by this one.

## Rejected alternatives

- **Finish wiring `EraGuard.check!` into a real adapter's boot path** (option B considered directly). Rejected — no adapter is named anywhere in the roadmap that would consume it, and building out a second, generic drift-guard mechanism ahead of a concrete second consumer repeats the same speculative-generality mistake [0031](0031-eras-become-a-registered-boot-gate-not-a-hardcoded-loader-step.md) itself declined (shipping `BootGates` proven by two real gates, not zero).
- **Move `EraGuard`/`EraTamper` into `PostgresEra`'s own namespace**, as originally proposed in 0031's forward pointer. Rejected on rereading `era_tamper.rb`'s own comment in full — it defends the current placement (`Runtime`-owned, adapter-as-caller) as the correct shape, not the problem.
- **Delete `spec/translation/language_spec.rb`'s EraGuard tests outright**, relying on `spec/adapters/driven/postgres_era/lineage_spec.rb`'s live-Postgres coverage instead. Rejected — that coverage requires a real database connection; losing the fast, DB-independent path for rule-kind-detection logic is a real regression in test speed and CI-independence, not a neutral cleanup.
- **Leave the driver in place, just fix the doc comment.** Rejected — the file-I/O convention and the duplicate per-aggregate orchestration are the actual maintenance liability (a second place rule-kind-coverage logic could silently drift from `CoverageCheck`'s), not merely the comment's wording.
