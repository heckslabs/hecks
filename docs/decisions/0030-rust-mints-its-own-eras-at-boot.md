# Rust mints its own eras at boot — no Ruby process in production, no migrations

**Status:** Accepted — implemented. Supersedes [0029](0029-rust-reads-and-writes-any-era-ruby-mints.md)'s central decision ("minting stays Ruby's job, permanently") — everything else 0029 shipped (the generic `journal::read_lineage_head_all`/`_by_id`/`append_lineage_mutation` path, `lineage_harness`, the first differential harness) is unchanged and is exactly what a Rust-minted era still reads and writes through afterward. New: `rust/host/src/storage_shape.rs`, `mint.rs`, `approval.rs`, `reference_transform.rs`, `reference_validate.rs`, `bin/mint_harness.rs`; rewritten: `main.rs`'s boot gate (`HECKS_ERA` removed entirely); Ruby side: `lib/hecks/translation/rule_compiler.rb` (extracted, shared with `head_compiler.rb`), `Exporter.translation_hash`/`translation_aggregate`/`translations`/`compiled_translation_aggregate`, `bin/project_rust`'s new `translations`/`source_text` export; new differential fixture `rust/host/tests/fixtures/mint_via_rust_matches_ruby.rb`.

## Context

0029 drew a clean line: Rust reads and writes against any era Ruby has already minted; minting — provisioning, compiling migration SQL, running the audit, gating on an approval digest — stays Ruby's job permanently. That line rested on two of this project's own standing decisions ([0010](0010-ruby-is-the-reference-implementation.md), Ruby is the reference implementation; [0011](0011-rust-compiles-types-interprets-dispatch.md), per-shape codegen doesn't converge) and was a reasonable reading of them — right up until the user stated the actual production requirement directly, once 0029 had already shipped:

> "yes — its the reference implementation but rust will have no dependencies on Ruby implementation in production. So it has to mint its own eras."

And, more specifically, ruling out the obvious middle ground (a deploy-time step where an operator runs Ruby against the target database before redeploying Rust):

> "okay, i don't want it to be a deploy thing. I want the rust runtime to refuse to boot unless it has a translation and then mint — that's the point — no migrations. There's no way around it."

This is a different, stricter claim than 0029's own "Rust stays dependent on Ruby to mint" consequence anticipated, and it is the actual requirement, not a hypothetical one this project might grow into. "Ruby is the reference implementation" ([0010](0010-ruby-is-the-reference-implementation.md)) still holds — Ruby remains the sole *authority* that a translation edge is well-formed, that a `compute`/`rekey` edge has been sampled and approved by a human, and that a bluebook parses at all. What changes is *who executes the mint transaction in production*: not "Ruby runs it, Rust reads the result later," but "Rust runs it itself, against SQL Ruby precompiled and shipped ahead of time" — the exact split this codebase already uses everywhere else (commands, types, the expression grammar's operator table, the parser's own keyword table): Ruby compiles once at build time; the deployed Rust binary executes, with zero Ruby process anywhere near it.

Three research passes over the real mint transaction (`lineage/mint_transaction.rb`, `head_compiler.rb`, `provisioning.rb`, `resumable_backfill.rb`) confirmed this was buildable along exactly that seam, with one real, independent bug found and fixed first: `Exporter.translation_hash`/`translation_aggregate` omitted `rekeys`/`backfills` entirely, meaning a recorded approval for a `rekey`-bearing edge never actually bound to that edge's own rekey SQL, in production, today — closed regardless of this ADR ([lib/hecks/projector/exporter.rb](../../lib/hecks/projector/exporter.rb)).

## Decision

Rust's own boot gate (`main.rs`) computes its own compiled shape hash and label (`storage_shape.rs`, a byte-exact Rust port of `StorageShape.project`/`mint_hash`, over the same canonical IR already flowing through `ir.json`) and decides, entirely on its own, using only what `hecks_eras` and `ir.json` already tell it:

- **A held era already names this exact shape** — boot at it, whichever ordinal (RLS refuses a write if it turns out superseded — [0029](0029-rust-reads-and-writes-any-era-ruby-mints.md)'s own proven guarantee, unchanged).
- **No held era at all** — this domain is brand new to this database. Mint era 1 itself (`mint::hold_first`), zero Ruby involved.
- **The latest held era's shape differs from this binary's own** — walk the one translation-edge chain leaving it (`mint::edge_chain`, over `ir.json`'s `translations` key), check every compute/rekey edge in that chain against a matching, unstale, human-recorded approval (`approval::check` — the identical digest/freshness semantics `lineage_manager/minter.rb` holds itself to, cross-checked byte-for-byte against Ruby's own real `ApprovalDigest.edge_digest` output), run the full live audit (below), then mint the next era itself (`mint::mint_era`).
- **No translation edge covers the drift** — refuse to boot, by name, toward `bin/scaffold_translation`/`bin/translation_audit --approve`. This is the actual point: no deploy-time Ruby step, no migration, just a refusal until a human authors and reviews the edge — then the very next boot mints it.

**The mint executor** (`mint.rs`, ~1000 lines) is a faithful, function-for-function port of the real DDL/DML sequence — provisioning (`hecks_eras`/`hecks_approvals`/the journal/the six `hecks_tr_*` SQL functions, all idempotent), per-era partition + head-snapshot + matview + head-view assembly, the synchronous chunked backfill (SAVEPOINT-nested, matching Ruby's own `resumable_backfill.rb`), role grants, the RLS fence flip — using SQL Ruby's `Translation::RuleCompiler` (extracted from `head_compiler.rb`, now shared by both the live mint path and this export) precompiled once at build time and shipped in `ir.json`'s new `translations` key. Rust never compiles a migration rule to SQL; it only executes text Ruby already compiled — the identical "compile once, execute generically" shape [0022](0022-self-host-the-expression-grammar.md) already established for the expression grammar.

**Full live-audit parity, not a weaker approximation** — the user's own explicit choice when asked how much of Ruby's live safety verification Rust should reproduce ("Full parity — Rust re-verifies live, matching Ruby's guarantee exactly"):

- **Layer 2** (`reference_transform.rs` + `mint.rs`'s own `audit_before_mint`) — a direct port of `Ports::Persistence::Lineage#translate`, the pure portable-rule interpreter (rename/move/convert/drop/backfill) Ruby's own Layer 2 diffs the compiled SQL against. Reads the live compiled chain as a plain `SELECT` (never the persisted matview — a refusal here must leave no half-born era, the same ordering `Minter#mint!` holds itself to: audit before mint), independently re-derives what the translation *should* produce, and hard-refuses the whole mint if they disagree anywhere a `compute` rule doesn't own — plus the same id-set/record-count conservation checks Ruby's own Layer 2 makes.
- **Layer 1** (`reference_validate.rs`) — structural parity: every translated record must satisfy its aggregate's declared types, patterns, admits/closed-set, and lifecycle (its state field, if any, must be a value the lifecycle actually reaches) — recursively, through nested value objects and entity lists, generic and IR-driven off `ir.json`'s already-present metadata, no new Ruby export needed for this part.
- **A deliberate, named gap, not a silent one**: custom value-object invariant *predicates* (`invariants: [{canonical: "cents >= 0"}]`, arbitrary expression text) are not evaluated. Everything else Layer 1 checks in Ruby now runs live in Rust; this one piece doesn't yet. See Consequences for why and what closing it needs.

**`mint_harness`** (`bin/mint_harness.rs`) is the differential-parity proof's Rust side — the same `#[path]`-included-sibling-modules shape `lineage_harness.rs` (0029) already established, running the exact boot-gate sequence above standalone, pointed at a real `ir.json` file instead of `HECKS_IR_PATH`. `mint_via_rust_matches_ruby.rb` is the first fixture in this codebase where *both* sides of a diff are a real mint, in two different languages, against two separate scratch databases, using `ir.json` genuinely produced by `Hecks::Projector::Exporter` rather than a hand-approximated shape — and it passes: Rust's own mint (DDL, translated data, everything) agrees with Ruby's, byte for byte.

## Consequences

- **The user's actual requirement is met**: the deployed Rust binary has zero dependency on a running Ruby process in production. Ruby's role is now build-time-only for this subsystem too — author a bluebook change, scaffold and review the translation edge, approve any `compute`/`rekey` sample, regenerate `ir.json` — matching every other part of this codebase already built this way.
- **Scoped to a domain's own aggregates — not to any vendored/framework chapter it attaches (`uses_framework`).** `Exporter.lineage` (and hence `ir.json`'s `lineage.capable_aggregates`, and hence `mint::hold_first`'s own list) is computed for exactly one bluebook — the target domain's — never for a chapter it vendors (e.g. Banking's `uses_framework "Governance"`/`"Identity"`). But a vendoring domain's compiled dispatch table genuinely includes the vendored chapter's own commands (`rust/src/generated/<domain>/merged.rs` lists `Governance::RoleAssignment.Assign` etc. directly), and `rust/host`'s runtime write path (`dispatch.rs::step_mutations` → `journal.rs::append_lineage_mutation`) journals whatever aggregate name the kernel hands it, with no filter against the domain's own capable-aggregates list. So the deployed Rust binary genuinely CAN mint its own era 1 for its own aggregates with zero Ruby — but head-snapshot tables for a vendored chapter's aggregates are never provisioned by that self-mint, only by `bin/project_deploy`'s generated `mint-era` Makefile target, which walks every OTHER loaded bluebook and calls `ensure_first_head!` for their aggregates too (a real fix for a real production incident — see that target's own comment, `bin/project_deploy:1616-1633`, quoting the exact refusal a vendored aggregate's first write hit: `relation "payment_head_snapshot_1" does not exist`). Until `Exporter.lineage`/`ir.json` is extended to also export a vendoring domain's attached chapters' own lineage-capable aggregates, **a domain with no `uses_framework` vendoring is genuinely deploy-time-Ruby-free; a domain that vendors a framework chapter still needs the Makefile's `mint-era` step (specifically, its vendored-chapter loop) at least once per newly-attached chapter.** Not yet closed; named here so it isn't mistaken for done.
- **Ruby is still the reference implementation and the sole authority for what's *correct*** — it still parses bluebooks, compiles migration SQL, and is where a human reviews and approves a `compute`/`rekey` sample. What moved is *execution*, not *authority*. [0010](0010-ruby-is-the-reference-implementation.md) still holds; this ADR does not reopen it.
- **Two deliberate, documented narrowings from Ruby**, both because this crate has no bluebook parser (`rust/parser`, never linked into `rust/host` — [0012](0012-what-is-hecks.md)'s own boundary):
  1. Era 1 is named *eagerly* at hold time (it already has its own shape hash in hand — that's why it's holding), not lazily the way Ruby's `ensure_named!` re-parses held text on demand. No behavioral gap; only a timing difference.
  2. An existing held era with a `NULL` hash (one Ruby minted and never named, because nothing had drifted away from it yet) is out of scope for Rust to mint forward from — refused by name ("boot Ruby once against this database to name it, then redeploy"), not silently stalled.
- **A third, performance-only narrowing**: the mint executor always uses the full (non-layered) ancestor-tail chain build, never `head_compiler.rb`'s own `layered_chain_sql` optimization (building era N from era N-1's already-materialized matview instead of re-scanning the raw tail). Correctness is identical either way; this is deferred until a real deployment's era count makes the difference matter.
- **The named Layer 1 gap (invariant predicates) is real and left open on purpose, not rushed shut.** Closing it needs an executable form of `canonical` expression text Rust can run without either (a) a *third* independently-written expression interpreter (this codebase's own recurring lesson — [0022](0022-self-host-the-expression-grammar.md) exists precisely because a second one was a mistake), or (b) a direct Cargo dependency on the `rust` kernel crate to reuse `rust::kernel::expr::interpret` directly, confirmed unsafe: `rust/src/generated/mod.rs`'s own per-domain `pub mod` list is not feature-gated (only the `active` re-export is), so any dependency on that crate would statically bake every domain's generated dispatch code into every Lambda's own deployed binary regardless of which `.wasm` it actually loads at runtime — the exact per-domain isolation `rust/host`'s own `Cargo.toml` holds itself to. The real fix is a new build-time export: the same parsed AST `rust/project/expr_emitter.rb` already builds (today only emitted as Rust source literals) serialized to `ir.json` as JSON data too, plus a small interpreter in `rust/host` that consumes it as data. Scoped out of this pass, named here so it isn't lost.
- **A real, independent bug was found and fixed along the way**, unrelated to whether this ADR shipped at all: `main.rs`'s own boot gate called `journal::held_eras` before anything provisioned `hecks_eras` — on a truly fresh Postgres instance, the very first domain ever deployed would have crashed at boot instead of holding era 1. Found live, by `mint_harness` exercising the real boot-gate sequence end to end for the first time (every existing lineage test called `mint::hold_first` directly, which provisions internally). Fixed by calling `mint::ensure_base` unconditionally, right after `journal::ensure_schema`, before the first `held_eras` call — idempotent, so this costs nothing on a database that already has the tables.
- **[0029](0029-rust-reads-and-writes-any-era-ruby-mints.md)'s "Rejected alternatives — Full port" entry is no longer rejected; it's what shipped.** Its own reasoning (contradicts 0010, repeats 0011's per-shape-codegen failure mode) does not actually apply here, because this was never a per-shape Rust SQL compiler — the SQL is still compiled once, by Ruby, and shipped as data, the identical shape 0011 itself pointed toward as the alternative that *does* converge.

## Rejected alternatives

- **A deploy-time migration step** (operator runs Ruby against the target database, then redeploys Rust) — explicitly ruled out by the user directly: "i don't want it to be a deploy thing... no migrations. There's no way around it." This was the natural reading of 0029's own scoping and is exactly what this ADR replaces.
- **Rust links the `rust` kernel crate directly to reuse its expression interpreter for Layer 1 invariant predicates** — rejected; see Consequences above. Would work today but silently reintroduces the per-domain coupling `rust/host`'s whole design (opaque, per-domain `.wasm` modules loaded at runtime, zero compile-time linkage) exists to avoid.
- **A second, hand-written expression interpreter duplicated into `rust/host`** — rejected for the same reason `rust::kernel::expr`'s own header gives for existing at all: this codebase has already paid for a duplicated-interpreter mistake once (why [0022](0022-self-host-the-expression-grammar.md) exists); a third copy repeats it rather than closing the actual gap, which is a missing *export*, not a missing *interpreter*.
- **Ship Layer 1 as a stub that always passes** — rejected as dishonest relative to the user's explicit "full parity" choice. The structural half (types/patterns/admits/lifecycle) is real, live, and shipped; the predicate gap is named and left open rather than papered over.
