# `list_of admits:/pattern:` resolved — not by porting a new capability, but by removing a real Rust over-enforcement

**Status:** Shipped, following up on ADR 0043's own left-open question. ADR 0041 named `list_of admits:/pattern:` as a "structurally close" backlog item; ADR 0043 investigated it, found a bigger, more consequential unknown underneath (whether the SCALAR case's own usage-level `admits:`/`pattern:` check has any real Ruby enforcement at all), and stopped short of a verdict — "resolving this needs reading `Runtime::CommandInterpreter`'s FULL dispatch pipeline closely... that is real, separate investigation work." This ADR is that investigation, completed, with a concrete fix.

## The question, answered exhaustively

Traced `Runtime::CommandInterpreter::DISPATCH_ORDER` (`lib/hecks/runtime/command_interpreter.rb:32`) in full — not just the `MutationApplier`/`Arithmetic` paths ADR 0043's own investigation stopped at. `normalize_args` runs as step 3, **unconditionally, on every dispatch**, before `enforce_givens`/`apply_mutations`. It calls `coerce_declared_arguments` (`interpreting.rb:70-77`), which walks **every declared command attribute present in the payload** — not just mutation sources/targets — through `Value.for_attribute` (`value/coercion.rb:52-80`).

Inside `for_attribute`, two DIFFERENT things happen depending on the check:

- **`admits:`** — `admit_declared_set` (`value/admission.rb:56-67`) fires unconditionally at line 78, for every SCALAR attribute (list attributes return early into `hydrate_entity_list` at line 56, before ever reaching it). This is genuinely, unconditionally enforced by Ruby — for scalar attributes, regardless of whether they're ever a `sets` mutation source.
- **`pattern:`** — `check_patterns` (`coercion.rb:547-561`) is called only from `validate!`, called only from `build` (`coercion.rb:268-273`) — i.e. only when the attribute's type resolves to an actual VALUE OBJECT and gets rebuilt. A bare-scalar command attribute carrying its own `pattern:` directly (not via a VO's own field) never triggers a `build` call at all, so `check_patterns` is **never reached — for either scalar or list shapes, mutated or not.**

Confirmed live, not just by static trace: a purpose-built fixture (same pattern as ADR 0042/0043 — a temp copy of `examples/banking`, a new `Account.TagAccount` command with `attribute :label, String, pattern: '^[a-z]+$'`, never a `sets` source) dispatched against Ruby's real interpreter with a pattern-violating value (`"NOT-LOWERCASE"`) — **silently accepted**, no refusal, `label` never stored (a pure fact-recording argument, as expected). A parallel `admits:`-carrying fixture, same shape, **correctly refused** (`"marker admits Account::AccountKind — ... — got \"totally-invalid\""`), confirming the split is real, not uniform permissiveness.

Grepped the real corpus (`examples/*/bluebook/*.bluebook`) for every `admits:`/`pattern:` occurrence: every `pattern:` hit sits inside a `value_object "..." do` block (a VO-field-level declaration — `types.rb`'s own, separate, correctly-enforced-on-both-sides check) — zero real corpus commands declare a USAGE-LEVEL `pattern:` on their own attribute at all. `list_of admits:`/`pattern:` similarly has zero real corpus declarations. Confirms ADR 0043's own finding: this gap is real but currently unreached by any shipped domain.

## The fix — not a port, a removal

`rust/project/commands.rb`'s `invariant_checks_for` (mirrored in `rust/codegen/src/commands.rs`) generated `emit_pattern_check` unconditionally for every non-list command attribute, right alongside `emit_admits_check`. Given the confirmed split:

- **`emit_admits_check`'s existing scalar behavior is correct — kept exactly as it was.** Ruby genuinely enforces it unconditionally; Rust already matched.
- **`emit_pattern_check`'s call from `invariant_checks_for` is removed entirely.** Ruby never enforces a usage-level scalar `pattern:`, so generating a check here made Rust STRICTER than the reference implementation — the opposite direction from every other gap this whole plan has closed. Per ADR 0010 (Ruby is the reference implementation; Rust conforms to it, not the other way around), the check is removed rather than Ruby's own behavior changed — reversing this would be a real product decision (making Ruby newly refuse something it has always silently accepted), out of scope for an equivalence fix. `types.rb`'s own separate call to `emit_pattern_check` — the VALUE-OBJECT field-level door, which genuinely does fire via `build` in Ruby — is untouched; only the command-level usage door's call site changed.
- **`constraint_list_problems` (and its two call sites, `command_skip_reason`/`port_operation_skip_reason`) is removed entirely**, in both generators. It used to refuse generating a WHOLE command/port-operation outright whenever a list attribute carried `admits:`/`pattern:` — a real, but now-unnecessary, over-restriction: neither is ever enforced by Ruby for a list attribute either (`admit_declared_set` is reached only via the scalar branch of `Value.for_attribute`), so the honest behavior is to generate the command normally with no check for that attribute (which `invariant_checks_for`'s own pre-existing `unless attr[:list]` guard already produces for free), not to refuse the whole command. This is what actually resolves the original `list_of admits:/pattern:` backlog item — not a new per-element check, but recognizing the existing skip (`unless attr[:list]`) was already the right generated code, and the surrounding REFUSAL around it was the only wrong part.

## Verification

- **Red-before/green-after, both engines, for real**: the `TagAccount` fixture regenerated through the OLD (pre-fix) generator refused with `"label.label must match ^[a-z]+$, got \"NOT-LOWERCASE\""` — confirmed as the real, live divergence. Regenerated through the fixed generator: no refusal, `label` silently unstored, byte-for-byte matching Ruby's own real dispatch result for the identical script.
- **Both generators verified in lockstep for the ONE shape neither real corpus nor `spec/codegen_parity_spec.rb` exercises**: ran the `hecks-codegen` binary directly against the fixture's own IR and diffed its `account.rs` output against `bin/project_rust`'s — byte-identical except the expected domain-name string in the header comment (a parameter difference, not a generator divergence).
- `spec/codegen_parity_spec.rb --tag io`: 8/8, unchanged — confirms zero real corpus command exercises either checked path, so this fix has zero observable effect on any currently-shipped domain (matching the grep finding above).
- `spec/rust_conformance_spec.rb spec/codegen_parity_spec.rb --tag io`: 30/30.
- Full sweep: `bundle exec rspec` (2232/0), `bundle exec rubocop` (645 files/0 offenses).
- Every real domain builds clean and regenerates byte-identically outside the intended diff: banking, compliance, pizzas, roster, meta.
- `git status` confirmed clean of unrelated byproduct drift (`Cargo.toml`/`mod.rs` default-feature bookkeeping, `governance`/`identity` framework-regen churn, the temp fixture's own generated output) before commit.

## What this means for the original backlog item

`docs/decisions/0041`'s own "`list_of admits:/pattern:` — structurally close" framing turns out to have needed no new per-element list-checking machinery at all. The list case was never actually a missing capability — Ruby's own real behavior for a list attribute's `admits:`/`pattern:` is silent non-enforcement, which is exactly what dropping the check (already the generated behavior via the pre-existing `unless attr[:list]` guard) produces. The only genuine bug was the SURROUNDING refusal (`constraint_list_problems`) that stopped such a command from generating at all, and a second, independently-discovered over-enforcement on the SCALAR side that ADR 0043 surfaced but couldn't resolve without this exhaustive trace.
