# Lineage becomes optional in the Rust Lambda host, but auth stays bound to it

**Status:** Accepted — implemented.

## Context

ADR [0033](0033-eras-become-a-loadable-persistence-plugin.md) made eras a loadable plugin on the Ruby side. `rust/host` (the compiled Lambda binary — one binary per domain, `bootstrap`, no runtime plugin system: "Rust has no runtime plugin system and shouldn't grow one" — ADR 0031's own rejected alternative) has no equivalent seam and was never investigated for one until this ADR — architecturally positioned "eventually" (no concrete domain needs it today; every currently-deployed domain has ≥1 lineage-capable aggregate), for the same reason 0033 was: eras/lineage might someday be something the company provides outside Hecks core.

Investigation (not assumption) found the real shape of the coupling:

- `mint::decide_boot_action` (the hold-first/use-existing/mint-next/refuse decision) takes only `held: &[HeldEra]`/`my_label: &str` — it never consults `aggregates` at all. The mint/hold sequence runs at boot regardless of whether anything is lineage-capable.
- `dispatch::handle`'s advisory lock (`dispatch.rs:135`, `SELECT pg_advisory_xact_lock(hashtext('hecks_lambda_journal.' || $1::text))`) is keyed on `config.domain` — the domain NAME, needed for every dispatch regardless of lineage, not an era-specific fact.
- The per-mutation head-snapshot journaling loop (`dispatch.rs`'s `step_mutations` loop, calling `journal::append_lineage_mutation`) is the one piece that's genuinely lineage-only — and per `journal.rs`'s own header, deliberately never wired into `dispatch::read`'s ordinary rehydrate-replay seed, so nothing else depends on it.
- `auth.rs`'s Google-auth `Member` sessions (`append_member_state`, `provision`, `grant_access`) go through this exact same lineage machinery (`append_lineage_mutation`, `read_lineage_head_by_id`/`_all`) specifically because `Member` isn't reachable through `dispatch::read`'s own instance path — a real architectural reason (indexed point-lookup by id), not an accident.
- Real proof the coupling is load-bearing, not incidental: `examples/pizzas/bluebook/pizzas.hecksagon` binds `Order` to `PostgresEra` (lineage-capable) but `Governance::RoleAssignment`/`RoleTransition` to plain `Memory` — both dispatch through the same Lambda host and, today, the same domain-wide era.
- `main.rs` is genuinely one binary, one entry point (`[[bin]] name = "bootstrap"`), handling dispatch, the web UI, and auth in-process — there's no separate "auth build" to statically exclude the coupling; the decision has to be made at boot, from data, not at compile time.

Design-review settled two things before implementation: (1) `auth.rs`/`Member` always requires the lineage subsystem present, permanently, regardless of what the domain's other aggregates use — no new non-lineage persistence path gets built for a need nothing has named yet; (2) this ships as an ordinary redeploy, no coordinated migration — every currently-deployed domain already has ≥1 lineage-capable aggregate and takes the unchanged branch either way.

## Decision

**`journal::LineageConfig` keeps `domain: String` mandatory and changes only `era` from `i32` to `Option<i32>`.** This is the one design choice that made the rest of this change small instead of sprawling: `domain` is needed unconditionally (the advisory lock), so it was never the right field to wrap in an outer `Option<LineageConfig>` — doing that would have forced threading `Option<&LineageConfig>` through every function in `web.rs` that touches `config.domain` on the way to somewhere else, for no functional gain. Only `era` — the fact that's genuinely absent for a domain with nothing lineage-capable — needed to become optional. `web.rs`'s and `dispatch.rs`'s outer function signatures (`render`, `route`, `auth_route`, `google_callback`, `handle`, `handle_routed`, `handle_facts`, …) are **unchanged**.

**`main.rs`'s boot gate computes `needs_lineage = !aggregates.is_empty() || std::env::var("GOOGLE_CLIENT_ID").is_ok()`** before touching the database for anything lineage-related. When true, everything runs exactly as before (`mint::ensure_base`, `journal::held_eras`, `mint::decide_boot_action`, hold/mint) and `era` is `Some(ordinal)`. When false, none of that runs — `hecks_eras` is never provisioned, never queried, never minted into — and `era` is `None`, directly, with zero DB interaction for lineage at all.

**`journal::append_lineage_mutation`** — the one true chokepoint every lineage write passes through — internally does `let Some(era) = config.era else { anyhow::bail!(...) }` at its own top, using the resolved `era` for the rest of its body. This is a defensive backstop, not the primary gate.

**`dispatch::handle`'s `step_mutations` loop** — the primary gate — is skipped entirely when `config.era.is_none()`: an empty `Vec` stands in for `step_mutations`, so the loop body (and therefore `append_lineage_mutation`) never runs for a lineage-free domain's ordinary business dispatch. Nothing else needed to change in `dispatch.rs`.

**`auth.rs` is untouched.** Its functions still take `config: &LineageConfig` and still call `append_lineage_mutation`/`read_lineage_head_by_id`/`read_lineage_head_all` exactly as before. This is safe by construction: `auth.rs` is only ever reached once Google auth is actually configured (`GOOGLE_CLIENT_ID` set, checked independently by `auth::authorization_url` itself before anything else), and configuring it is exactly what makes `needs_lineage` (and therefore `era: Some(_)`) true in the first place. `append_lineage_mutation`'s own internal bail is what catches it if that invariant is ever violated, rather than a silent wrong answer.

## Consequences

- A domain with nothing lineage-capable and no Google auth configured never touches `hecks_eras`/`hecks_approvals` at boot — genuinely absent from that boot's call graph, the same "structurally absent, not run-and-skipped" shape ADR 0031 established Ruby-side for `Runtime::BootGates`.
- Verified against the real cross-language differential harness, not just unit tests: `spec/rust_host_lineage_conformance_spec.rb`'s 5 examples (previously reported as `pending` in this environment due to an unrelated rustc-version mismatch between Homebrew's default toolchain and what `aws-config`/`aws-sdk-lambda` require) all pass once the correct toolchain is on `PATH` — Rust's own mint, and Rust's own lineage read/write path, byte-for-byte match Ruby's, unchanged by this ADR.
- `cargo test --bin bootstrap`: 86 passed both before and after this change; the 17 failures in both runs are an unrelated, pre-existing environment gap (`dist/*.wasm` build artifacts not present in this working tree), confirmed identical before and after.
- No new Cargo feature flags, no new binary targets, no runtime plugin system for Rust — consistent with ADR 0031's own rejected alternative ("Rust has no runtime plugin system and shouldn't grow one"). The conditional lives entirely in `main.rs`'s boot sequence, reading data (`ir.json`'s `lineage.capable_aggregates`, the `GOOGLE_CLIENT_ID` environment variable) already available to it.

## Rejected alternatives

- **Wrap the whole `LineageConfig` in `Option`** (`Option<&LineageConfig>` threaded through `web.rs`/`dispatch.rs`). Rejected on investigation: `config.domain` is used unconditionally for the advisory lock (`dispatch.rs:135`) and read directly in `web.rs` (a comparison of `config.domain` against one client domain's name in `web.rs`) — neither is lineage-specific. Making the whole struct optional would have forced an `Option`-unwrap or `.map()` at every one of those sites for no functional reason, when only `era` is genuinely sometimes-absent.
- **Physically split `journal.rs` into an ordinary-journal module and a lineage-specific module**, as originally planned during design review. Rejected on investigation, not assumption: `crate::journal::{snake, quote_ident, LineageConfig, Mutation, append_lineage_mutation, read_lineage_head_all, read_lineage_head_by_id, HeldEra, held_eras, Approval, approval_for, last_ordinal}` are imported directly by `mint.rs`, `approval.rs`, `auth.rs`, `dispatch.rs`, `main.rs`, and `web.rs`'s own test code — a real split means updating import paths across all six files for a purely organizational win, since the functional goal (era becomes optional) needed none of it. The struct-field change above achieves everything the split was meant to enable, at a fraction of the risk, with nothing left half-done: `journal.rs`'s own top-of-file header already correctly describes itself as "deliberately non-era-aware" for the ordinary-journal half and names the lineage functions as "the part of this crate that does [have an era/lineage concept]" — the file already documents the boundary; it didn't need to physically enforce it too.
- **Build a new non-lineage `Member`-persistence path** so Google auth could work in a lineage-free domain. Rejected before implementation (design review) and reconfirmed here: `auth.rs`'s existing coupling to the lineage head-snapshot mechanism is there because `Member` needs indexed point-lookup-by-id that the ordinary replay/journal model doesn't provide as cheaply — a real architectural reason, not an oversight — and no domain today needs a lineage-free deployment with Google auth.
- **A Cargo feature flag** (`--features lineage`) to statically exclude `mint`/`approval`/`reference_transform`/`reference_validate`/`storage_shape` from a lineage-free build. Rejected — there is only one binary target (`bootstrap`) serving every domain; a feature flag would require a second compiled artifact per domain (lineage vs. not), decided at build time, when the actual decision (does *this* domain need lineage) is a runtime fact from `ir.json`/environment, not a build-time one. The `if needs_lineage` branch in `main.rs` gets the same result without a second binary to maintain.
