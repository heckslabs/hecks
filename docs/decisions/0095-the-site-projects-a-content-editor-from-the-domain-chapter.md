# The Site projects a content editor from the domain chapter

**Status:** Proposed. Date: 2026-10-06. A project that publishes content needs its editors to create and change it. The Site chapter projects a third-party content system's half of the sign-in and drives the domain from it; this adds a small editor of our own, generated from the domain's bluebook, so editing needs no third-party CMS.

## Context

`AdminCms` and `PayloadDriver` assume a content system that owns the editing screens and the data model, and the domain is made to follow it. The domain is already declared: its aggregates, attributes, value objects, lifecycles, commands (with roles) and queries say what can be created and what can be changed, and the host already answers `/dispatch` for exactly those. An editor is the part that is left, and it can be derived.

ADR 0092, ADR 0093 and ADR 0094 were taken when this was merged, so this is 0095.

## Decision

1. **A projector, `:site_cms_editor` (`Site::CmsEditor`), emits the files of a small Node/TypeScript package.** It takes the `Editor` row (the domain's directory and chapter, where the editor is served, the session cookie, the host's address variable, the login page, the roles) and the domain chapter, and writes under `--editor=<dir>`: `src/schema.ts`, the server, the sign-in, the pages, the form reader. The output is a pure function of the row and the chapter, with the banner every projection has and no time or machine in it, so it is golden-tested and `--check` holds it current.
2. **The editor is generic by aggregate.** The pages and forms are not generated per aggregate. `src/schema.ts` carries the chapter's shape as one typed constant (names, kinds, optional, `list_of`, value objects, lifecycle transitions, command roles, queries), and the same few files read it for every aggregate. A value-object attribute is a nested fieldset, a `list_of` attribute is a run of repeatable rows, a lifecycle state is a badge, never an input, and a lifecycle move is offered only from the states it applies in. This is the shape the CMS packages use (a slug as identity, value objects, lists nested two levels, optional parts, a lifecycle, commands that act on one instance); an aggregate of any other shape is edited by the same code.
3. **The domain never holds editor JSON.** The editor reads and dispatches through the host like any other client (`@hecks/client`'s `HostClient`: `read`, `query`, `dispatch`), and nothing about the editor is declared in the domain: no editor attribute, no editor aggregate. The editor-facing detail (title, base path, roles) is in the `Editor` row beside the route table, on the Site side, as `PayloadField` rows are.
4. **The server is a sidecar and authenticates for itself.** The host honours `/dispatch` only from the same machine, so the editor is a server-side caller, not code in the browser, and the browser never gets that access. Every person is authenticated by the editor: the site's admin hand-off sends a signed-in admin to `sso_path` with a short-lived account token, which the server verifies with the secret it shares with the host (`verifyAccountToken`); the editor then asks the host's members list whether the person holds one of the roles, and only then starts its own signed session cookie. The list is asked again on every request (remembered for a minute), so removing someone locks them out; a question that cannot be asked is a no. Posts from another site are refused (SameSite=Lax and an Origin check). This is the sign-in `AdminCms` generates for a content system, written for a plain server.
5. **A command's outcome is judged by the state that comes back.** The host answers HTTP 200 whether or not the domain refused, and its `refusals` can be replayed from history. The editor reads the instance before and after; a lifecycle move must reach its target, any other command's arguments must be in the new state, and only when nothing changed does the last refusal naming this verb decide. A refusal is shown inline on the form in the domain's own words, with the person's input kept. Commands run as the role they declare.
6. **`@hecks/client` gains `query(name, args?)`** (and `rowsOf` to read its answer), because the host's `/dispatch` already answers `{"query": name, "args": {...}}` and a list page is a query. It is additive.
7. **Templates are files, not heredocs.** The TypeScript is about nine hundred lines; each file is a `.tmpl` with `__NAME__` placeholders beside the projector (as the deploy projections keep theirs), so it reads, highlights and type-checks as TypeScript. Placeholders are filled in one pass, so a value that looks like one is left as it is.

## Consequences

- A project gets an editor for its domain from a row, with no content system to run, secure and keep in step with the domain.
- Adding an attribute, a command or a lifecycle state to the bluebook changes the editor on the next projection; a stale editor fails `--check`.
- An attribute whose value object is a structured document body is edited with a rich-text widget (see the addendum).
- `rust/host` is unchanged.

## Alternatives considered

- **One generated page set per aggregate.** More output, and a change to the shape of any page means a change to every one; the generic server has one set of pages.
- **A browser app calling the host.** The host refuses a non-loopback caller by design, and a browser that could reach it would hold the domain's whole write surface.
- **Keeping editor state in the domain.** The domain would then name its editor; the editor is a client of the domain, like the site.

## Open items

- Nothing yet runs the editor against a live host; the pages are run under node against a stand-in host in the specs.
- A command that acts on another aggregate's instance is offered with a field for its id rather than a picker.
- Entities inside an aggregate, and closed-set (`admits`) attributes as choice lists, are not given their own inputs yet.

## Addendum: the rich-text widget

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR.

- **The widget is chosen by shape.** An attribute gets `widget: "body"` when its value object has a `blocks` list of a value object that has `kind` and `spans`; neither the attribute's nor the value object's name matters.
- **The domain's tree is the only format.** The widget edits the domain's own `blocks` (each with `kind`, `level`, `align`, `indent`, `spans`, `items`, `media_ref`, `alt`, `caption`; spans with `text`, `marks` and `href`; a line break is a span of `"\n"`; a nested list is flat items with a `depth`). It posts that tree as the dotted-path fields every other value object and list uses (`body.blocks.0.spans.1.marks.0.name`), read back by `src/ui/input.ts`. There is no JSON of an editor format and no second encoding. The server renders the current value as hidden inputs, so a browser without the script posts the body unchanged.
- **Plain JavaScript, no DOM in the pure part.** `body_model.js` (`bodyToHtml`, `emptyBody`, `bodyToFields`, `safeHref`) and `body_parse.js` (`htmlToBody`, `htmlToBodyWithNotes`, a small tokenizer and tree with no DOM) run in node and in the browser; `body_widget.js` is the browser part. They are `.js`, not `.ts`, because the package runs under node's type stripping with no build step and a browser cannot load TypeScript; `tsconfig.json` gains `allowJs` so the TypeScript pages can import them. The server serves the three files to a signed-in editor at `<base_path>/assets/<name>`. No npm runtime dependency is added.
- **Escaped always.** Every text, attribute value and address is escaped on its way into markup; an address is kept only when it is a path (not `//`), `http://`, `https://`, `mailto:` or `tel:`, with no whitespace or control characters; marks, kinds and alignments outside the closed sets are not written. The list and detail pages render the body read-only with `bodyToHtml`.
- **Reduced, never silently dropped.** HTML pasted or dropped into the widget is reduced to the nearest block or mark by `htmlToBodyWithNotes`, and the widget shows what it reduced (a heading below level 4, a table, a script, an image with no media key, a link to a disallowed address, inline styles other than weight, italic, underline, strike-through and alignment). The result is normalised: adjacent spans with the same marks and address are merged and empty ones dropped, so a body with such spans reads back merged.
- **Not yet verified:** the widget was driven in Chrome against a static page, not against a live host, and its browser behaviour (execCommand-based marks, prompts for links and images) is not under the specs, which run the pure functions and the server pages under node.

## Addendum: picture upload and picker

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR.

- **The domain holds the record, the editor holds the bytes' route.** A picture's record (key, alt text, mime type, width, height, optionally a focal point) is an aggregate of the domain's chapter, made of plain value objects; the bytes are never in the domain. The editor finds the aggregate by shape in the schema: a creating command whose attributes are the aggregate's identity, an alt text (`alt` or `alt_text`) and a mime type (`mime_type`, `mime` or `content_type`), optionally `width` and `height`, every other attribute optional. No aggregate or command name decides it; the attribute names are the vocabulary, as `blocks`, `kind` and `spans` are for a body. The query with no arguments is the listing (every instance is read when there is none). With no such aggregate the schema has no `media` key, no upload file is generated, and the widget keeps its prompts.
- **Upload.** `POST <base_path>/media` takes `multipart/form-data` (`file`, `alt`) from a signed-in editor on this site. The body is read within the row's `media_max_bytes` plus a fixed allowance for the form's framing (never more is held), the type is decided by the picture's first bytes against JPEG, PNG, WebP, GIF and AVIF (the claimed type and filename are ignored, so an SVG, or an SVG named `.png`, is refused with 415), a blank alt is refused inline before anything is kept, and then the bytes go through the storage port under `<sha256 hex>.<ext>` and the domain's register command records the picture. Width and height are read from the bytes where the format makes that cheap (not AVIF). The same bytes uploaded again return the picture already registered. A refusal by the domain is shown in the domain's words; the bytes of such a refused upload stay in storage (they are content-addressed, so a retry reuses them).
- **Storage port.** `MediaStorage` has `put(key, bytes, mime)`, `url(key)` and `read(key)`; `read` is the one addition to the two methods first sketched, because the editor serves the files. `diskStorage` is generated into the package and writes under `media_dir`; an object-store adapter implements the same interface in the consuming project and is passed as `createApp({ storage })`.
- **Serving.** `GET <base_path>/media/<key>` answers only for a key of the generated form (64 hex digits and an allowed extension), so no path leaves the directory; it sets the type from the key's extension, `X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`. It is behind the same session and membership gate as every other page.
- **Picker.** The widget's image button loads `media_picker.js` only when the editor element carries `data-media`: an upload button (drag and drop onto the panel too), the registered pictures as thumbnails shown from the adapter's own addresses, an alt text field that is required before insert, an optional caption. Inserting adds an image block whose `media_ref` is the key. Everything the server sends is put in the page as text.
- **Not yet verified:** the picker was driven in Chrome against the generated editor served by node with a stand-in host (upload, both refusals, listing with a thumbnail, insert), not against a live host or an object-store adapter. Drag and drop was not exercised in a browser, and AVIF, WebP and JPEG size reading is under no spec beyond the type check.

## Addendum: pictures from another chapter

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR.

- **The problem.** An editor edits one chapter, but a project often keeps bodies in one chapter and pictures in another, so a body's widget had no picker: the chapter holding the bodies has no picture aggregate, and the one holding pictures has no bodies.
- **The smallest design.** The `Editor` row takes an optional `media` field naming another chapter of the same domain directory. The picture aggregate is found there by the same shape rule, and the editor's `/media` upload, listing and picker use it. The row still names one chapter to edit; the picture chapter is not merged into its navigation, so its aggregates are edited by that chapter's own editor.
- **How it is carried.** `schema.ts`'s `media` entry gains `domain` (the picture chapter's name) and `definition` (the picture aggregate, since the editor's own aggregates do not hold it), only when `media` is named. The media handler then reads and registers pictures through a client for that domain (`Library::MediaItem.RegisterPicture`), with the role the command declares. A row without `media` produces the same `media` entry as before.
- **Refused.** `media` naming the editor's own chapter, a chapter the domain directory does not declare, or a chapter with no aggregate that registers pictures.
- **Not done.** Several `Editor` rows in one project (each with its own base path) and merging chapters into one navigation are not offered.

## Addendum: the first run against a real host

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR.

- **Clearing arguments are not fields.** The bluebook clears an optional field with an optional argument the command never reads (`sets :draft_body, to: :nothing`). The projector recognises it by shape (optional, not an attribute of the aggregate, feeding only plain `sets` of fields that can be empty, named by no `given` or `ensures`), leaves it out of the form and the schema's attributes, and sends nothing for it (an empty list when it is a list, named in the command's `empty`).
- **Success is judged by the state that comes back.** The check no longer compares the arguments sent with the state held, since a command may set a field from an argument that is not a field. It holds when the instance changed (for a lifecycle move, to the move's target), or, when nothing changed, when the host's last refusal does not name this verb.
- **Refusals read as what they are.** A `given` that was not met is shown as `Not allowed unless <condition>.`, a value object's invariant as the field and the rule without the offending value, and an aggregate-level invariant as its rule.
- **Forms start from the current text.** A rich-text body the instance has not set yet (a draft not yet saved) starts from the body it holds of the same shape.
- **Link and image forms are in the page.** The widget asks for a link address or an image's key, alt text and caption in a small form attached to the toolbar, not `window.prompt`, which blocks the page. The picker for registered pictures is unchanged.
- **Sign-out.** `POST <base_path>/logout` clears the session cookie and sends the person to the login page; the header has the button. The sign-in token is consumed by a redirect to the base path, so it does not stay in the address bar.
- **The client pin follows the release.** The generated `package.json` depends on `@hecks/client` at `^<the version of this hecks>`; the client and the gem are released at one version, so the pin tracks it.

## Addendum: the editor's look, its shell, and a writing surface from libraries

This follows the decision above and does not depart from its shape (a generated Node package, a generic server, output that is a pure function of the chapter and the row), so it is an addendum and not a new ADR. It supersedes two earlier choices: the hand-written contenteditable widget and the inline stylesheet.

- **Libraries, and why these.** The pages carry Tailwind CSS 4 and daisyUI 5 class names (with `@tailwindcss/typography` for the text), and the writing surface is Tiptap 3 on ProseMirror. All are MIT and exact-pinned in the generated `package.json`. Shoelace was tried first and dropped: its repository was archived with no further releases. daisyUI is CSS only, so the server-rendered HTML needs no custom-element runtime and the stylesheet is one static file; its dialog, drawer, table, tabs, badge, alert and toast are classes on native elements. The build (`npm run build`, run before `npm start`) is Tailwind's CLI for the stylesheet and esbuild for the script; the generated sources are checked by `--check` and nothing built is committed. Every class name the generator writes is a whole string, never joined, because Tailwind finds classes by reading the sources.
- **Theme from the row.** `accent` (a six-digit hex colour, refused otherwise), `brand` and `logo` are optional fields of the `Editor` row. The accent makes two daisyUI themes, light and dark, in `src/browser/app.css`. Primary buttons are ink-filled (daisyUI `neutral`); the accent (`primary`) marks selection, focus, links, the current navigation item and the published state. A text or fill pair that would not reach the contrast standard (4.5:1, 3:1 for the edge of a control) is moved until it does, so no accent can make the editor unreadable; the spec reads the generated stylesheet's own colours and holds every pair, for several accents, in both themes. With no accent the neutrals are fixed; with one they take its hue. The theme button sets `data-theme` and keeps the choice in `localStorage` (blocked storage means the system setting), and a small script in the head applies it before paint.
- **The shell.** A daisyUI drawer (a checkbox is its state, so it opens with no script) holds the navigation with the count each aggregate holds; a header carries breadcrumbs, the person and role (the members list already knew the role), the theme button and sign-out. The counts cost one read of the host per page.
- **Commands.** An instance command that asks for nothing and is safe is a button on the instance's page; one that asks for input has a page, `GET <base_path>/<Aggregate>/id/<id>/<Command>`, whose form is posted to the same address; the refusal re-renders there. A command is destructive when its first word is `withdraw`, `retire`, `discard`, `delete`, `cancel` or `remove`, or when it is a lifecycle move into a state named for one of their past forms. That is read from the bluebook's own words, never a list of aggregates; it is in the schema as `destructive`, and the lifecycle's badge tones are in it as `tones` (the starting state `neutral`, a destructive state `danger`, the others `ok` and `info` in turn). A destructive command asks in a native `<dialog>`; a browser with no script follows the button to a page that asks the same question.
- **Notices.** A success redirects with a one-minute cookie, `<session_cookie>_flash`, holding a kind and a sentence, signed with the shared secret plus a suffix, read once and cleared in the response that shows it; a forged, expired or marked-up cookie shows nothing or shows escaped text. No server-side state. A refusal is shown on the form and as a notice; an invariant that names a command's attribute marks that input (`aria-invalid`, a message linked by `aria-describedby`) and the script focuses it.
- **Writing surface.** Tiptap's lists are replaced by `tiptap-extension-flat-list` (MIT, current, from Common Curriculum), which models a list as top-level items with an `indent`, as the body's list items have a `depth`, so the conversion in `src/browser/body_doc.js` is one item to one item. We extend its two node types only to write the indent as a `data-` attribute: it writes inline `style` attributes, which a strict policy blocks. Alignment is a `data-align` attribute for the same reason, so `extension-text-align` is not used, and the editor is created with `injectCSS: false` (it would add a style element), with ProseMirror's own rules in the stylesheet. The conversion is plain JavaScript with no DOM and is held under node: it round-trips a body that holds every field, keeps marks in the body's own order, drops any address that is not a path, http(s), mailto or tel, and says when a list item that skips a level was moved up. Pasted HTML still goes through the server's reducer, so the notes about what was reduced are the same. A blockquote holds one or more paragraphs and each becomes a quote block.
- **Content security policy.** Every page is sent with `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`. Nothing in the pages or the scripts sets a `style` attribute or adds a style element; the scripts set a few positions through the style object, which the policy allows. The policy is held by a spec, not only by running it.
- **Static files.** The stylesheet, the script and its chunks, the theme script and the logo are served to signed-in editors with an ETag made from their bytes. A page names `name?v=<hash>`; that address is `immutable` for a year, any other is `no-cache` and answered 304 when nothing changed. They are `private`.
- **Picture picker.** A drop zone and a file field, each file with its own required alt text, an upload progress bar and a message of its own when refused, a grid of thumbnails of the registered pictures, and the alt text and caption for the place the picture is used.

Not done, and not verified:

- The built bundle was driven in Chrome against the generated editor served by node with a stand-in host (list, detail, forms with nested and repeated fields, the writing surface with a nested bulleted list, the picker choosing a registered picture, the confirmation dialog, a refusal, a notice, the narrow drawer). The picker's upload with a progress bar and the per-file refusals were not driven in a browser, and neither was drag and drop. No screen reader was used.
- The generated package's `npm audit` reports vulnerabilities in the build tools (`braces` through Tailwind's file watcher, `postcss-selector-parser` through the typography plugin). They are in build-time dependencies, not in what is served, and are reported rather than overridden.
- The generated TypeScript passes `tsc` except for the calls that need `@hecks/client` with `query`, which the pinned release must publish (as for the earlier addendum).

## Addendum: one editor over several chapters, relationships, long lists and dates

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR. It replaces the earlier "not done" note that merging chapters into one navigation is not offered.

- **The smallest design for several chapters.** `chapter` in the one `Editor` row takes a comma-separated list; the first names the domain the host is addressed by and the generated package. Several rows merged by `base_path` were rejected: a row cannot say whether a field was given or defaulted, so the rows could not be merged without guessing. The schema gains `chapters` (when there are several) and, on each aggregate, `chapter` and `roles`; an editor of one open chapter has none of them and reads as before. With several chapters an aggregate is addressed `<base_path>/<Chapter>/<Aggregate>`, the verb and the queries are sent qualified (`Library::Gallery.Compose`, which the client leaves alone), counts and the current page are held by `Chapter.Aggregate`, and a chapter named `assets`, `media`, `logout` or `api` is refused. Two aggregates of one name in different chapters are two; a target is resolved in the same chapter first.
- **Roles.** `chapter_roles` limits a chapter to roles; the navigation and overview cut it out for the others (markers in the page, removed per request), its pages answer 403, and so do the picture routes when the picture aggregate's chapter is limited. The role each command is dispatched as is still the one it declares.
- **Relationships and dates are read from declarations.** The rules are listed in `docs/site-routes.md`. The `<kind>:<slug>` convention is read only from an attribute's `pattern`, because nothing else in the bluebook states it; the server checks every strict key again, whatever the script did.
- **Lists and counts.** Paging, search and the state filter are on the server through the address, over the one read the page already makes; the page's rows are cut after the host answered, so the host still returns everything. The host has no count query, so the navigation's counts are the lengths of that read, and one read now serves a page and its counts. A host that grows a paged or counted query is where a large list would be made cheap.
- **Not verified.** The multi-chapter editor was built (`npm run build`), type-checked with `tsc`, run under node against a fake host in four time zones, and driven in Chrome against a stand-in host: the chapter-grouped navigation, a date round trip, a `<kind>:<slug>` picker, paging and the remembered filter, in the dark theme at a window about 500 pixels wide. It was not driven at 1280 or 375 pixels, in the light theme, or against a real host; a `datalist` suggestion's rendering is the browser's. The 403 on a restricted chapter is held under node, not in a browser.


## Addendum: a record as one thing

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR. Every rule below reads declarations (a key's `pattern`, a closed set, a moment, a lifecycle, `draft_` attributes), never an aggregate or a command by a project's own name, and each is absent when its shape is. `docs/site-routes.md` lists them for a reader; the reasons are here.

- **Related records.** `B` is related to `A` when `B`'s identity attribute is a `<kind>:<slug>` key (see `KeyKinds`) whose kinds resolve, by the picker rule, to `A`. Reusing the picker's resolution means one rule decides what a key names. The `<Kind>Key` / `SubjectKey` / `DocumentKey` part names the brief floated were not used: only a pattern states the convention, as in the earlier addendum. A panel is a document (the aggregate has a rich-text body), a gallery (a list that names the picture aggregate) or metadata (anything else), checked in that order. The editing command is the draft-saving command of a document that keeps drafts, else the first command on an existing record that is neither a lifecycle move nor destructive and takes the body or pictures (any arguments for metadata). An empty state links to the creating command's own page with the key filled in the query string, rather than embedding the form: the form is long (a body editor) and its page already refuses and re-renders correctly.
- **The way back.** A page reached from a record carries `_back` in its query and posts `__back`; only an address under `base_path` is followed, so a link written by anyone cannot send a person away, and a success redirects there with the usual notice (a refusal re-renders with the way back kept).
- **Scheduling.** An aggregate is scheduling-shaped by a key-pattern subject, a closed-set action, a due time that is a moment, a lifecycle whose first state moves to at least two states that move nowhere, and a creating command that takes the three. A due time that is an integer not named like a moment (`due`, not `due_at`) is not found: the moment rule reads names, and this reuses it. The editor makes the record's identity (a UUID) when the identity is not the subject, since nobody should type it. The panel and screen only call the aggregate's own commands; the help text says a runner elsewhere runs the actions. A closed set (`one_of`) is now a select wherever it appears, and the server checks the posted value is a member before sending the command.
- **Preview.** `preview` is a template, refused unless an http(s) address or a one-slash path, without credentials, whitespace, unknown placeholders or a placeholder in the origin, because the origin is written once into `frame-src` and the policy gets nothing else. The frame is `sandbox="allow-scripts allow-same-origin"`: the site's scripts must run, and without `allow-same-origin` it would have an opaque origin, with no storage, cookies or requests to itself. On another origin that flag gives the page no way to reach the editor; on the editor's own origin (a path template) it removes the sandbox, which is why an absolute address is the documented choice there. Every record has a Preview except those of the picture and scheduling aggregates, which are not pages of the site. Nothing is sent into the frame; the drawer reloads it after a draft is saved and is open again after a form is sent.
- **Drafts.** The draft-saving command is found by `draft_<x>` arguments that are counterparts of held attributes of one type, with a body among them; publishing and discarding are found by the mutations that read the draft (`state(:draft_<x>)`) and by an argument that only clears it. An autosave is a form post with a header that makes the server answer in plain text, and the server runs it only for the draft-saving command, so the live attribute is never written from it.
- **Activity.** Not built. A read answers `events: []` (`rust/host/src/dispatch.rs`, `read`: a read reports current state, never event or refusal history), a command's answer carries only the events of that run, the journal's steps are not exposed on `/dispatch`, and the `/api/*` routes answer records. A per-instance history needs a host read that returns a record's events, with when and by whom; the editor would then list them.
- **Not verified.** Run in Chrome against a stand-in host at a 1280 pixel window in the dark and light themes: the related panels and their return, scheduling and cancelling, the preview drawer at three widths (including reload after a save), and autosave through typing, blur, a refused save and its retry, then publishing. Not driven at 375 pixels (the browser tool did not change the viewport), against a real host, or with a screen reader; the native date-and-time control was set by script, not by hand.


## Addendum: a list of mixed blocks

This follows the decision above and does not depart from it, so it is an addendum and not a new ADR. A page that is a free sequence of different things (a picture band, then two paragraphs, a row of cards, a gallery) is, in a bluebook, one value object with a `kind` held in a `list_of`. The editor could edit it only as identical rows. It now edits it as ordered cards, and every rule below reads declarations, never a name.

- **Detection (bluebook).** A `list_of` value object that has a discriminator is a block list. The discriminator is a part whose type is a closed set (`one_of`) of one plain value, or a text part that an invariant restricts to a literal list (`["a", "b"].include?(kind)`), so a model that spells its kinds either way works with no declaration. A value object that holds `spans` is a body's block and is never a block list. The kinds, the limits (`<list>.size <= <n>` in an invariant or a command's `given`) and the parts that make a picture (`media_ref` with `alt`, the vocabulary a body's image block already uses) are read from the model.
- **Which slots each kind uses (bluebook, a declared table).** The smallest declaration that is readable and not an expression is a closed set of rows with the parts `kind`, `requires` and `uses`, held in the same aggregate: one row per kind, the slots it must have and the slots it may have, by name. A slot no row names (a variant, a background) belongs to every kind; naming `media_ref` brings its `alt`. It lives in the bluebook and not in the hecksagon or the `Editor` row because it says what the domain's kinds are, which a renderer reads as well as an editor; the hecksagon is wiring and the `Editor` row is the site's, and neither knows the model's kinds. The table is found by shape (its parts and its kinds), the same way a body is, and holds nothing at runtime: the invariants still decide, and a refusal is always the domain's. The cost is that the table and the invariants can drift; the editor shows the domain's refusal either way. With no table every slot is shown and the invariants of the form `kind != "<k>" || ...` only mark which slots a kind's rules read.
- **The surface (generator).** `src/ui/blocks.ts` draws the cards on the server, `src/ui/block_list.js` holds the rules that need no page (shared by the server and the script), and `src/browser/blocks.js` adds adding, removing and moving. The list is plain markup that posts the same dotted-path fields every value object does, so a browser with no script still edits the blocks it has; only adding, moving and removing need the script. A new card is made from a `<template>` the page carries for its kind, written by the same function that draws an existing card. Cards are collapsed by script; a rich-text body inside a card (or inside an entry of a card) gets its writing surface when its card is first opened, so a page of forty cards holds a handful of editors. The kind of a card is fixed once it is made.
- **Reordering and removal.** Move up and move down are buttons with the card's number, kind and summary in their names, and the result is announced in a polite live region (`Moved panel 3, Hero: Welcome to position 2 of 39.`). A button at an end stays focusable and says so when pressed. Focus stays on the button that was pressed after a move, and after a removal goes to the next card, else the previous one, else the add control. Removing asks first, in a native dialog whose default is to keep it. There is no drag handle.
- **Pictures.** A picture's key, alt text and caption are drawn together with the existing picker (`Choose a picture`); the key may still be typed, since it may be an address. A key with no alt text is marked on leaving the alt field, and an autosave waits.
- **The working copy.** A draft is found when the draft attribute and the live one are lists of one value object that is a block list (before, only a body). Its starting values are the live list when no draft is saved (an empty list counts as none). The autosave posts the whole list through the draft-saving command and holds back, saying which card and why, while a card lacks what its kind requires; Save draft is never held back, so a stale table cannot stop a save. The draft is saved by one editor at a time: the last save wins, and nothing here compares versions.
- **Refusals.** A refused invariant names the value object and the rule, and echoes the value it was given. The editor matches the echo to the submitted block (null and absent slots count as equal), else the blocks whose kind the rule's words name, and marks that card: opened, `Needs attention`, the slots the kind requires that are empty (else the slots the rule names) `aria-invalid` and described by the rule's wording, a summary at the top that links to each card, and the first marked control focused. An autosave that is refused answers with the same blocks in a header, and the script opens them. A refusal that matches no block is shown as a whole, as before.
- **Found by running a real host.** A host answers a refused command with the state it holds, which may echo an unset optional slot as `null` and in another key order than a read. The editor decided a command had applied when the state it came back with differed from the state before it, so a refused save of a list was shown as saved. The comparison now leaves nulls out and sorts keys.
- **Not verified.** The block list was driven in Chrome against a real host (Postgres, the Rust host) with a 39-block page: add, move by keyboard, remove with the dialog, a refusal, autosave, publish; at a window about 1300 pixels wide in both themes, and at 375 pixels in a frame served through a scratch proxy (the browser tool could not narrow its window). Not driven: dragging (there is none), a touch device, a screen reader, and the picker's upload inside a card. The `Choose a picture` button was not pressed in the real browser, and no uploaded picture was shown as a thumbnail.

## Addendum: pages of a fixed structure

This follows the decision above and does not depart from it, so it is an addendum. A page whose structure is fixed by the model (named slots: a heading, rich writing, a picture with its description, repeated groups that hold groups of their own) is, in a bluebook, one aggregate whose `content` is a value object. The editor drew it, but could not work on it as a page. Four gaps closed, each by reading a declaration; nothing names a package, a page or a client.

- **The working copy of a value object (bluebook, read by the generator).** A draft is recognised when the aggregate holds a live attribute and a `draft_`-prefixed twin of one type and a command whose every argument is the twin, and the attribute is a rich-text body, a block list, or any value object, alone or in a list (before, only the first two). The save, publish and discard commands are found by shape as before, the clearing argument (`nothing`) is left out of the form and sent as an empty list only when it is a list. The form starts from the live content when no draft is saved. The page's own screen shows `Changes not published yet`. The form of a value object is saved as a whole (`data-draft-form`): any input, list move, picture choice or writing surface marks it changed, and the autosave holds back, naming the card, while a member lacks a slot its value object requires.
- **A picture slot (bluebook shape, generator).** A value object with a media key and an `alt` (the vocabulary a body's image block and a block list already use) is a picture wherever it sits, at any depth and as a member of a group. It is drawn as one group with the existing picker; `alt` is required, and a form is not sent, and the autosave waits, while a picture names its file and has no description, with the error beside the field and the card that holds it opened. The domain's own refusal is the same rule, so a request that does not come from this page is refused in the domain's words.
- **A long text (bluebook: an invariant; generator: a writing box).** The smallest declaration that needs no change to the language is the rule a model already writes to bound a text, `summary.to_s.size <= 600` (or `size`, `length`, optionally after `summary.unset? ||`), held in the value object or aggregate that has the part, or in a command's `given`. Both runtimes enforce it and the editor reads it: the part carries `maxLength`, and above 200 characters `multiline`, which is a `textarea` with the limit as `maxlength` and a line that says it. A text with no bound stays one line. No attribute option was added (`max_length`, `multiline`) because it would change the Ruby DSL, the Rust parser, the IR and both runtimes for what an invariant already says and enforces; the threshold is the generator's, written once in `Limits::MULTILINE_FROM`. The forms surface's name-based `textarea` hint (`description`, `body`, `note`) is not used: it guesses from a name, and would turn existing editors' one-line fields into boxes.
- **Repeated groups (bluebook limits, generator cards).** A list whose members hold a rich-text body or a picture at any depth, a list of their own among them, is drawn with the block list's cards and templates (a member cannot be copied as plain inputs once a script has made a writing surface in it); any other list stays rows. A list in a member is a group of cards one level in (two levels in all). Required is what the value object declares, shown on each member's slots (a required part of an optional group is not marked, since the group may be left out); an optional group with nothing in it is left out of the arguments and one with something in it is sent whole, a required part sent empty so the domain's rule words the refusal; a member left entirely blank is dropped. The limits are the holder's own invariants (`chapters.size >= 1`, `parts.size <= 12`) or a command's `given`: shown beside the list, carried as `data-max`, and the add control says so when it is reached. Rows (flat lists) show and enforce the same maximum.
- **Refusals.** A refusal names a value object and the rule and may echo the value. The editor finds, at any depth of the submitted arguments, the value object of that type whose value the echo equals, else the only one of its type; it marks the card (`Needs attention`, opened with the cards that hold it, a summary that links to each), the slots it lacks that its value object requires (else the slots the rule names) `aria-invalid` and described by the rule's words, and focuses the first. The mark is no longer put on the whole working copy as well. An autosave that is refused answers with the same value objects in a header, by their field names.
- **Verified.** Run under node against a stand-in host (the pure halves over tables), and driven in Chrome against a real host (Postgres, the Rust host, built from this tree's `hecks-build`) with a 13-chapter page of nested parts: save a draft (autosave, a reload shows the live content as the start), a refusal mapped to the part of a chapter, a picture chosen outside a list and a missing description marked, keyboard move with the result announced, publish, and discard of a draft that is a list; at 375 pixels in a frame served through a scratch proxy. Not driven: dragging (there is none), a screen reader, a picture upload inside a card, a touch device.
- **Open.** A stale refusal summary stays until the page is reloaded after an autosave fixes it. The picker keeps the alt text of the picture it replaces until it is edited. Card headings start at level 3 under the page's level 1, a skip the block list already had. A list in a list in a list is drawn as rows.
