# Eras become a loadable persistence plugin, not code core always carries

**Status:** Accepted — implemented. New: `lib/hecks/ports/persistence/plugin.rb` (the registry), `lib/hecks/ports/persistence/plugins/era.rb` (the entry point). Moved: `lib/hecks/translation.rb`+`translation/**`, `lib/hecks/adapters/driven/postgres_era.rb`+its subtree, `lib/hecks/runtime/era_check.rb`/`era_guard.rb`+`era_guard/shape_diff.rb`/`era_tamper.rb`/`storage_shape.rb`, `lib/hecks/ports/persistence/lineage.rb` — all into `lib/hecks/ports/persistence/plugins/era/`, namespaces unchanged (`Hecks::Runtime::EraCheck` etc. stay exactly what they were; only their file location moved). Changed: `lib/hecks.rb`, `lib/hecks/adapters/driven.rb`, `lib/hecks/runtime.rb` (drop the era requires), `lib/hecks/runtime/loader.rb` (generic plugin-contribution loop, structural compute-rule backstop), `lib/hecks/projector/exporter.rb`, `lib/hecks/projections/shape.rb` (guard on `Ports::Persistence.plugin?(:era)`), `bin/project_rust`/`bin/project_tenant`/`bin/scaffold_translation`/`bin/translation_audit`/`bin/shape` (require the plugin directly), plus every spec that boots a domain genuinely bound to `PostgresEra`. One correction found during implementation, below.

## Context

ADR [0031](0031-eras-become-a-registered-boot-gate-not-a-hardcoded-loader-step.md) made era-checking *behaviorally* optional — a domain with nothing lineage-capable never runs it. It did not make the code optional: `~4,326 LOC` of era/lineage-specific Ruby (`lib/hecks/translation/**` — 742 LOC; `lib/hecks/adapters/driven/postgres_era.rb` + its subtree — 2,915 LOC; `lib/hecks/runtime/era_check.rb`/`era_guard.rb`+`era_guard/shape_diff.rb`/`era_tamper.rb`/`storage_shape.rb` — 957 LOC) is still `require`d unconditionally by core, every time, for every app, whether or not it ever binds `PostgresEra`.

Six real edges make that unconditional load-bearing today, not incidental:

- `lib/hecks/adapters/driven.rb:14` — `require_relative "driven/postgres_era"`, unconditional, alongside every other adapter.
- `lib/hecks/runtime.rb:53-56` — unconditionally requires `era_guard`, `storage_shape`, `era_tamper`, `era_check` as part of `Runtime`'s own load sequence, before `runtime/loader`.
- `lib/hecks/runtime/loader.rb`'s `run_boot_gates!` — calls `EraCheck.check_compute_rules_for_registry!` unconditionally every boot (by design: a `compute`/`rekey` translation rule requires Postgres whatever adapter is actually bound, so ADR 0031 deliberately left this outside `BootGates`'s capability gate), and hardcodes `EraCheck.method(:check_lineage!)` by name when registering the conditional `:era_check` gate.
- `lib/hecks/projector/exporter.rb` (core — used to export IR for every domain) unconditionally requires and calls `Runtime::EraCheck`/`Translation::RuleCompiler`.
- `lib/hecks/projections/shape.rb` (a registered core `Projector::Target`, backs `bin/shape`) unconditionally calls `Runtime::StorageShape.project`.
- `lib/hecks/ports/persistence.rb:12` unconditionally requires `persistence/lineage.rb`, whose only two real consumers (verified by grep) are `era_check.rb` and `translation/audit/layer_two.rb` — both era-specific, despite the file's core-looking location.

The DSL-builder shadow-parsing forks (`Bluebook::MetaValidator.shadow_parsing?`, consulted in `value_object_builder.rb`, `attribute_collector.rb`, `identity_declaration.rb`) are **not** part of this — investigated fresh for this ADR and confirmed already as tight as they can get: one shared boolean flag, three genuinely different grammar-default forks, no duplicated logic. `EraGuard`/`EraTamper` stay exactly where ADR 0032 put them (`Runtime::`, called *by* the adapter, not the reverse).

Packaging today is a single gem (`hecks.gemspec` globs all of `lib/**/*`); `adapters/driven.rb`'s eager-require-everything model applies to all 16 adapters, not just this one. The stated goal here is narrower than a separate gem: a plugin *module*, loadable into the persistence layer, that core never mentions by name — explicitly because eras/lineage might someday be something provided outside Hecks entirely rather than a part of it, and a defined plugin contract is what would let an external package satisfy that contract later with zero changes to Hecks core. A separate gem (own repo or same-repo multi-gem) was considered and rejected for now: real packaging weight (a second gemspec/version to release) for a boundary a plain plugin registry already gets, with no second real consumer yet to prove the abstraction against.

## Decision

**A small, real plugin registry lives under `Ports::Persistence`** (`lib/hecks/ports/persistence/plugin.rb`): `Ports::Persistence.register_plugin(name, plugin)` and `Ports::Persistence.plugin?(name)` / `.each_plugin`. A plugin is anything responding to `contribute_boot_gates(registry, gates)` (may be a no-op). Registration is a side effect of requiring the plugin's own file — the same shape an adapter's own `.rb` file already uses to make itself known (`Registry#add_adapter`) — **not** a manifest core maintains. Core never contains the string `"era"` as a plugin name anywhere; an app (or a future external package) that wants era/lineage support does exactly what every adapter-specific spec fixture already does for a single adapter file: `require` it.

**The era/lineage code moves to `lib/hecks/ports/persistence/plugins/era/`**, structured as:
- `plugins/era.rb` — the single entry point an app requires; requires everything below and calls `Ports::Persistence.register_plugin(:era, Era)` at load time.
- `plugins/era/` — `translation/` (renamed from `lib/hecks/translation/`, unchanged internally), `postgres_era.rb` + subtree (moved from `lib/hecks/adapters/driven/`), `era_check.rb`, `era_guard.rb` + `era_guard/shape_diff.rb`, `era_tamper.rb`, `storage_shape.rb`, and `lineage.rb` (moved from `lib/hecks/ports/persistence/lineage.rb` — confirmed era-only by consumer).
- `Era.contribute_boot_gates(registry, gates)` — registers `:era_check` (phase `:pre_verify`) exactly when `EraCheck.lineage_capable_registry?(registry)`, using `EraCheck.method(:check_lineage!)` as the gate, precisely what `Loader.run_boot_gates!` did inline before.

**`Loader.run_boot_gates!` no longer hardcodes `EraCheck` at all.** It calls `Ports::Persistence.each_plugin { |plugin| plugin.contribute_boot_gates(registry, gates) }` before running the `:pre_verify` phase — generic, so any future persistence plugin gets the identical seam for free, with zero changes to `Loader`. `:saga_rehydration` is unaffected — it was already proven core-not-era-specific by ADR 0031's own two-gate design and keeps being registered directly by `Loader`.

**`check_compute_rules_for_registry!` stays hardcoded and unconditional in `Loader`, but shrinks to structural-only.** Today's version (era-owned, understands what "requires Postgres" means) moves into the plugin as the *real* check, run by `Era.contribute_boot_gates` alongside `:era_check`'s registration — a domain with the plugin loaded gets the exact same rich, adapter-aware refusal it does today. Core keeps one small, plugin-agnostic backstop: does this bluebook's IR declare a `compute`/`rekey` rule at all (structural — core already parses the DSL and knows this) with **no plugin registered that provides it**? Refuse, naming which plugin to `require`. A domain using `compute`/`rekey` with the era plugin loaded never sees this path; a domain that forgot to require the plugin at all gets a clear refusal instead of whatever way calling into an unloaded translation subsystem would fail.

**`Exporter.lineage`/`.compiled_translation_aggregate`, and `projections/shape.rb`, guard their era-specific calls on `Ports::Persistence.plugin?(:era)`** instead of calling unconditionally — unloaded plugin behaves exactly as "nothing lineage-capable" does today (`capable_aggregates: []`, translation export skipped, `bin/shape` refusing the same way an era-free domain already would).

**`bin/project_rust` keeps requiring the era plugin directly, unconditionally** — a dev/build CLI that has to handle whatever domain it's pointed at is a legitimate, explicit consumer, not a core-boundary violation; this is exactly "load the plugin where you need it."

**No separate gem, no `Gemfile` change.** The plugin ships inside the same `hecks` gem (still one `hecks.gemspec` glob), reachable at `hecks/ports/persistence/plugins/era`. Splitting it into an actual second gem — same repo or not — is explicitly deferred; nothing here forecloses it (the require boundary and the plugin contract are the same shape a separate gem's own entry file would need anyway).

## Consequences

- **One correction found during implementation, not anticipated in the Decision above**: `PostgresEra`'s `.adapter` DSL declaration (`Hecks.adapter "PostgresEra" do port "persistence"; field :database; ...; end`) could NOT move into the plugin directory alongside the `.rb` implementation. `Adapters::Folder#load_library` discovers every adapter by globbing a fixed directory tree (`lib/hecks/adapters/*/*.adapter`) on every single boot, unconditionally — a require-path-based plugin boundary doesn't reach a directory-glob-based discovery mechanism. The `.adapter` file stays at `lib/hecks/adapters/driven/postgres_era.adapter`, in core, on every boot, for every domain — but it is pure metadata (which port, which fields), no era-specific code, and inert for a domain that never binds to it (`registry.adapter_class("PostgresEra")` is only ever resolved for a domain that actually does, at which point the plugin must already be loaded for the class to exist). Only the Ruby *implementation* is genuinely gone for an app that doesn't need it.
- An app that never binds `PostgresEra` loads zero era/lineage code — not "loaded but inert," genuinely absent from the process, no `Translation`/`EraCheck`/`EraGuard`/`PostgresEra` constants defined at all.
- Core (`Loader`, `Exporter`, `projections/shape.rb`, `ports/persistence.rb`) never names `EraCheck`/`PostgresEra`/`Translation` again — every reference is through the generic plugin contract (`register_plugin`/`plugin?`/`each_plugin`/`contribute_boot_gates`) or, for the compute-rule backstop, plain IR structure.
- This is the seam a future external, company-provided era/lineage package would need to satisfy to work with an unmodified Hecks core: `require` its own entry file, call `Ports::Persistence.register_plugin(:era, SomePlugin)`, implement `contribute_boot_gates`. Nothing else in core changes to support that.
- `bin/project_rust`'s explicit, unconditional require of the era plugin means the Rust codegen path is not itself plugin-gated — every domain's `ir.json` still gets full lineage export capability at build time regardless of whether that specific domain uses it. This is a deliberate, narrow exception (named above), not a gap.
- The compute-rule backstop in core is intentionally less specific than what shipped before (it can say "requires a persistence plugin, none is loaded" but not "requires Postgres specifically," since core no longer knows what any given plugin actually needs) — a real, small wording regression, accepted because the alternative (core knowing "Postgres" by name) is exactly the coupling being removed.
- Existing deployed domains (Banking, Pizzas, Embryonaut, and a client site) all bind at least one aggregate to `PostgresEra` and so must add exactly one line to their own bootstrap (`require "hecks/ports/persistence/plugins/era"`, alongside their existing `Kernel.load` of the `.adapter` file) — a one-time, ordinary-redeploy change, not a coordinated migration.

## Rejected alternatives

- **A separate gem** (own repo, or same-repo multi-gem). Rejected for now — real packaging weight (a second gemspec, a second version to release, a `Gemfile`/`gemspec` dependency edge to maintain) for a boundary the plugin registry already achieves. The registry is the harder, real design work; a gemspec around it later is comparatively mechanical, so nothing here forecloses it.
- **A plain require-boundary with no registry** (core just stops requiring era files; an app requires them itself; no `register_plugin`/`contribute_boot_gates` contract). Rejected — cheaper and more YAGNI-consistent on its own, but it defines no seam a future external package could implement against, which is the actual reason this extraction was requested (eras potentially becoming something the company provides outside Hecks, not a hypothetical).
- **Building a new non-lineage `Member`/auth persistence path** so a lineage-free domain could still use Google auth. Considered and rejected as part of this same design pass (see [0034](0034-rust-lineage-becomes-optional-in-the-lambda-host.md) for the Rust-side version of this same call) — no domain today needs it, and `auth.rs`'s existing coupling to the lineage head-snapshot mechanism looks like a real architectural reason (indexed point-lookup-by-id), not an accident worth working around for a hypothetical.
- **Keeping `check_compute_rules_for_registry!` entirely inside the plugin, with no core backstop at all.** Rejected — a domain that declares `compute`/`rekey` but forgot to require the era plugin would fail some other, less legible way (an undefined-constant error deep in dispatch, or silently do nothing useful) instead of a clear boot-time refusal naming the fix.
