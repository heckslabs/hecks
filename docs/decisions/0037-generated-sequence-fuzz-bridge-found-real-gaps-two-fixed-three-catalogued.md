# The generated-sequence Rust conformance bridge (PRD 04) — what it found, what shipped, what's catalogued

**Status:** Bridge built and working (`spec/rust_conformance_fuzz_spec.rb`). Two real bugs fixed this round (wording + a stale-codegen catch-up, both verified). Three further real, confirmed gaps catalogued below, not fixed this round — the bridge's own examples are `pending:`, citing this document, until they're closed. This is real, budgeted findings-work, not a stalled feature: see "Why pending, not filtered, not fixed," below, for why this is the honest state to leave it in.

## Context

`spec/rust_conformance_spec.rb` only ever proved Ruby/Rust agreement over a fixed, hand-authored corpus. Phase 6 of the equivalence-gap plan built the bridge PRD 04 asked for: generate real `SequenceGenerator` sequences, run each through `Replay.call` and the compiled Rust binary, diff the same way the fixed-corpus spec already does (shared logic factored into `spec/support/rust_conformance_helpers.rb`).

It worked immediately — the very first real run (pizzas, banking; 10 seeds each; 25 steps/sequence) found real divergences, exactly as the plan predicted ("it would have caught most of today's nine bugs automatically"). A wider, un-gated direct sweep (60 seeds/domain, no `rspec` overhead) surfaced the same handful of distinct root causes repeatedly, at high frequency — this is not noise, it's real, confirmed structural drift. Six findings total: two fixed and verified this round, three real-and-confirmed-but-not-fixed (one of them, Finding 5, a genuine data-integrity gap — more serious than the other two put together, even though it fires far less often), and one not yet fully diagnosed.

## Finding 1 — FIXED: String-scalar composite-shape mismatch had the wrong wording

`rust/project/json_codec.rb#scalar_type_error`'s own comment used to say plainly: "a `String` scalar mismatch keeps `json_type_error`'s own generic wording, since nothing in this corpus exercises Ruby's own wording for THAT shape." The fuzzer found the counterexample the same day: `Pizzas::Order.AddTopping` with an Array offered for `ToppingName.value` (String-typed). Ruby's real wording (`Value::Coercion#check_scalar_shapes`, the "numeric_field" template, fired for a String/Boolean field ONLY when the offered value is Array/Hash-shaped — Integer/Bool standing in for a String is deliberately tolerated) is `"ToppingName.value expects String, got [3,8]"`; Rust's was the generic `"ToppingName.value: expected String"`.

Fixed at the source, both generators (`rust/project/json_codec.rb` and `rust/codegen/src/json_codec.rs`), scoped exactly to the composite-shape case (checked at runtime — codegen can't know the offered value's actual JSON shape ahead of time) so the deliberately-tolerated non-composite case is untouched. Verified: `spec/rust_conformance_spec.rb` (fixed corpus, still 100% green) and `spec/codegen_parity_spec.rb` (both generators still byte-identical) both pass; the exact repro case now matches Ruby byte-for-byte.

## Finding 2 — FIXED (as a side effect): `examples/pizzas`'s generated Rust was stale

Regenerating pizzas to apply Finding 1's fix also picked up a real, unrelated drift: `Pizzas::Order.Purchase` gained a `given("the payment covers the price")` in the Ruby source at some point after the checked-in `rust/src/generated/pizzas/` was last regenerated, and nobody had regenerated since — the compiled binary was missing that given entirely. This is exactly the shape Phase 8/9 exist to prevent going forward (parity checked only against a fixed test corpus, decoupled from what's actually compiled and shipped). `governance`/`meta` (pizzas' own framework dependencies) were regenerated alongside it, byte-verified clean (no unrelated content changes beyond catching up to current source).

**`examples/roster` was checked the same way and found to ALSO be stale** (confirmed: regenerating it changes 194 lines of `ir.json` plus `metadata.rs`, unrelated to anything this round touched) — NOT regenerated or committed this round; a domain-by-domain audit of which generated trees are stale, and why, is real, separate, and not small enough to fold into this phase's own scope. `examples/banking` has its own PRE-EXISTING, already-known regeneration blocker (missing `CorrectFee` dispatch from the `corrects` construct — noted in earlier session work, unrelated to Findings 1-2) that a full regen would surface but this round deliberately did not attempt to fix.

## Finding 3 — CATALOGUED, not fixed: missing-required-argument wording is generic, not Ruby's rich template

**By far the highest-frequency divergence** — present in nearly every generated sequence of any real length, across both domains tested. Ruby's real wording (`ArgumentGate#refuse_absent_arguments`, `AbsentArgument`/`absent_args` template): `"{command} was not given {absent} — it takes {declared}"` — e.g. `"Grant was not given starts_at — it takes from_role, to_role, starts_at"`. Rust's actual wording, confirmed live: `"GrantArgs.starts_at: missing from JSON args"` — `Json::require`'s own generic kernel-level fallback (`rust/src/kernel/json.rs:244-247`), used for EVERY missing key anywhere (both a command's own top-level argument and a nested value-object field, which have no equivalent Ruby-side "was not given" wording at all — only command-level arguments do).

**Why this isn't a quick fix**: `Json::require` is shared, generic kernel code — it cannot special-case "am I a top-level command argument" (it has no idea; a value object's own nested scalar field calls the identical function). The real fix belongs at CODEGEN time, per command, in `rust/project/commands.rb`'s (and `rust/codegen/src/*.rs`'s) `from_json` generation: emit an UPFRONT check of every required key's presence — matching Ruby's own batch behavior exactly (`required - given`, SORTED, possibly naming MULTIPLE absent keys in one message — Rust's current per-field `v.require()` calls only ever report the FIRST missing field, a structural difference, not just a wording one) — before constructing any field, with the SAME `exempt` identity-attribute carve-out `refuse_absent_arguments` gives an aggregate's own self-addressing attribute, and the SAME "declares none" empty-list wording (`declared_reading`'s own comment: "Freeze does not declare standing — it takes " read as broken, not empty, before that fix landed"). A real, scoped, but genuinely NEW codegen feature — not attempted this round.

## Finding 4 — CATALOGUED, not fixed: query arguments skip typed construction and invariant checks entirely

Confirmed live: `Pizzas::Order.CostingLessThan` with `ceiling: {cents: -1}` (a `Price`-typed query argument; `Price` declares `invariant("a price is never negative")`). Ruby refuses — `"Price invariant violated — a price is never negative (given {\"cents\":-1})"` — because a QUERY argument goes through the exact same typed `Value.build` pipeline a command argument does. Rust succeeds silently (`rows: []`, no refusal at all).

Root cause, confirmed by reading the generated code: a query condition against an `Arg`-typed value (`crate::kernel::QueryConditionValue::Arg("ceiling")`, `registry.rs`) is resolved directly out of the raw JSON args at query-dispatch time (`kernel/named_query.rs`) — never through a typed `Price::from_json()` construction, so `check_invariants()` (and, separately, a genuine type mismatch — confirmed live too: `Pizzas::Order.CostingLessThan` with `ceiling: [10, 2]` also silently doesn't refuse where Ruby does) never runs at all for a query argument. Commands ALREADY call `.check_invariants()?` on every typed argument (`dispatch_rent`'s own generated code: `args.customer.check_invariants()?;`) — queries never gained the equivalent. This is architecturally the deepest of the four findings: closing it means `kernel::named_query`'s `Arg` resolution needs to route through the same typed-construction-plus-invariant-check path commands already have, which is real, separate design work, not attempted this round.

## Finding 5 — CATALOGUED, not fixed: a real, live data-integrity gap — `resolve_state_references` was never ported to Rust

**The most serious finding of the four, in consequence if not in frequency.** Confirmed live: `Banking::SafeDepositBox.Rent` with `customer: {value: "nonexistent-customer"}` (no such Customer exists). Ruby refuses — `Hecks::Runtime::NotFound: no Customer with reference "nonexistent-customer"`. Rust succeeds, mints the box, and stores `"customer": "nonexistent-customer"` as a genuinely dangling reference — a real, silent data-integrity violation, not a wording mismatch.

Root cause, traced fully: `SafeDepositBox` declares `belongs_to Customer` at the AGGREGATE level (minting a `Reference<Customer>`-typed `customer` field on the aggregate itself), but `Rent` — the command that sets it — separately REDECLARES `attribute :customer, CustomerNumber` on ITSELF (a plain value-object type, not `Reference`), because the caller needs to pass the wrapped `{"value": "..."}` shape, not a bare reference id. This means Ruby's COMMAND-argument-level reference check (`CommandRules::References#resolve_references`, the one `rust/project/domain_generator.rb`'s own `reference_checks` already ports) never fires either — `Rent`'s own attribute isn't `reference?`-true. What actually catches it in Ruby is a SEPARATE, later check: `resolve_state_references`, called at `step_save` (`command_interpreter.rb:258`, BEFORE the actual persistence write), which walks the AGGREGATE's OWN attributes (correctly `Reference<Customer>`-typed) against the SETTLED state after `sets :customer` copies the argument in — catching exactly the case the command-level check structurally cannot. `references.rb`'s own header names why this second check exists at all: "`reference_to Customer` ... was declared 14 times across banking and enforced nowhere" — a real bug Ruby itself once had and fixed; Rust's codegen was written to the OLDER, command-argument-only shape and never gained the equivalent.

**Confirmed narrow blast radius** (dedicated investigation, not assumed): `SafeDepositBox.Rent` is the ONLY real corpus command, across all five example domains (banking, pizzas, roster, compliance, chess) and every entity within them, that redeclares an aggregate-/entity-level reference's own minted field name with a different, non-Reference type. Every OTHER `reference_to`/`belongs_to` relationship in the corpus (dozens, `Account.Open`'s `reference_to Customer` among them — checked directly, refuses identically on both engines) is either declared directly on the acting/creating command (so `resolve_references`'s existing command-level check already catches it, on BOTH sides) or inherited from the aggregate with no local redeclaration at all (same coverage). This is real and needs closing, but it is not the pervasive, "any of the 14 declared references could silently corrupt" risk it might first appear to be.

**Why not fixed this round**: closing it properly means porting `resolve_state_references` itself — a genuinely new codegen feature (walk the AGGREGATE's, not the command's, own attributes; the existing `reference_checks` helper is reusable since it already operates on anything with `[:attributes]`, aggregate or command; needs wiring into the generated dispatch function's pre-save step, matching Ruby's exact ordering) into BOTH generators, plus (per Ruby's own `resolve_state_references` recursing into `construct.entities`) deciding whether entity-level recursion is needed now or can be deferred — the real corpus has zero entity-level `reference_to`/`belongs_to` declarations today (confirmed the same investigation), so an aggregate-only port would already close every real, currently-reachable case, with entity recursion staying a documented, deliberately deferred extension for whenever the corpus gains one.

## Finding 6 — NOT YET DIAGNOSED: Bignum-adjacent refusal divergences

The wider un-gated sweep (using PRD 05's own widened `INTEGER_EDGE_CASES`, including `2**100`) surfaced several refusal mismatches involving a Bignum-magnitude value (`Pizzas::Order.CreatePizza`'s `Price.cents` given a value around `±1.27e30`) where Ruby and Rust disagreed on WHETHER to refuse, not just how to word it — but a full trace of WHY (which of several possible causes: Ruby's `Price` invariant catching it via a different path than the plain numeric-field check; JSON round-trip of a value this large losing precision differently on each side; something else) was not completed this round — flagged honestly as unfinished investigation, not swept under Finding 3 or 4's own explanations even though it may turn out to be one of them.

## Why `pending:`, not a filter, not a fix

Every other "known gap" this whole plan has catalogued (`known_reaction_gap?`, `KNOWN_REFUSAL_GAP_VERBS`, `structural_refusal_gap?`) is a NARROW, per-entry filter — strip exactly the one divergent record a cited, understood boundary explains, keep comparing everything else. Findings 3 and 4 don't fit that shape: Finding 3 fires on a large fraction of every generated sequence of any real length (any command with more than one required argument, hit with any malformed/incomplete args — which `ValueGenerator`'s own `INVALID_MEMBER_PROBABILITY`/edge-case tables produce constantly), and once it fires it can cascade (a step that should have refused with rich wording produces a DIFFERENTLY-refused history from that point forward, same as any refusal-shaped mismatch would). A per-entry filter broad enough to swallow Finding 3 would have to match on "any message containing 'missing from JSON args' on the Rust side, or matching 'was not given' on Ruby's" — which is defensible in isolation, but stacking it with an equally-broad filter for Finding 4 (an entirely absent refusal, not a mismatched one — nothing to "strip," a filter can't manufacture the missing entry) starts to look like a comparison that mostly excludes itself, exactly the "silent cap" this whole plan's own verification section warns against ("no silent caps... `log()` what was dropped").

So: `spec/rust_conformance_fuzz_spec.rb`'s own two examples are `pending:` (RSpec's own honest marker for "known failing, not yet fixed," not `skip`/`xit`, which would hide it from output entirely), each citing this document by number, with a short comment pointing at whichever Finding number is expected to be the dominant cause. The comparison logic itself — every helper, every existing filter, `SEEDS_PER_DOMAIN` — is untouched and fully working: un-pending either example locally (`SEEDS=5 bundle exec rspec spec/rust_conformance_fuzz_spec.rb --tag io` after removing the `pending:` line) reproduces every finding above directly, which is exactly what the next session closing Finding 3 or 4 needs to verify against. Fixing either finding for real is expected to flip its example green without touching the spec file itself at all.

3. Re-run the un-gated wide sweep (60+ seeds/domain) after each fix to confirm the fixed finding's OWN signature is actually gone, not just quieter — the same discipline every fix this whole plan has used.

## Status 2026-09-08 — findings 3, 4 and 6 closed; 5 and 7 still open, 7 blocks gating

Stage 10 of the Bluebook semantics migration (docs/semantics/bluebook-semantics.md) un-pended both examples to find out what was really left. Two changes made the comparison honest rather than a silent cap:

- **Refusals are compared by KIND, not wording** (C8.2 — prose is not the contract; the semantics corpus already held both kernels to this). The `error` text still rides along until the existing structural-boundary filters have matched on it, then drops. A Ruby query-log entry for a verb the Rust side structurally refuses ("is not generated for this domain") is dropped by the same ground truth (`structurally_refused_verbs`). A query's own echoed `args` are normalized to `f64` precision on both sides before comparing (`reduce_to_wire_precision`) — `Json::Num` is `f64` end to end, so an integer outside 53-bit exact range is already rounded the moment Rust's own JSON parser reads it, before any argument-typing logic runs; this says the two engines agree once the wire format's own precision is accounted for, not that the wording matches.
- **Finding 3 closed** in both generators: a command's `from_json` now refuses every missing non-optional argument up front as `AbsentArgument`, sorted, through the `absent_args` wording site — before any field is typed. Entity commands get the same check; port operations keep their per-field shape (their receiver exemption was not ported). **Finding 4 closed**: each chapter registry emits `check_query_args`, which builds and invariant-checks every value-object query argument before `named_query::run` reads the raw JSON (`kernel/cli.rs`; embryonaut's committed snapshot predates it and keeps a documented no-op shim).

The un-pended run also found four divergences the original catalogue did not list, all now settled under C3.7 and pinned by corpus fixtures: value-object `pattern`/`admits` were checked *after* invariants in Rust (now nested → constraints → invariants, Ruby's order); a null or missing non-optional value-object field was accepted and stored by Ruby (now `TypeMismatch`, "X.f expects T, got nil", the same wording Rust's generated `from_json` gives it); an optional argument offered as null was refused by Rust (now absent, as in Ruby); and a multi-field composite value offered a non-object shape (a bare Array, every field happening to declare a `default:`) silently defaulted every field on the Rust side instead of refusing — now every generated `from_json` refuses `TypeMismatch` upfront when handed anything but a JSON object.

**Finding 5 remains open and catalogued** — `resolve_state_references` is still not ported; no seed in the gating run reaches `SafeDepositBox.Rent` with a dangling customer. **Finding 6** was explained by C3.3: an out-of-range integer is a `TypeMismatch` at the boundary on both sides now, and the wire-precision normalization above accounts for the rest of what looked Bignum-adjacent.

**Finding 7, newly catalogued this round, is the one thing still blocking gating** — see its own section below: Ruby validates one command argument's shape and invariants together before moving to the next; the generated Rust dispatch checks every argument's shape first, then every argument's invariants, so the two runtimes can pick a different refusal out of the same malformed input. `spec/rust_conformance_fuzz_spec.rb`'s two examples are `pending:` again, citing this finding by number — every other divergence the un-pended run could reach is closed.

Known, recorded wording asymmetry left in place: a bare-scalar command argument's mismatch is worded with the command name in Ruby and the args-struct name in Rust; kinds agree, and no fixture pins the prose.


## Finding 7 — CATALOGUED, not fixed: per-argument shape-then-invariant interleaving order

Found by the stage-10 un-pended run itself, seed 5 of the banking sequence: `Governance::RoleAssignment.Assign` with `scope: {value: ""}` (a valid-shaped but invariant-violating `Scope`) *and* `starts_at: [5, 3]` (an invalid-shaped `Timestamp`, declared after `scope`). Ruby refuses `InvariantViolation` on `scope` — it never reaches `starts_at`. Rust refuses `TypeMismatch` on `starts_at` — the same kind of refusal Rust always answers for this shape, just the wrong ONE of two real refusals present in the same input.

Root cause, confirmed by reading the generated code: Ruby's `coerce_declared_arguments` (interpreting.rb) validates one argument COMPLETELY — shape AND invariants together, via `Value.build` → `validate!` — before moving to the next declared argument, so the first argument whose value is wrong at all (shape or invariant) wins, in declaration order. The generated Rust dispatch function does the opposite: `<Command>Args::from_json` builds every field's SHAPE first (the whole struct, one `Ok(Self { .. })` literal), and only afterward — a separate statement in `dispatch_<command>`, after `from_json` has already succeeded — calls `.check_invariants()` on each field. A shape failure on a LATER-declared argument is reached before an earlier argument's own invariant failure ever gets a chance to run.

**Why not fixed this round**: closing it means restructuring `emit_command`'s generated dispatch shape in both generators — interleaving `field: Type::from_json(..)?; field.check_invariants()?;` per declared attribute instead of building the whole args struct before checking any invariant — a real, generator-wide change, not a local one, with correctness stakes for every command already generated. Scoped, real, and worth doing; not attempted in the same session that found it, matching this document's own discipline for Finding 5.

**Confirmed narrow trigger shape**: needs an EARLIER-declared argument that is shape-valid but invariant-invalid, together with a LATER-declared argument that is shape-invalid, on the SAME command, in the SAME dispatch — `spec/rust_conformance_fuzz_spec.rb`'s own two examples are re-pended citing this finding by number until it closes.
