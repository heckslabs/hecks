# Phase 10's first shipped capabilities — `offset`, `nulls`, and `authorize`/TenantScope, ported for real

**Status:** Shipped, both generators, each verified against a real (or, for one item, purpose-built) fixture. This closes five items of Phase 10's own "long-tail feature-completeness backlog" — the backlog itself stays open; see "What Phase 10 still leaves open," below, and `docs/decisions/0041` for the honest accounting of everything still open, investigated directly rather than guessed at.

## What shipped

A declared `query "X" do ... end` block's own `offset N` now generates for real, for the same subset `order_by`/`limit` already cover (one or more field-comparator conditions, ANDed, against a single aggregate's own attributes). Before this round, ANY declared `offset` — literal or a caller-bound Symbol arg, valid or not — made `rust/project/queries.rb#query_skip_reason` refuse the WHOLE query, unconditionally, the same way `cursor`/`consistency`/`authorization`/`null_semantics` still do.

Ground truth: `Runtime::QueryInterpreter#interpret` (`lib/hecks/runtime/query_interpreter.rb`) already had real `offset` support (a prior round in this same session fixed a bug where `declared.offset` was never read at all — see that file's own "OFFSET FIRST, THEN LIMIT" comments) — this round is purely the Rust side catching up to Ruby's own already-correct behavior, not new Ruby semantics.

**Kernel** (`rust/src/kernel/`):
- `query_ordering.rs` — `pub type Offset = Limit` (identical Literal/Arg wire shape, identical resolution rule — one type, two names, not a duplicate enum). `apply()` gained an `offset: Option<&Offset>` parameter, applied via `Vec::drain` AFTER the declared order and BEFORE the limit truncation — matching Ruby's own `skipped = ordered.drop(...)` then `capped = skipped.first(...)` sequence exactly (SQL's own `LIMIT n OFFSET m` order, not the reverse).
- `named_query.rs` — `QueryDef` gained `pub offset: Option<query_ordering::Offset>`, threaded into `run_cross_domain`'s own `query_ordering::apply` call.
- `read_model.rs` — its own `apply_filtered_head_options` call site now passes `offset: None` explicitly (a read model still has no `offset` field at all; `read_models.rb`'s own eligibility gate is unchanged — this is a real, currently open, separate item on Phase 10's own backlog, not silently closed as a side effect of this round).

**Both generators** (`rust/project/queries.rb` and `rust/codegen/src/queries.rs`, kept in parity per ADR 0010):
- `offset` removed from the combined `extras` refusal list.
- `declared_offset_skip_reason`/`emit_query_offset` added, mirroring `declared_limit_skip_reason`/`emit_query_limit` exactly (identical wire shape) — `emit_query_offset` reuses `emit_query_limit`'s own computation and swaps only the spelled Rust type name (`Limit::` → `Offset::`) so a generated `offset:` field doesn't read as a copy-paste bug to a human.
- `emit_query_def`/`QueryDef` (both generators) and the exemplar placeholder (`rust/src/exemplar/queries.rs`) all gained the new field.

`spec/codegen_parity_spec.rb --tag io`: 8/8 — both generators still produce byte-identical whole-file output on every real corpus member, offset included.

## The real, previously-catalogued gap this closes

`spec/corpus/rust_conformance/named_queries_order_limit.json` — already a real, existing fixture — has always exercised `Banking::ATMCard.ByFee` (`where(status: "active"); order_by :daily_fee; limit 3; offset 1` — the real corpus declaration in `examples/banking/bluebook/payment_cards.bluebook`, comment: "the second-cheapest three, skipping the very cheapest"). `spec/support/rust_conformance_helpers.rb`'s own `KNOWN_REFUSAL_GAP_VERBS` tolerated this ONE verb's refusal-vs-real-answer mismatch by name — a documented, narrow, known gap, not a silent one.

**RED, confirmed directly before any fix**: `bin/rust_conformance examples/banking spec/corpus/rust_conformance/named_queries_order_limit.json native` — exactly one mismatch, Rust refusing `Banking::ATMCard.ByFee` ("is not generated for this domain") where Ruby returns a real 3-row answer.

**GREEN, confirmed directly after**: same command, same fixture, against `examples/banking` regenerated with the fix — `matches.` `KNOWN_REFUSAL_GAP_VERBS` no longer needs to name this verb at all; removed.

## Regenerating banking (and why compliance/pizzas/meta/governance/identity/roster came with it)

`QueryDef` is one shared struct compiled into every domain unconditionally (`rust/src/generated/mod.rs` declares `pub mod <domain>;` for all of them with no `#[cfg(feature = ...)]` gate — only the `active` re-export is feature-scoped), so adding a field to it is a breaking change for every domain that has ANY declared query, not an additive one that could coexist with stale committed output. `bin/project_rust` was re-run for real against every in-repo domain with at least one `QueryDef` row (`banking`, `compliance`, `pizzas`; `meta`, the self-hosted language, regenerates automatically as a side effect of any run) — `roster` and `embryonaut` were also re-run/checked but have zero `QueryDef` rows in either's own tree, so neither's `.rs` content actually changed from this round (confirmed: `roster`'s regen touched only its own `ir.json`/`metadata.rs`/`roster.rs`, no `registry.rs`/`merged.rs` diff). `governance`/`identity` (shared framework chapters both `banking` and `pizzas` pull in via `uses_framework`) came along automatically as part of those domains' own regen — genuinely regenerated from real source both times, not hand-patched.

`embryonaut` itself lives in a separate repo (`embryonaut_bluebooks`, outside this checkout — the known dogfood coupling) and was deliberately NOT regenerated here: its own `registry.rs`/`merged.rs` declare zero `QueryDef` rows today, so the struct change doesn't break its build, and there is no `offset`-bearing query in it to prove anything against. Left untouched, matching the same "don't touch what you can't verify" discipline ADR 0037/0039 already established.

**Honest side effect, not scope creep**: because `banking`/`compliance`/`pizzas` had to be regenerated anyway (the struct change forces it), this round's regen ALSO picked up every already-landed-but-not-yet-regenerated generator fix from earlier in this same session (Phase 3's `none_in_state`, Phase 4's `gt`/`gte`/`lt`/`lte`-against-a-literal, wherever those touch `queries.rb`'s own output for these three domains) — this is unavoidable given the struct change, not a deliberate widening of this round's own scope. `spec/rust_conformance_spec.rb --tag io` (20/20) and the full suite (2232/0 failures) both confirm nothing broke; `spec/codegen_parity_spec.rb --tag io` (8/8) confirms the two generators are still in lockstep.

## UPDATE (same session) — read-model `offset` too

Immediately followed by the natural next step: a declared `report "X" do ... end` block's own `offset`, on the SAME eligible many-side head `order_by`/`limit` already apply to. `read_models.rb`'s own eligibility gate used to refuse ANY declared `offset` unconditionally (`READ_MODEL_BARE_KEYS` didn't list it, so its mere presence as a key disqualified the whole read model) — the exact same shape the AGGREGATE-query fix above just closed, one construct over.

**Kernel**: `read_model.rs` gained `pub type ReadModelOffset = query_ordering::Offset` (an alias, same reasoning as `ReadModelLimit`/`ReadModelOrderBy`) and `ReadModelDef::offset: Option<ReadModelOffset>`, threaded into `apply_filtered_head_options`'s own `query_ordering::apply` call — no `None`-forcing needed this time, since the kernel-side `apply` signature already had the `offset` parameter from the AGGREGATE-query round above.

**Both generators**: `offset` added to `READ_MODEL_BARE_KEYS` (Ruby) / the equivalent Rust const; `declared_offset_skip_reason` (already defined for AGGREGATE queries) reused directly inside `read_model_options_content_skip_reason`; `emit_read_model_offset` added, mirroring `emit_query_offset`'s own "reuse `emit_read_model_limit`'s computation, swap the spelled type name" move; `ReadModelDef`/`emit_read_model_def`/the exemplar placeholder (`rust/src/exemplar/read_models.rs`) all gained the field. A hand-written unit test fixture in `read_model.rs` itself (`find_accepts_both_the_declared_and_the_snake_cased_spelling`) needed the new field too — caught immediately by `cargo test`, not silently left broken.

**The real gap closed**: `Banking.ComplianceDashboard` (`examples/banking/bluebook/customer_and_compliance_views.bluebook` — a rootless-style dashboard over disputed card payments, `order_by :amount, :desc; limit 5; offset 5`) was `KNOWN_REFUSAL_GAP_VERBS`'s OTHER remaining entry, exercised by `spec/corpus/rust_conformance/read_models.json`. **RED, confirmed directly** (via `git stash` to isolate the exact pre-fix binary): one mismatch, Rust refusing `Banking.ComplianceDashboard` where Ruby returns a real answer. **GREEN, confirmed directly after** (`git stash pop`, rebuild): `matches.` `KNOWN_REFUSAL_GAP_VERBS` is now EMPTY — kept as a real, empty array (not deleted), so the next genuine narrow gap has an obvious place to be named.

**Regen scope, this time smaller**: `ReadModelDef` is the same kind of always-compiled shared struct `QueryDef` is, but only `banking` declares any `ReadModelDef` rows today (confirmed by grep before regenerating) — so only `banking` (plus `governance`, pulled in via `uses_framework`, plus `meta`, which always regenerates) needed a real `bin/project_rust` run this time, not the five-domain sweep the AGGREGATE-query round needed.

**A self-inflicted near-miss, caught and fixed before commit**: after regenerating, `rust/Cargo.toml`'s `default` feature had flipped to `["banking"]` (`bin/project_rust`'s own side effect, documented in `spec/project_deploy_parity_gate_spec.rb`'s own comments) — hand-editing just the `default = [...]` line back to `["roster"]` left `rust/src/generated/mod.rs` internally INCONSISTENT with it (its own `#[cfg(...)]` guards and comments still said "banking," reflecting the state at the moment `bin/project_rust` ran, not the hand-edited file). Caught by diffing `mod.rs` against HEAD before committing rather than assuming a one-line Cargo.toml fix was sufficient. Fixed correctly by re-running `bin/project_rust examples/roster` — which regenerates both `Cargo.toml` and `mod.rs` together, consistently, from the tool itself — confirmed via `git diff rust/src/generated/mod.rs` showing zero diff afterward. Lesson for next time: never hand-edit `Cargo.toml`'s `default` feature after a `bin/project_rust` run; re-run the tool for the intended default domain instead.

## UPDATE (same session) — a declared `nulls :first`/`:last`, too

Third round, same session: `query_ordering::OrderBy` gained a `nulls: NullsMode` field (`Native`/`First`/`Last`) — `QuerySpecification::Common::NullSemantics`'s own `mode`, a SEPARATE top-level query/read-model option in Ruby's IR (not nested inside `order_by` there), folded into the one Rust struct that only ever means anything alongside a declared order. Before this, ANY declared `null_semantics` — even a real, meaningful `nulls :last` — made the whole query/read model refuse outright, the same combined-`extras` shape `offset` used to share.

**No refusal case needed at all, unlike `offset`/`limit`**: `nulls(mode)` (`lib/hecks/query_specification/common/dsl.rb`) accepts ANY value, completely unvalidated — `NullPolicy.order`'s own `case policy&.mode.to_s; when "first"...when "last"...else...` already treats an unrecognized mode exactly like no declared `nulls` at all (falls through to the direction-dependent default). `null_semantics_variant` (both generators — `rust/project/queries.rb`, `rust/codegen/src/queries.rs`) mirrors that exact fallback: `"first"` → `First`, `"last"` → `Last`, anything else (including absent) → `Native`, never a refusal.

**Kernel**: `apply_declared_order` rewritten to decide final null placement by `nulls` AFTER the existing direction-based reversal (same order Ruby's own `case` runs in) — `First`/`Last` pin nulls to that end regardless of ascending/descending; `Native` keeps the old direction-dependent default (first for ascending, last for descending) byte-for-byte unchanged for every query that declares no `nulls` at all (confirmed: `spec/rust_conformance_spec.rb`'s entire existing corpus, none of which declares `nulls`, still passes unmodified). Read models get this for free — `ReadModelOrderBy` is `query_ordering::OrderBy` itself, an alias, so the field appears there automatically; only the generator-side `READ_MODEL_BARE_KEYS`/wiring needed touching, no read-model-specific kernel change.

**The real gap closed**: `Banking::ATMCard.Active` (`examples/banking/bluebook/payment_cards.bluebook` — `order_by :nickname; nulls :last`, with `nickname` DELIBERATELY optional per that file's own comment: "Active's own query below relies on this to demonstrate `nulls` for real"). No existing fixture exercised it, so a new one was written (`spec/corpus/rust_conformance/null_semantics_nulls_last.json`) rather than reused: three ATM cards, two renamed (nicknames "Alpha"/"Zulu"), one left unnamed. **RED, confirmed directly** (`git stash` isolation): one mismatch, Rust refusing `Banking::ATMCard.Active` where Ruby returns a real answer. **GREEN, confirmed directly after**: `matches.` — and confirmed SUBSTANTIVELY, not just "no mismatch reported": querying the rebuilt native binary directly shows the exact predicted row order `card-b(Alpha), card-a(Zulu), card-c(nil)` — the unnamed card moved from where the OLD direction-only default would have put it (first, since order_by is ascending) to last, proving the `nulls :last` override is genuinely being read and applied, not coincidentally matching a default that happened to agree.

**Regen scope**: `OrderBy`/`ReadModelOrderBy` are shared structs compiled unconditionally like `QueryDef`/`ReadModelDef` were — every domain with ANY declared `order_by` at all needed the new field, not just ones declaring `nulls`. Confirmed via grep: `banking`, `pizzas`, `meta` (auto). `compliance`/`roster`/`governance`/`identity`/`embryonaut` declare zero `order_by` in any query/read model, so none of their `.rs` content changed.

## UPDATE (same session) — a declared `authorize policy, tenant: :field` (TenantScope), too

Fourth round, same session: a declared query's own `authorize` boundary, real for the first time. Ground truth: `Runtime::TenantScope.apply` (`lib/hecks/runtime/tenant_scope.rb`) — that module's own header is explicit about scope: "the boundary itself, made mandatory... whether THIS caller actually holds `policy` for THIS tenant needs real identity infrastructure this runtime does not have — that stays a named, open gap." `policy` itself is never read by `TenantScope.apply` at all (only `.tenant` is), so this generator carries no `policy` field either — matching Ruby's own scope exactly, not silently answering more than Ruby does.

**No refusal for a tenant-less `authorize`**: `AuthorizationSpec#to_h` is `{policy:, tenant:}`; a `nil` tenant (`authorize policy` alone, no `tenant:`) is a REAL, harmless no-op in Ruby too (`TenantScope.apply`'s own `return declared unless tenant`) — `declared_authorization_skip_reason` (both generators) matches that exactly rather than treating the mere presence of a declared `authorize` as disqualifying.

**Two effects ported, both from `TenantScope.apply`**: (1) the wire arg named by `tenant` must be present or the query refuses (`Unauthorized`/`tenant_required` — the refusal-wording template already existed in the generated kernel, unused until now); (2) a synthetic `field == args[tenant]` condition gets ANDed onto the query's own declared wheres. Both baked into `named_query::QueryDef` — a new `TenantAuth { query_name, tenant_field }` field for (1) (checked in `run_cross_domain` before any filtering runs), and the synthetic condition appended to the compiled `conditions` array at CODEGEN TIME for (2) (reusing the existing `QueryCondition`/`QueryConditionValue::Arg` machinery wholesale — no new kernel filtering logic needed for the condition itself, only the presence check). Deliberately QUERY-only: read models still refuse a declared `authorize` outright, unchanged — no real corpus read model declares one to prove a port against.

**The real gap closed**: `Banking::SafeDepositBox.Rented` (`where(status: "rented"); order_by :branch_code; authorize :vault_access, tenant: :branch_code`). New fixture (`spec/corpus/rust_conformance/authorization_tenant_scope.json`): two boxes rented in two branches, three query steps designed so no accidental fallback (treating `authorize` as inert) could pass all three — no `branch_code` arg at all (must refuse), a real `branch_code` (must return only that branch's box, not both), and an unknown `branch_code` (must return zero rows, not every branch's). **RED, confirmed directly** (`git stash` isolation). **GREEN, confirmed directly after** — and confirmed SUBSTANTIVELY by querying the rebuilt native binary directly: the DOWNTOWN ask returns exactly the DOWNTOWN box, the NOWHERE ask returns zero rows, proving the tenant filter genuinely narrows rather than coincidentally matching.

**A real, general, pre-existing gap this surfaced and fixed along the way**: `spec/rust_conformance_spec.rb`'s own stricter "queries" field comparison (distinct from `bin/rust_conformance`'s own CLI comparison, which didn't catch this) failed on the new fixture even after the authorization logic itself was correct — `kernel/cli.rs`'s "query" step handler only ever pushed a `queries`-list entry on SUCCESS, never on refusal, while Ruby's own `Fuzzing::Replay#call` always pushes one per query step regardless of outcome (`rows: nil`, `error:`, and for a `"::"`-qualified question `reference_rows`/`reference_error` too). This fixture was the FIRST real corpus case ever to exercise a query step that genuinely refuses, so the gap had simply never been exercised before — not introduced by this round's own logic, but real and general (would affect ANY query-step refusal, not just `Unauthorized`). Fixed in `kernel/cli.rs` for both the declared-AGGREGATE-query and read-model branches (the ad hoc filter branch needed no fix — Ruby's own `run_filter` rescue never pushes a `queries` entry on failure either, already matching).

## UPDATE (same session) — read-model `authorize` too, verified against a purpose-built fixture

Fifth round, same session: `authorize`/TenantScope extended to read models, exactly as ADR 0041 (written between the fourth and fifth rounds) predicted it would transfer — `ReadModelDef` gained `authorization: Option<named_query::TenantAuth>` (the SAME struct the query-side port already defined, reused directly, no new type), the presence check inserted into `read_model::run` right after `reference_id` resolves (matching `ReadModelInterpreter#project`'s own call order: `model = TenantScope.apply(model, args)` runs right after the reference id is fetched), and the synthetic condition folded into `read_model_def`'s own `conditions` via `query_conditions_with_authorization` (already generic over "some construct with a `wheres` array and maybe an `authorization` hash" — no read-model-specific version needed). `read_model_filtered_head_as` already treated a real `authorization.tenant` as eligibility-triggering before this round (confirmed by reading it) — this round just stopped refusing on that basis.

**No real corpus read model declares `authorize`** (confirmed, ADR 0041) — so this is the one Phase 10 item this session shipped without a real corpus fixture, verified instead against a purpose-built one: a temp copy of `examples/banking` (never committed) with one new read model, `ComplianceDashboardByAuth` (`reference_to Account; include Account; include CardPayment; where(status: "disputed"); order_by :amount, :desc; authorize :vault_access, tenant: :authorisation`) — the SAME shape as the real `ComplianceDashboard`, plus the tenant boundary. Two disputed card payments (`AUTH-1`, `AUTH-2`), three query steps: no tenant arg (must refuse), `authorisation: AUTH-1` (must return only that ONE payment), `authorisation: NOPE` (must return zero). **RED, confirmed directly** (`git stash` isolation, `bin/project_wasm` + `bin/rust_conformance` against the temp domain): all three query steps refused pre-fix. **GREEN, confirmed directly after** — `matches.`, and substantively: the AUTH-1 ask's own `card_payments` array holds exactly one row (not both disputed payments), the NOPE ask's holds zero, checked by reading the wasm binary's raw JSON output directly, not just trusting the diff tool's summary.

**A self-inflicted `git stash` recovery, same lesson as ADR 0040's own Cargo.toml near-miss**: building the temp fixture domain via `bin/project_wasm` WHILE the real Phase 10 changes were stashed (for the RED baseline) registered `rm_auth_fixture` as a real Cargo feature and regenerated `governance`/`identity` (pulled in via the temp domain's own `uses_framework`) — real, uncommitted side effects landing in the SAME working tree the stash pop needed to reapply into cleanly. `git stash pop` correctly refused to silently clobber either side, left BOTH the stash and the conflicting working-tree changes intact, and named exactly what conflicted. Recovered by diffing tracked-file status before/after the fixture build (the same `tracked_diff`/`restore_tracked_diff` pattern `spec/project_deploy_parity_gate_spec.rb` already uses), reverting only the fixture-build's own byproducts, then popping the stash cleanly onto a tree that once again matched HEAD exactly. Lesson for next time: never build a throwaway fixture domain while real work sits in `git stash` — isolate one or the other first (a worktree, or commit-then-amend, rather than stash-and-build-something-else).

## What Phase 10 still leaves open

The rest of the plan's own Phase 10 list, untouched: query/read-model `cursor`/`consistency`/`group_by`/`count`/`median`; mutation-op gaps (`sets` ops beyond append/set/increment/decrement/delegate — including `corrects`'s own real admissibility half, which needs new per-instance event-log infrastructure the Rust kernel doesn't have at all today; multiply/clamp/remove; cross-aggregate "door"-argument type-bridging limits); `list_of` with `admits:`/`pattern:`. `docs/decisions/0041` has the full, directly-investigated accounting of why each remaining item is a bigger or riskier lift than the five this session shipped. ADR 0039's own finding that banking's committed artifact wouldn't pass the deploy-time parity gate is now FURTHER addressed (the offset-shaped, null-semantics-shaped, and authorization-shaped mismatches it implicitly covered are all gone; the `corrects`-construct gap and the missing-argument-wording gap it also names are untouched, still open, still separately tracked) — banking's own artifact should be re-checked against the parity gate once those are closed too, not assumed clean from this round alone.
