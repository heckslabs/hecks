# `read_model`'s `where`/`order_by`/`limit`/`offset` can now name WHICH many-side `include` they target

**Status:** Shipped, Ruby-only. `seal_query_options` (`lib/hecks/bluebook/dsl/read_model_builder.rb`) has always refused `where`/`order_by`/`limit`/`offset` outright the moment a read model declares more than one many-side `include` — a real, deliberate ambiguity refusal ("no way to say WHICH of several unrelated collections a caller meant"), but with no way at all to resolve that ambiguity: a read model with four `include`s could never filter even one of them, no matter which field. A real production bluebook (`children-of-the-light`'s `NovelSummary`) hit exactly this: `Character`/`Part`/`Timeline`/`Note` all gathered around `Novel`, wanting `where(superseded_by: nil)` on `Character` alone, forced instead into a documented workaround — separate `Character.Active`/`Timeline.InOrder` queries, called and stitched together outside the read model, because `NovelSummary` itself could filter nothing. This ADR gives `where`/`order_by`/`limit`/`offset` an optional `on:` naming which many-side aggregate they apply to, closing that gap without touching the single-target case at all.

## The syntax chosen, and the two rejected

Three shapes were on the table:

1. **A target kwarg on each option**: `where(superseded_by: nil, on: Character)`.
2. **A scoped block**: `on(Character) { where(...); order_by(...) }`.
3. **A filter attached to `include` itself**: `include Character, where: { superseded_by: nil }`.

**(1) was chosen.** The deciding fact, found by reading `rust/parser/src/parse/read_model.rs` directly rather than assuming: `read_model`'s own body is parsed as a flat sequence of already-recognized words (`where`/`order_by`/`limit`/`include`/...), matched line-by-line against a fixed word table — there is no nested-block construct inside `read_model` today (unlike `aggregate`/`command`/`policy`, which all `opens:` a genuinely separate sub-context in the self-hosted grammar, per `lib/hecks/language/bluebook/bluebook.bluebook`'s own `opens:` column). Option 2 would need a brand-new nested `ReadModelTarget` grammar context and a second builder class purely to re-expose `where`/`order_by`/`limit`/`offset` one level down — real, but disproportionate machinery for "which collection does this apply to." Option 3 cannot express more than one `where` clause, or `order_by`/`limit`/`offset` at all, without smuggling a second, parallel option-DSL into `include`'s own kwargs — it doesn't generalize to the same four words this ADR is scoped to.

Option 1 reuses the exact methods (`where_impl`/`order_by_impl`/`limit_impl`/`offset_impl`) and the exact accumulation (`@wheres` is already an array; `@order_by`/`@limit`/`@offset` stay singular, exactly as today) with one additive field each. `on:` is scoped to `ReadModelBuilder`'s own override of these four methods, not the shared `QuerySpecification::Common::DSL` mixin `Query` also uses — a plain `query` block has no `aggregate_heads` concept at all, so `on:` there would be a silently-ignored no-op; overriding only in `ReadModelBuilder` means a `Query` calling `where(..., on: X)` gets Ruby's own loud `unknown keyword: :on` instead.

`on:` names the included aggregate by TYPE (`on: Character`, matching `include`'s own primary argument, resolved through the same `Naming.demodulise` `reference_to`/`include` already use) — not by the include's own `as:` alias. **A real, deliberate scope limit, not an oversight**: a read model that `include`s the SAME type twice under two different `as:` aliases has no way to say which one `on:` means, today. No real corpus read model does this (`NovelSummary`/`CustomerPortfolio`/`ComplianceDashboard` all include each type once), so it wasn't built; accepting `on:` as *either* a type constant or an `as:` symbol is the natural follow-up the moment a real bluebook needs it.

## What changed

- **`WhereClause`/`OrderBy`/`LimitSpec`/`OffsetSpec`** (`lib/hecks/query_specification/common/*.rb`) each gain an optional `target` member. `to_h` omits the `target:` key entirely when unset — the same "absent, not null" convention `count`/`median_field` already established (`lib/hecks/bluebook/read_model.rb`'s own comment), so every existing golden IR fixture (`spec/golden/ir/*.json`) for every real read model stays byte-identical; nothing serializes a new key until a bluebook actually declares `on:`.
- **`ReadModelBuilder`** overrides `where_impl`/`order_by_impl`/`limit_impl`/`offset_impl` to accept `on:`, resolving it once via a shared `resolve_target` (`Naming.demodulise`, `nil` when omitted).
- **`seal_query_options`** no longer asks one question ("exactly one many-side head?") — it asks two, independently:
  1. Does every `on:` actually name a many-side included aggregate? (Checked regardless of how many many-side heads exist — a typo refuses immediately, not only when ambiguity would otherwise bite.)
  2. Is there still an **untargeted** `where`/`order_by`/`limit`/`offset` (or `authorize`'s `tenant:`, unchanged and out of scope for `on:` — see below) declared? If so, the read model needs EXACTLY one many-side head for that untargeted option to mean anything — the original rule, verbatim, still enforced, still with the same message text (`spec/runtime/read_model_interpreter_spec.rb`'s existing `/includes N many-side aggregates, not exactly one/` regex still matches).

  A read model with several many-side heads is legal now precisely when every declared option is targeted; one with a single many-side head is unaffected either way, `on:` or not.
- **`Behaviour::ReadModel#filtered_head_name`** (singular) becomes **`#filtered_head_names`** (plural) plus a new **`#options_for(head_as)`**, which returns a small view (wheres/order_by/limit/offset/null_semantics) scoped to one head — untargeted options apply when that head is the sole many-side head (the old behavior, unchanged), targeted ones apply when their `target` resolves to that head's own aggregate.
- **`Runtime::ReadModelInterpreter#project`** and **`Adapters::SqliteProjection#query_read_model`** — both call sites that used to compute one `eligible` name and run `Ports::Query::InMemory.execute(rows, model, args)` against it now iterate `filtered_head_names` and run `execute(rows, model.options_for(head[:as]), args)` per eligible head, so two different many-side collections can each be filtered/ordered/paged independently in the same read model, in the same pass.
- **`group_by`/`count`/`median`** are explicitly UNCHANGED — `seal_group_by`/`seal_aggregation` still require exactly one many-side head, no `on:` support. A real, deliberate scope limit (see below), not an oversight.

## Rust parity — explicitly a follow-up, for three separate, real reasons found by reading the actual Rust source, not assumed

1. **The kernel's own `ReadModelDef` is single-target by construction.** `rust/src/kernel/read_model.rs`'s `ReadModelDef` carries exactly one `filtered_head: Option<&'static str>` plus one flat `conditions`/`order_by`/`offset`/`limit` — not a per-head map. Making the kernel multi-target-aware means restructuring this struct (and its one hand-written interpreter, `run()`) from "the one eligible head" to "zero or more (head, options) pairs" — a real, load-bearing change to a struct every generated domain's `READ_MODELS` table uses, the same shape of cross-cutting risk ADR 0048 declined to make unilaterally for `corrects`. Out of scope here.
2. **The codegen eligibility gate would otherwise silently miscompile, not just fail to support, this shape** — found and closed defensively in this PR even though full execution stays out of scope. `rust/project/read_models.rb`'s `read_model_filtered_head_as` picks `aggregate_heads.find { |head| head[:many] }` — the FIRST many-side head, unconditionally, trusting the very invariant this ADR relaxes. Before this change, Ruby's own `seal_query_options` made it structurally impossible for this function to ever see more than one many-side head with options declared; after this change, it's possible, and unless guarded, this codegen would silently generate a `ReadModelDef` applying a `Character`-targeted `where` to whichever many-side head happened to be declared first (e.g. `Part`) — a real, silent Ruby/Rust divergence, exactly what this task was asked not to introduce undiscovered. **Closed by a new skip-reason**, mirrored in both generators (`rust/project/read_models.rb` and `rust/codegen/src/read_models.rs`, verified byte-identical the same way every other skip-reason already is): a read model with more than one many-side head and ANY declared `where`/`order_by`/`limit`/`offset` is now refused cleanly at codegen time ("not generated yet"), the same honest, already-established shape as every other out-of-scope option this generator names — never silently miscompiled, and never a row this PR needed to make actually correct.
3. **`rust/parser`'s own `.bluebook` text parser doesn't recognize `on:` and would misparse it, not refuse it.** `rust/parser/src/build/query_derive.rs`'s `where_clauses` turns EVERY named argument pair on a `where` line into a `WhereClause` unconditionally — it has no concept of a non-field named argument on `where` at all. Fed a real `where(superseded_by: nil, on: Character)` line, this parser would today read `on: Character` as a SECOND where clause on a field literally named `on`, comparing it against the token `Character` — silently wrong, not a diagnostic. **Deliberately not fed anything**, for this PR: the new syntax is exercised only in Ruby-side specs and a throwaway `Hecks.with_registry` doc example, never in any real corpus bluebook (`examples/banking/bluebook/*`, or any dogfood domain) that `rust/parser`/codegen ever touches — so this gap exists, is named here, and is inert today. **A required precondition of ever shipping this capability in a real, Rust-ported domain**: `rust/parser`'s own argument-gate handling for `where`/`order_by`/`limit`/`offset` needs to learn `on:` as a distinct, non-field named argument (mirroring however `include`'s own `as:` is already special-cased) before parity can even be attempted, independent of the kernel work in (1).

None of this was discovered mid-flight and left implicit — all three were traced through the real Rust source before this ADR was written, per this project's own standing discipline (ADR 0048/0049/0050's own "read the actual code, don't assume" precedent).

## What's still out of scope

- `on:`-by-`as:`-alias (see above) — no real corpus need yet.
- `authorize(...).tenant`'s own targeting — a read model with several many-side heads and a declared `authorize policy, tenant: :field` is still refused exactly as before; extending `on:` to it is a natural, separate follow-up (`tenant:` scopes a caller-identity check, not a collection filter — worth its own design pass, not bundled here).
- `group_by`/`count`/`median` staying single-many-head-only (above).
- Full Rust kernel/parser/codegen execution support (above) — three concrete, separately-scoped follow-ups, not one open-ended gap.

## A live bug this change actually hit, found and fixed, not merely anticipated

`WhereClause`/`OrderBy`/`LimitSpec`/`OffsetSpec`'s new `target` member is reconstructed from the wire IR by `lib/hecks/bluebook/assembly/marks.rb` — the REPLAY path every real boot goes through (`ReadModelBuilder#build` produces the DIRECT, in-process objects, but a real `Hecks.bluebook`/`Hecks.boot` load reconstructs every construct from its own serialized `to_h` instead). The first working version of this change built `target` correctly at DSL time and serialized it correctly, but `marks.rb`'s own `where_clause`/`order_by`/`limit` reconstruction methods were hand-written before `target` existed and never read it back — `on:` silently vanished the moment a real bluebook loaded (reproduced directly: `Character.Supersede`'s own `on: Character` never reached the interpreter, and every row came back unfiltered). Fixed by reading `clause[:target]`/`declared[:target]` in all three; `offset`'s own reconstruction is generic (`OPTIONS`-table-driven, spreads whatever keys the wire hash carries) and needed no change at all. Found by running the real spec suite against a real Banking boot, not by inspection — the exact discipline ADR 0050's own "found a gap in the existing verification harness" section already models.

A second, narrower Ruby bug surfaced the same way: `ReadModelBuilder`'s own override of `where_impl` (needed to add `on:`) broke on plain `where(field: value)` calls with NO `on:` at all — Ruby stops auto-converting a bare `**kwargs` hash into a positional argument the moment a method declares any real keyword parameter, so `where_impl(clauses, on: nil)` raised `wrong number of arguments (given 0, expected 1)` on every ordinary call, never reaching `on:`. Fixed with a `(*positional, on: nil, **rest)` signature, verified directly (`ruby -e` reproduction) before and after. A related but distinct issue — bare `WhereClause`/`OrderBy`/etc referenced from `ReadModelBuilder`'s own lexical scope resolve to an unrelated self-hosted-grammar construct of the same name via `ConstShim`'s `const_missing`, not `QuerySpecification::Common`'s real struct — fixed by fully qualifying all four references.

## Verification

- **New coverage**, `spec/runtime/read_model_interpreter_spec.rb`: a read model with THREE many-side heads (`Account`/`Entry`/`Note`, mirroring `NovelSummary`'s own shape) refusing an `on:` that names a non-many-side aggregate (the ROOT itself); a real, seeded, two-many-head read model (`CardPayment`/`ATMCard` off `Account`, added to the real Banking domain from Ruby, not the corpus files) where `on: CardPayment` filters CardPayment to its disputed set while ATMCard — with no `on:` of its own — comes back whole; the still-ambiguous refusal when an option omits `on:` with more than one many-side head is the EXISTING spec, unchanged, and still passes with the identical message text.
- **Full suite, twice** (default tags, and `--tag io`): `2430 examples, 0 failures` both runs (was `2428, 0` before this session's own two new examples).
- **`bundle exec rubocop`** on every changed Ruby file (`where_clause.rb`/`order_by.rb`/`limit_spec.rb`/`offset_spec.rb`/`read_model_builder.rb`/`behaviour/read_model.rb`/`read_model_interpreter.rb`/`sqlite/projection.rb`/`assembly/marks.rb`/the spec file): `10 files inspected, no offenses detected` (two `Metrics/CyclomaticComplexity` offenses from the first draft of `seal_query_options`/`filtered_head_names` were fixed by extracting named helper methods, not by disabling the cop).
- **`bin/model_check`**: `0 errors` across every real domain — unaffected, as expected (this change touches no aggregate/lifecycle).
- **`bin/doc_coverage`**: "every live word carries prose and a running example" — unaffected, because `on:` is a new named ARGUMENT on already-admitted words (`where`/`order_by`/`limit`/`offset`), not a new WORD; see the self-hosted-grammar gap named below.
- **`spec/guides_spec.rb`**: all 17 guides pass, including `queries-and-read-models.md`'s own new, REAL, executed doctest (a tiny invented `Bookshelf` domain — `NovelSummary`, `Character`/`Note`, `on: Character` — proving the filtering for real, not merely shown).

## One more explicitly named gap: the self-hosted grammar table itself

`lib/hecks/language/bluebook/{projection,paging}.bluebook` — the self-hosted grammar's own argument-gate rows for `where`/`order_by`/`limit`/`offset` in `ReadModel` context — were NOT updated to add an `on:` row. This is safe today (word_gate's `try_calls_through` forwards `builder.send(calls, *args, **kwargs, &block)` unfiltered for any word with a non-empty `calls:`, so the grammar table plays no role in admitting or rejecting `on:` at runtime — confirmed directly, not assumed, while diagnosing the bugs above), but it does mean `docs/implemented/reference/`'s own generated tables (`bin/reference`) won't list `on:` as a recognized argument for these four words. A real, deliberate scope limit for this PR, not an oversight: `docs/query-dsl.md` and the guide both document `on:` in hand-written prose instead. Adding the grammar rows (and regenerating `docs/implemented/reference/`) is a small, separate follow-up.
