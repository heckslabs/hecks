# PostgresEra's era-1 self-mint now finds a vendored bluebook's own real source text

**Status:** Fixed. `EraCheck.source_text_for` (`lib/hecks/ports/persistence/plugins/era/era_check.rb`) now checks the registry itself for a `uses_embryonaut_bluebook` attachment before falling back to a single-file domain directory's one file — closing a gap where a vendored, PostgresEra-bound second bluebook could get minted with an entirely different domain's own source text stamped as its held era-1 text.

## The bug, found live

A real, private project (children-of-the-light — its own `.bluebook`/`.hecksagon`/`.world`, a real PostgresEra-backed Postgres database, already at era 12 of its own schema history) added `uses_embryonaut_bluebook "notes"` to its `.hecksagon`, attaching a second, small, vendored bluebook chapter named `Notes` (`vendor/embryonaut_bluebooks/notes/bluebook/`), with a matching `Hecks.hecksagon "Notes" do persisted_by "PostgresEra" end` and `Hecks.world "Notes" do ... end` binding it to the same database — mirroring exactly how `examples/banking` wires `Governance`/`Identity` via `uses_framework`.

The first `Hecks.boot` printed "BOOT OK" — PostgresEra silently self-minted a fresh era 1 for the never-before-seen `Notes` domain, the ordinary, expected outcome for any brand-new domain with zero prior eras. A second, separate `Hecks.boot` call (a fresh Ruby process, nothing changed on disk in between) against the SAME database then refused: `cannot boot Notes: the shape changed (era 2) and no translation edge covers it`.

`Notes`' own real shape, computed directly and independently of boot (`StorageShape.mint_hash` after an ordinary `Loading.bootstrap`/`load_bluebooks` sequence), was identical and deterministic across two separate Ruby processes. The shape computation itself was never in question. Querying `hecks_eras` directly told the real story: `Notes`' own single era-1 row held `held_text` starting with the literal string `Hecks.bluebook "ChildrenOfTheLight" do` — the TARGET domain's own bluebook source, stamped under `Notes`' own name. Deleting that row and retrying reproduced the identical bug again — deterministic, not a race.

## Root cause

`Runtime::Loader.run_boot_gates!` runs `Runtime::EraCheck.check_lineage!(registry, directory)` once per boot, which loops `registry.bluebooks.each_value` and, for each one, calls `source_text_for(bluebook, directory)` to recover that bluebook's own real source text — the text PostgresEra's era-1 self-mint (`LineageManager::EraResolver.check!` → `Lineage#hold_first!`) freezes into `hecks_eras.held_text` the first time it sees a domain with no prior eras at all.

`source_text_for`'s own job is entirely file discovery: given a bluebook's declared name, find the real `.bluebook` file(s) that built it. Its primary path — scanning every `.bluebook` file in the domain's own directory for one that literally declares `Hecks.bluebook "<name>"` — is correct and was never the problem (and is exactly what a prior fix, still visible in this file's own header comment, closed for `uses_framework`: a domain directory holding more than one file, one of them a framework member's, is resolved correctly by content match, then by `Framework.members` lookup). The bug lived in the SINGLE-FILE special case one level down: a domain directory holding exactly one `.bluebook` file falls back to treating that one file as the answer for WHATEVER bluebook is being asked about — "a fixture may legitimately name its file differently from the `Hecks.bluebook` it declares" — **unless** the bluebook being asked about is a known `Framework.members` name, in which case the framework registry is consulted instead.

That single exclusion (`Framework.members.key?(bluebook.name)`) was the whole guard. `uses_embryonaut_bluebook` has no equivalent registry — `lib/hecks/embryonaut_bluebook.rb`'s own header explains why: a vendored package ships in the CONSUMING project's own checkout, not inside this gem, so there is nothing analogous to `Framework::ROOT` to check membership against. So the single-file fallback let a vendored bluebook fall straight through: `Target`'s own directory held exactly one `.bluebook` file (`target.bluebook`), `Notes` is not a `Framework.members` key, and the guard handed `Notes`' era check the TARGET's own file, verbatim, as if it were `Notes`' own source. This is not a closure-capture bug or a memoization bug — each loop iteration in `check_lineage!` calls `source_text_for` fresh, with its own `bluebook` block parameter — it is a genuinely incomplete exclusion list: one real "where else could a bluebook's source live" answer (`Framework.members`) was checked, and a second, equally real one (`uses_embryonaut_bluebook`) was not.

The wrongly-stamped `held_text` is inert for the boot that writes it — `hold_first!` never re-parses it, it just freezes it as a record. The damage surfaces on the NEXT boot: `EraResolver.check!` re-derives `Notes`' own REAL current shape from its own real bluebook (now correctly resolved, since `check_lineage!` is asked fresh every boot) and compares it against the shape a shadow-reparse of the WRONGLY held text would have produced — which is `Target`'s shape, not `Notes`'. They can never match (two unrelated domains essentially never share a shape by coincidence), so `EraResolver` falls all the way to `mint!`'s no-translation-edge refusal: a real, deterministic false positive on drift that was never real.

## The fix

`source_text_for` (and its extracted helper `fallback_source_files`) now takes an optional `registry:` and asks it the one question `Framework.members` cannot answer: did any hecksagon in this registry record a `uses_embryonaut_bluebook` call whose name Pascal-cases to this bluebook's own declared name? (`HecksagonBuilder#uses_embryonaut_bluebook` already records every call onto `@vendored_bluebooks`, carried onto the built `Hecksagon` — this was already there, just never consulted here.) When it did, that name resolves to the exact directory `EmbryonautBluebook.load!` itself already resolves from (`<registry.root>/vendor/embryonaut_bluebooks/<name>/bluebook/`, rebuilt from `directory` the same way `check_lineage!`'s own `directory` parameter already is `registry.root`'s immediate child), and every `.bluebook` file there — in the same `Dir.glob` order actually loaded at boot — becomes the real source text. The single-file fallback's guard now excludes a bluebook resolved this way, exactly as it already excluded a `Framework.members` one.

`check_lineage!` threads `registry` through to `source_text_for` at its one call site; the two pre-existing specs in `spec/runtime/era_check_spec.rb` that call `source_text_for` directly with two positional arguments still pass unmodified, since `registry:` defaults to `nil` (skipping the vendored lookup entirely — the correct behavior for a caller with no real registry to ask).

## Why `uses_framework "Governance"` alone does not reproduce this

Checked directly before writing the regression spec, not assumed: `Governance` IS a `Framework.members` key, so the pre-existing guard already excludes it from the single-file fallback correctly, whether or not the attaching domain's own directory holds one file or several (`examples/banking`'s own multi-file directory and a hypothetical single-file `uses_framework "Governance"` fixture both resolve correctly, before and after this fix). Only `uses_embryonaut_bluebook` — the one attachment mechanism with no `Framework.members`-shaped registry to check — reproduces the bug.

## A discrepancy from the original field report, checked and left named rather than silently smoothed over

The original live report also described the wrongly-minted row's `label` column as populated (and matching, likely non-coincidentally, `ChildrenOfTheLight`'s own real era 12 label). Reproducing the bug against this repo's own current schema shows `Lineage::EraStore#hold_first!` (era 1's own mint path) never sets `label` at all — only `held_text`/`held_digest`/`held_projection`; `label` is populated only by a later `mint!` (era > 1, a real translated edge). The `held_text` corruption reproduces byte-for-byte and is the actual, confirmed root cause; the `label` detail may reflect a different code path or gem version in the private project, and is left unresolved here rather than asserted as reproduced.
