# Phase 10's remaining backlog, scoped by direct investigation — none of it is a same-shape repeat

**Status:** Investigated, not implemented (except read-model `authorize` — see the UPDATE below, which this ADR itself predicted and a later round in the same session went on to ship). ADR 0040 shipped four real Phase 10 items in this session's first pass (declared-query `offset`, read-model `offset`, `nulls :first`/`:last`, `authorize`/TenantScope for queries) — all four shared one property that made them tractable in a single low-risk pass: each mapped directly onto kernel machinery (`QueryCondition`/`QueryConditionValue::Arg`, `query_ordering::apply`) that already existed for a sibling feature, and each had exactly one real, motivating corpus declaration to prove a fix against. This ADR documents, by reading the actual code rather than guessing, why every item covered below does NOT share that property — so a future round scopes correctly instead of re-deriving this.

## `corrects` — the one that looked smallest, and had a real surprise in it

Real corpus motivation is strong: `Banking::Account.CorrectFee` (`examples/banking/bluebook/deposit_accounts.bluebook`) is the only declared `corrects` in the whole corpus, and it uses the SIMPLE shape — explicit `sets` mutations alongside `corrects "FeeApplied", reason: "..."`, not the `reverses: true` derived shape (see below for why that second shape is its own, separate, harder problem).

**What's genuinely easy, confirmed by reading `MutationApplier#apply` directly**: `:corrects` is a REAL no-op at mutation-application time — "it targets no field on THIS instance... whatever field this correction actually changes is an ORDINARY declared... mutation of its own, applied by one of the branches above like any other." For `CorrectFee` specifically, that means `corrects "FeeApplied"` compiles to literally nothing, and the two mutations that DO real work (`sets :balance, increment: :amount` / `sets :fees_cents, decrement: :amount`) are PLAIN increment/decrement — already fully supported by the generator today. Porting this half is genuinely small: allow `"corrects"` into `commands.rb`'s `unsupported_ops` allow-list, add a `when "corrects" then nil` arm to `mutations.rb`'s case (mirroring `"delegate"`'s existing one), done.

**What's NOT small, found by reading `CommandRules::Admissibility#enforce_correction_target` directly** — the actual reason `CorrectFee` refuses when it should:

```ruby
def enforce_correction_target(instance, aggregate, command, domain:)
  command.mutations.each do |mutation|
    next unless mutation.op == :corrects
    event_key  = "#{domain}::#{aggregate.hecks_name}"
    event_name = mutation.target.to_s
    next if @registry.event_log.any? do |event|
      event.name == event_name && event.aggregate == event_key && event.id == instance.id
    end
    raise NothingToCorrect, "..."
  end
end
```

This checks whether THIS SPECIFIC instance has ever emitted the named event, against `@registry.event_log` — a full, queryable, per-instance event history. **Confirmed directly: no such structure exists anywhere in the Rust kernel today** (`grep -rln "event_log\|EventLog\|emitted_events" rust/src/kernel/*.rs` — zero matches). `kernel/cli.rs`'s own `events` output field is a flat list built up DURING one replay run, for reporting/comparison — not a queryable, per-instance history `dispatch_by_name` could consult mid-dispatch to answer "has aggregate X, id Y, ever emitted event Z." Porting `enforce_correction_target` for real means adding genuinely new state — either a per-instance emitted-event-name index threaded through the `Store`/dispatch pipeline (touches every aggregate's own generated code, not just ones using `corrects`), or some other mechanism not yet designed. This is real, separate kernel-architecture work, not a codegen wiring task — the same class of gap ADR 0036 (PostgresEra concurrency) documented rather than rushed.

**UPDATE (same session) — the gap is precisely scoped now, into two real, comparably-sized design options**: `docs/decisions/0048` traces `rust/host/src/dispatch.rs`'s ACTUAL production dispatch path (not just the CLI conformance harness) and finds the kernel's own `events: Vec<Event>` accumulator (`cli.rs`) already structurally mirrors `@registry.event_log` — but `rust/host`'s real snapshot optimization (`journal::load_steps_after`, skipping full replay once a snapshot exists) means a `corrects` check built on that accumulator alone would be silently wrong in production once a domain's journal grows past its first snapshot. Two concrete options, either requiring real design/product decisions, not just code: (1) extend the snapshot format to also carry forward a per-record "corrected-event-names seen" set, preserving the performance optimization; (2) force full replay for any domain using `corrects` at all, simpler but a permanent, journal-size-scaling performance cost for such domains. "Not yet designed" is now "two named options, needing a decision between them" — real forward progress on scoping, even though neither option was implemented.

**A second, independently-flagged reason not to touch `reverses: true` at all right now**: `AggregateBuilder#seal_correction_targets`'s own comment (`lib/hecks/bluebook/dsl/aggregate_builder.rb`) is explicit that `append`/`remove` reversal "LOOK symmetric but are not reliably so... collapsing one shape into the other correctly needs the target list's own value-object field names, not just the mutation's own recorded shape — a real gap, left for a follow-on round rather than guessed at here." That's Ruby's OWN authors declining to fully solve this; porting it to Rust before Ruby's own derivation is complete would mean chasing a moving, partially-unspecified target.

## `group_by`/`count`/`median` — a new aggregation concept, not a new option

**UPDATE (same session) — the "per-adapter query-building logic" half of this claim was checked directly and is wrong; the real scope is narrower but still substantial.** A follow-up grep specifically for `group_by`/`GROUP BY`/`.group(` across every adapter (`postgres.rb`, `d1.rb`, `sqlite.rb`, `heki.rb`, `memory.rb`) found **zero matches** — no adapter pushes grouping down to SQL at all. `group_by`/`count`/`median` are computed entirely in Ruby, in `read_model_interpreter.rb` alone, over rows already fetched from the repository by whichever adapter answered the query (`rows.group_by { |row| row[field] }`, a hand-rolled `median` function, `nest` building the group-by-field-declared nested structure) — the SAME row set any adapter's own ordinary where/order-by machinery already produces, not a per-adapter concept. This means a Rust port would NOT need per-adapter query-building work — it needs ONE new shared kernel primitive (grouping + count/median over an already-fetched row set, the same shape `query_ordering::apply` already is for sort/offset/limit), reusable across every adapter's row-fetch path exactly the way `query_ordering::apply` already is. That still leaves real, substantial new work: the primitive itself doesn't exist yet, AND (unlike offset/limit, which never change the SHAPE of what's returned) a grouped/nested result changes the OUTPUT SHAPE itself — the exported JSON becomes a nested-by-group-field structure, not a flat row list — meaning this touches the response contract, not just an internal filter/sort step. `median`'s own even/odd-count convention and multi-field `nest`'s exact nesting order both need byte-for-byte Ruby parity, the same rigor every other Phase 10 item this session held itself to. Correcting the "cross-adapter" framing narrows WHERE the work lives but does not shrink it to a same-shape repeat of anything already shipped.

**UPDATE (same session) — the "simplest" real corpus case turns out to be a compound gap, not a single one.** Checked which real declarations actually exist: `AccountsByKind` (`examples/banking/bluebook/customer_and_compliance_views.bluebook`) is genuinely the simplest shape — `include Account` alone, `group_by :kind, :number`, no joins — while `DisputedPaymentCount`/`DisputedPaymentMedian` are two-head joins (`reference_to Account`, `include Account`, `include CardPayment`) needing the multi-head framework regardless. But `AccountsByKind` turns out NOT to be a small increment either: it declares no `reference_to` at all — it's a ROOTLESS read model (reads its one head's WHOLE table, not one record addressed by reference) — and `read_model_skip_reason`'s own logic (`rust/project/read_models.rb:162`) requires a `reference_target`-matched root for ANY read model, group_by or not; a rootless model has none, so it's refused before the group_by check is ever reached. **Rootless read-model support does not exist anywhere in this generator today** (confirmed: `rust/project/read_models.rb`'s own header explicitly names it, alongside `group_by`, as a capability that exists on this codebase's `main` branch but never landed on this branch's own `ReadModel`/`ReadModelInterpreter` lineage). So even the "simplest" real corpus group_by declaration needs TWO stacked new capabilities — rootless read-model support (a real, separate, standalone gap, currently undocumented as its own item anywhere in this ADR) THEN grouping/nesting on top of it — not one. A future round wanting to make headway here would get more value shipping rootless support first, on its own, before attempting group_by at all; that decomposition itself is new, useful scoping this investigation surfaces.

**UPDATE (same session) — traced far enough into the actual kernel/codegen shapes to leave a near-implementation-ready design sketch, stopping short of writing the code itself.** Reading `rust/src/kernel/read_model.rs`'s real `run` function and `AggregateScan` (`repository.rs`) directly, rather than assuming, found the rootless prerequisite is more tractable than it looked:

- **The whole-table read primitive already exists and is already Ruby-order-correct**: `AggregateScan::scan(&self, aggregate: &str) -> Option<Vec<(String, Json)>>` returns every record of an aggregate, id-ascending — already documented as matching Ruby's own `Ports::Query::InMemory`/`QueryInterpreter` id-ascending default. A rootless head would read via `store.scan(head.aggregate)` directly, a genuinely small addition alongside `run`'s existing `fetch_root`/`scan_matching` head-read modes (needing `ReadModelDef.reference_name` to become `Option<&'static str>`, skipping the current unconditional `args.get(def.reference_name)` resolution when absent).
- **The real architectural fork, found by tracing `nest`/`Value.materialize_unwrapped` precisely**: `nest`'s own per-field unwrapping (`AccountKind{name:"current"}` → bare `"current"`) is a TYPE-LEVEL fact — `value.value_object.sole_attribute`, resolved from the DECLARED shape, never from a runtime value's own apparent structure — not something a generic, data-driven `ReadModelDef` (the pattern `offset`/`order_by`/`authorize` all fit into, interpreted once by one hand-written `run` function) can express: `run` has no per-field type information at all once it's holding already-serialized `Json`. This means `group_by`'s own emission can't be "one more field on `ReadModelDef`" the way every already-shipped Phase 10 item was — it needs PER-READ-MODEL GENERATED CODE (a bespoke function per `group_by`-declared read model, the same shape `emit_command`/`emit_query` already are, not `emit_read_model_table`'s shared-interpreter shape), built by walking each attribute's declared type recursively and calling `sole_field_of(type_name, value_objects_by_name)` (`rust/project/json_codec.rb:78` — already exists, already mirrors `Behaviour::ValueObject#sole_attribute` exactly, already reusable verbatim) to decide, PER FIELD, whether to strip a wrapper.
- **This changes the honest cost estimate**: not "port one more option into the existing data-driven table," but "add a second, real code-generation strategy to the read-model generator, alongside the one that already exists" — a genuinely bigger unit of design than anything else this session shipped, even with the whole-table-read half now de-risked.

No code was written for this — the risk of a rushed, partially-verified generic mechanism that turns out to be the wrong shape (discovered only after committing to it) outweighs the value of a hasty attempt, the same judgment this session applied to `list_of admits:/pattern:` (ADR 0043) and `remove:` (ADR 0047). A future round has, at minimum, the exact fork to design around instead of discovering it mid-implementation.

**UPDATE (same session, after `corrects` shipped) — a real attempt, reverted cleanly, that narrows the remaining unknown to one specific thing.** With `corrects`'s own experience fresh (a function-pointer field on a data-driven struct closed an analogous "the kernel's generic interpreter has no type information at this point" gap cleanly, no `dispatch()` signature change needed), the same shape was tried here: `ReadModelDef` gained `group_by: Option<fn(Vec<(String, Json)>) -> Json>`, `reference_name` became `Option<&'static str>`, and `run` gained a rootless head-read branch (`store.scan(head.aggregate)` directly, bypassing `fetch_root`/`scan_matching` entirely — matching Ruby's own "each rootless head reads its own aggregate's whole table, independently, never cross-joined" rule) plus an output-side hook to call the transform function on the one `many`-side head instead of wrapping it as a flat array. This compiles-shape design is sound and was reverted only because it was left mid-build (the generator side — actually emitting a bespoke transform function's BODY per read model — was not yet written), not because anything about the struct/kernel shape was wrong.

The ACTUAL remaining unknown, found only by getting this far: `group_by`'s transform function receives `Vec<(String, Json)>` — the record's ALREADY-SERIALIZED JSON (from `store.scan`), not a typed struct — because `run` is one generic, hand-written interpreter with no per-record Rust type to speak of. This means the "recursive unwrap single-field VOs" logic (`sole_field_of`-driven, per ADR 0041's own prior update) has to walk a JSON *value*, guided by type knowledge baked into the GENERATED CODE at Ruby-codegen time (which fields/paths are known single-attribute VOs), not simply typed field access the way `corrects`'s own flag check could lean on `Expr::Lookup`. Worse, that same JSON now ALSO carries `corrects`'s own synthetic `emitted_*` flag fields (ADR 0049) — real Rust-only bookkeeping with no Ruby analog — which a group_by transform must explicitly exclude by construction (build the output from `aggregate[:attributes]` + lifecycle directly, never from the raw scanned JSON's own full key set), the exact same leak `bin/rust_conformance`'s own comparison harness already had to guard against. Neither problem is unsolvable — the codegen-time attribute walk needed already exists in spirit (`emit_fielded_record`'s own per-attribute loop already distinguishes list/scalar/nested shapes) — but writing and verifying it correctly, for a genuinely recursive multi-level VO nesting case, is real, additional engineering, not a mechanical finish. This is now the single most precise remaining scoping this backlog item has had all session.

**UPDATE (same session) — one more real layer confirmed, then a firm stop.** Checked `Instance#to_h` directly (`lib/hecks/runtime/instance.rb:97`: `@state.merge(id: @id)`, no materialization at all) to resolve a genuine ambiguity in this ADR's own prior update — confirmed `row(record)`'s own top-level fields stay as LIVE, still-typed values (`Value` instances, `Array`s) exactly as stored, never pre-converted to plain Hashes before `materialize_unwrapped` sees them. This validates the codegen-time type-walk approach (Rust has no runtime type left once serialized to JSON, but the SAME information Ruby's dynamic dispatch reads at runtime is available statically at Ruby-codegen time, the ordinary compiled-vs-interpreted difference every other Phase 10 port already has).

But it also surfaces one more real requirement: `materialize_unwrapped` recurses into a plain Hash (`when Hash then value.transform_values { ... }`) exactly the same way it recurses into a `Value` — meaning an ENTITY-typed list field (`Account.ledger: list_of(LedgerEntry)`, not a value object, so not present in `value_objects_by_name` at all) still needs its OWN nested VO fields unwrapped (`LedgerEntry.narrative: Narrative`, a single-field VO, needs unwrapping to a bare string exactly like a top-level field would). A codegen-time walk generating this correctly needs to look up `aggregate[:entities]` alongside `value_objects_by_name` — treating an entity like an always-multi-field composite (never itself single-attribute-unwrappable, but its own attributes still need the identical recursive treatment) — not just the value-object case this ADR's own prior updates focused on.

This is real, additional, verified scoping — not hand-waving — but it is also the point at which continuing to push forward stops being responsible: each layer traced this session has revealed one more genuine subtlety (rootless read semantics, the function-pointer design fork, JSON-vs-typed-struct, corrects-flag exclusion, and now entity-nested-VO recursion), and a system whose whole purpose is byte-identical behavior is the wrong place to stop discovering subtleties mid-implementation rather than before writing the first line of the actual unwrap function. This ADR's own accumulated updates are now a complete, accurate map for whoever builds this next — including the two concrete kernel-shape decisions (the function-pointer field, the rootless read branch) already proven to compile and fit correctly. No further attempt was made this session.

## `cursor`/`consistency` — investigated, closed: not an equivalence gap

`cursor`/`consistency` is now investigated: `docs/decisions/0044` traces the actual IR/DSL/interpreters directly and finds `consistency`/`freshness`/`use_index` were never real bluebook syntax at all (zero DSL method, zero IR field, zero interpreter reader — pure comment rot in the Rust generators' own headers, the same Phase 1 stale-comment pattern), and `cursor` is real syntax that Ruby's own `seal_cursor` permanently refuses at DSL-build time — meaning Rust's existing refusal to generate for it already matches Ruby's own hard refusal exactly. `inspection` (grouped with these five in the generators' comments) turned out to be the one live discrepancy, but it resolves as a Ruby-side dead-DSL-word finding (parses, round-trips, implemented by nothing, unsealed), not a Rust equivalence gap. No code changed; this closes the investigation.

## Cross-aggregate door-argument type-bridging — shipped, on a purpose-built fixture

`docs/decisions/0045` ships this for real: a purpose-built fixture (`Roster.Retire`'s own door argument retyped to a differently-named single-field VO wrapping the same scalar as the target's declared type) dispatched correctly through real Ruby with no refusal, confirming `delegate_skip_reason`'s exact-type-name-equality check was refusing a shape Ruby genuinely supports — Ruby's own delegate mechanism (and the Rust kernel's own JSON-alias-then-deserialize mirror of it) never compares the two arguments' declared types at all. Fixed by reusing `bridgeable_value_types?`/`value_rhs` (ADR 0042's own neighbor machinery, already trusted for `sets`/`append`) in place of the exact-match check — zero change needed to the emitted Rust code itself. Real corpus (`roster`, the one domain with a real `delegates_to` door) regenerates byte-identical.

## UPDATE (same session) — `clamp` shipped too, on a purpose-built fixture

`docs/decisions/0046` ships `clamp` (Integer fields only, same scope as `multiply`) on a purpose-built fixture (`Account.ClampDailyLimit`, bounding `daily_limit.cents` into `[0, 100_000]`). Reuses the SAME target-field-eligibility half (`arithmetic_target_field`) `increment`/`decrement`/`multiply` already share; the bounds half is new (`clamp_bounds_ints` — a literal two-element Array of Integers, the one shape `classified_source` produces for a `clamp:` mutation, never an argument reference). Verified against both directions (a value above-bound clamped down, a value within-bound left unchanged) via `bin/rust_conformance ... native`, and confirmed both generators emit byte-identical code for the new path directly (not just on real corpus, which still doesn't exercise it).

## UPDATE (same session) — `remove` investigated, found to expose a REAL, ALREADY-LIVE Ruby bug

Attempting the same fixture-first discipline for `remove` found something more serious than "genuinely different emission shape," and — after an initial mis-diagnosis was caught and corrected by cross-checking against an existing passing test (`spec/fixtures/entity_list_mutations`) — something bigger than `remove:` alone: `docs/decisions/0047` — a purpose-built fixture (`CardPayment.RemoveTag`, `sets :tags, remove: :tag`) dispatched against real Ruby with **no refusal**, emitted `CardTagRemoved`, but **removed nothing**. The real root cause: `Value.for_attribute`'s `hydrate_entity_list` only ever hydrates ENTITY lists (via `find_entity`), never VALUE-OBJECT lists — so ANY bare `sets :field` (a whole-array, argument-sourced `:set`, as opposed to element-by-element `:append`) targeting a `list_of(SomeValueObject)` attribute leaves its stored elements as raw, uncoerced Hashes instead of typed `Value` instances. **This is already live in the real, shipped corpus** — confirmed directly against completely unmodified `examples/banking`: `Banking::CardPayment.Authorize`'s own `sets :tags` leaves `tags`' elements as plain `Hash`, not `Value`. It has gone unnoticed because nothing else does a strict `Value#==` comparison against list elements; `remove:` is the first mechanism to need real equality rather than field-level string comparison, so it's the first to surface the gap. `remove:` against an `append:`-built list (untested this round, no real corpus command builds one that way) may already work correctly on its own. This is not a Rust gap — there is no correct Ruby behavior to port until the representation bug is fixed on the Ruby side first; ADR 0047 scopes what a future round needs, in order.

## The honest bottom line

Eight real Phase 10 items shipped in the session's own investigate-and-port pattern (ADR 0040, 0042, 0045, 0046) — four with a real corpus fixture, four (read-model `authorize`, `multiply`, door-argument type-bridging, `clamp`) on purpose-built ones. `cursor`/`consistency` is investigated and closed (ADR 0044): not a real gap at all. `remove` is investigated and closed differently (ADR 0047): not a Rust porting gap at all, but a genuine, pre-existing, previously-undiscovered Ruby bug already live in the real corpus — `Value.for_attribute`'s `hydrate_entity_list` never hydrates a value-object list's own elements (only an entity list's), so any `sets :field` targeting a `list_of(SomeValueObject)` attribute (`CardPayment.tags`, set by `Authorize`, real and shipped today) leaves its elements as raw Hashes rather than typed `Value`s — invisible until `remove:`'s own strict equality check needed real typing and got none. There is no correct Ruby behavior to port until that's fixed on the Ruby side first.

## UPDATE (same session) — `corrects` shipped too, with explicit user authorization for its own design tradeoff

`corrects` was the one item this session's own "investigate, scope, but don't land a cross-cutting kernel change unreviewed" discipline had correctly declined to ship unilaterally (ADR 0048). Asked directly, the user chose to extend the snapshot format rather than force full replay for `corrects`-using domains. `docs/decisions/0049` ships it: the key design insight (found only once actually building it, not just scoping it) was that "has this record ever emitted event X" can live as an ordinary derived boolean field ON THE RECORD ITSELF — needing zero change to `dispatch()`'s own function signature (only `GivenSpec`, the DATA already flowing through its existing loop, gained one optional field) and zero snapshot-schema migration (the flag rides along with the record's own existing JSON round-trip, which `rust/host`'s real snapshot mechanism, confirmed directly, already persists generically). Verified end-to-end including the exact snapshot-skip-then-replay-only-new-steps production scenario ADR 0048 was worried about, via a real two-process round-trip test, not just an argument. Both generators verified in lockstep (`spec/codegen_parity_spec.rb --tag io`, 8/8, including banking's own newly-generated `CorrectFee`).

Of the one item still genuinely open in the ORIGINAL sense (a real capability worth porting, blocked on effort/scope rather than a discovered non-gap, a discovered bug, or a now-resolved design question): `group_by`/`count`/`median` needs genuinely new kernel/generator infrastructure this session did not build — a new per-read-model code-generation strategy (not a field on the existing data-driven `ReadModelDef`, confirmed by tracing `nest`/`Value.materialize_unwrapped`'s own type-level unwrapping directly) stacked on top of rootless read-model support (confirmed to not exist anywhere in this generator today). `list_of admits:/pattern:` remains additionally blocked on ADR 0043's own unresolved correctness question, structurally close but unmotivated rather than fully scoped the way `group_by` now is.

## UPDATE (same session) — `group_by` shipped too, for the one real corpus shape, with explicit user authorization

Asked directly whether to build the second code-generation strategy this item needed, the user said yes. `docs/decisions/0050` ships `group_by` for `Banking::AccountsByKind` — the one real corpus declaration, a single rootless head with `group_by` alone (no `count`/`median`/`where`/`order_by`/`authorization`). Rootless read-model support and the function-pointer-based per-read-model transform strategy this ADR's own investigation scoped were both built as designed: `ReadModelDef.reference_name` became `Option<&'static str>`, `ReadModelDef.group_by: Option<fn(Vec<(String, Json)>) -> Json>` carries a bespoke generated transform per declaration, and a hand-written `kernel::read_model::nest()` does the actual grouping via `Json`'s own `PartialEq`. The recursive, type-directed unwrap this ADR's own investigation identified as the real remaining unknown was built exactly as scoped — walking both `value_objects_by_name` and `aggregate[:entities]` — plus one refinement the investigation didn't anticipate: Ruby's own `sole_attribute` has no closed-set exclusion at all, so a closed-set VO with one attribute (`AccountKind`) unwraps exactly like any other single-attribute VO, found by testing rather than assumed. Verified independently of `bin/rust_conformance`'s own shallow comparison (which doesn't check query content at all) via a direct Ruby-`Fuzzing::Replay`-vs-Rust-native-binary content diff, including a real entity-nested-VO case. Both generators verified byte-identical (`spec/codegen_parity_spec.rb --tag io`, 8/8). `count`/`median` remain out of scope — they need a genuinely separate two-head-join framework, not an extension of this rootless design.

`list_of admits:/pattern:` remains the one item in this ADR's own original scope still blocked on ADR 0043's unresolved correctness question.

## UPDATE (same session) — `list_of admits:/pattern:` resolved too, by removing a real Rust over-enforcement rather than porting a new capability

ADR 0043's own left-open question — whether a bare command-attribute's `admits:`/`pattern:` has any real Ruby enforcement at all when never a `sets` source — is now answered exhaustively (`docs/decisions/0051`): `admits:` IS enforced unconditionally for scalar attributes (Rust already matched, kept as-is); `pattern:` at that same usage-level door is NEVER enforced by Ruby, scalar or list, mutated or not — `check_patterns` fires only via a value object's own `build`, which a usage-level scalar attribute never triggers. Rust's own unconditional `emit_pattern_check` call made it stricter than the reference implementation — removed, per ADR 0010. The list case itself needed no new per-element checking machinery at all: the existing `unless attr[:list]` skip was already the correct generated behavior; the only bug was the surrounding refusal (`constraint_list_problems`) that stopped such a command from generating entirely, also removed. Verified red-before/green-after against a real purpose-built fixture dispatched through Ruby's own interpreter, with both generators confirmed byte-identical for the one shape neither real corpus nor `spec/codegen_parity_spec.rb` exercises.

With this, `group_by`, and `count`/`median` (`docs/decisions/0052`) all closed, every item ADR 0041 itself scoped as "structurally close, not yet shipped" is now resolved — the two-head-join framework `count`/`median` were assumed to need turned out not to be needed at all (0052's own finding: they reuse the SAME single-root, single-filtered-many-side-head machinery `ComplianceDashboard` already exercises, just reducing the filtered row set instead of returning it).
