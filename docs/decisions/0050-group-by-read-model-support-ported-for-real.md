# `group_by` read-model support — ported for real, for the one real corpus shape

**Status:** Shipped, with explicit user authorization. ADR 0041 named `group_by`/`count`/`median` as the last open items in Phase 10's read-model backlog. The user was asked directly whether to build real code-generation support for them now; the answer was "yes, implement it now." This ADR ships `group_by` for the one shape the real corpus actually declares — a single, rootless aggregate head, grouped, with no `count`/`median`/`where`/`order_by`/`authorization` alongside it (`Banking::AccountsByKind`). `count`/`median` need a genuinely separate, harder two-head-join framework and remain explicitly out of scope for this round, same as ADR 0041 already scoped them.

## Why this needed a second, real code-generation strategy, not one more field

Every other read-model shape this generator already ports (`ReadModelDef` in `rust/src/kernel/read_model.rs`) is data-driven: one generic `run()` function reads a struct's declared fields (`reference_name`, `wheres`, `order_by`, ...) and interprets them uniformly at runtime. `group_by` can't fit that shape, because **which field of a serialized JSON value is a single-attribute value object worth unwrapping is a TYPE-LEVEL fact** — known at codegen time from the aggregate's own IR, gone by the time the kernel is holding a generic `Json` blob at runtime. Ruby's own interpreter gets this for free (`Value.materialize_unwrapped` walks the live domain's own class metadata at runtime); Rust's kernel has no such metadata to walk. So `group_by` needed a bespoke, PER-READ-MODEL generated function, referenced by a function pointer (`ReadModelDef.group_by: Option<fn(Vec<(String, Json)>) -> Json>`) — the first read-model capability in this codebase generating a whole function body per declaration rather than one more data field.

## What was ported

**Kernel** (`rust/src/kernel/read_model.rs`):
- `ReadModelDef.reference_name` widened to `Option<&'static str>` — every prior read model has one; `group_by`'s one real shape is rootless and has none. `run()`'s reference-id resolution and root/scan-matching branches all made conditional on this.
- A rootless head-read branch: when `reference_name` is `None`, each head reads its own aggregate's whole table directly via the pre-existing `store.scan(head.aggregate)` (`AggregateScan`, already id-ascending, matching Ruby's own default ordering) — never joined against anything else, matching Ruby's own "each rootless head reads its own aggregate's whole table, independently" rule (`ReadModelInterpreter#group_by_target`).
- `ReadModelDef.group_by: Option<fn(...) -> Json>` — the function-pointer field. When present, the matching head's rows are run through it instead of the ordinary per-row wrapping, and the transform's own `Json::Object` result becomes the read model's whole answer.
- A new, hand-written `kernel::read_model::nest()`: groups rows by a list of field names using `Json`'s own `PartialEq` (a `Vec`-based linear scan, not a `HashMap` — `Json` has no `Hash` impl, and Ruby's own `Hash#group_by` preserves first-occurrence key order, which a linear scan matches and a hash table would not). Recursively strips one field per nesting level, JSON-object-key-stringifies the grouping value via `query_comparators::to_s` (made `pub(crate)`, reused rather than re-implemented — matches Ruby's own implicit `Hash#[]=` key-to_s coercion).

**Both generators** (`rust/project/read_models.rb`, mirrored in `rust/codegen/src/read_models.rs`):
- `group_by_skip_reason`: real per-declaration eligibility — single head, rootless (`reference_target` absent), no `count`/`median_field`, no `where`/`order_by`/`limit`/`offset`, no `authorization`, then validates every declared `group_by` field row (`row[:field]`, not the row itself — see bug note below) names a real attribute or the lifecycle field.
- `emit_group_by_transform(fn_name, aggregate, group_by_fields)`: generates the whole `pub fn` — wraps each row as `row_json`-equivalent (id + declared attributes + lifecycle field only, which by construction excludes any OTHER synthetic field like `corrects`'s own `emitted_*`, since those are never listed in `aggregate[:attributes]`), applies a recursive unwrap to every attribute, then calls `kernel::read_model::nest`.
- `unwrap_json_expr`: the recursive, type-directed unwrap generator. Walks BOTH `value_objects_by_name` and `aggregate[:entities]` — entities are a separate IR construct from value objects, and Ruby's own `materialize_unwrapped` recurses into them identically via its own `when Hash` branch, so the generator has to match that, not just handle value objects.
- `pub fn` visibility (not `fn`) — required because `merged.rs` (a separate generated file from `registry.rs`) references the function by bare name from a different module.

## Two real bugs found and fixed during this port

1. **IR shape**: `read_model[:group_by]` is an array of hashes (`[{field: "kind"}, ...]`), not bare strings. First attempt did `.map(&:to_s)` on the whole row, producing the STRING REPRESENTATION of a Hash (`"{:field=>\"kind\"}"`) instead of the field name — confirmed against `lib/hecks/bluebook/behaviour/read_model.rb`'s own `@group_by.map { |row| row.merge(field: row[:field].to_s) }` and fixed to read `row[:field]`.
2. **Closed-set value objects were wrongly excluded from single-field unwrap.** First attempt required `!vo[:closed_set]` before unwrapping a one-attribute VO — this broke `AccountKind` (closed-set, one `name` attribute), whose group-by key stayed as `{"name":"current"}` instead of unwrapping to bare `"current"`. Verified the actual rule directly from Ruby's `Behaviour::ValueObject#sole_attribute` (`attributes.first if attributes.size == 1` — no closed-set exclusion at all) rather than assuming; removed the guard.

## A gap in the existing verification harness, found and fixed along the way

`bin/rust_conformance`'s own comparison never covered query results at all (`instances`/`events`/`refusals` only) — so an initial "matches." result did not actually validate `group_by`'s own output content. Caught this directly rather than trusting the shallow check, and built an independent comparison (raw native-binary stdout vs. Ruby's own `Fuzzing::Replay.call(...)[:queries]`, diffed by direct Python dict equality) — this is what caught bug 2 above, which the shallow check would have missed entirely.

Separately, `spec/rust_conformance_spec.rb` and `spec/rust_conformance_fuzz_spec.rb` — the actual RSpec-level differential harnesses, distinct from the `bin/rust_conformance` script — turned out to have never been updated for `corrects`'s own synthetic `emitted_*` record fields (ADR 0049 fixed only the standalone script). Both specs' comparisons leaked `emitted_fee_applied` into failing diffs the moment `group_by`'s own `read_models.json`/`query_filters.json` fixtures put a `Banking::Account` record through a `queries` answer (a comparison surface the standalone script's fix never touched). Fixed with a single shared, recursive `strip_emitted_flags!` helper in `spec/support/rust_conformance_helpers.rb`, applied to both `instances` and `queries` in both specs — this was a real, live gap in already-shipped, already-committed work, not something introduced by `group_by` itself, just first exposed by it.

## Verification

- **Functional correctness, verified independently of the shallow harness**: two real-corpus scripts against `Banking::AccountsByKind` — one with three accounts of mixed kinds (current/savings/current), one adding a `Credit` to populate a real entity (`ledger`) — both compared via raw native-binary stdout vs. Ruby's own `Fuzzing::Replay.call` output, exact dict equality on both, including correct entity-nested value-object unwrap (`"narrative"`, `"direction"`, `"sequence"` all correctly flattened from their VOs).
- **Both generators verified in lockstep**: `spec/codegen_parity_spec.rb --tag io`, 8/8 domains byte-identical (including a genuine whitespace-fidelity fix — Ruby's `<<~RUST` squiggly-heredoc dedent produces a quirky 12-space-first-arm/20-space-rest indentation in `emit_group_by_transform`'s generated `match` arms; the Rust codegen crate's plain `format!`-based string building had to reproduce that exact byte pattern, not just equivalent whitespace).
- **`spec/rust_conformance_spec.rb spec/codegen_parity_spec.rb --tag io`**: 30/30 examples, 0 failures (was 12 failures before the `emitted_*`-in-queries fix above — all traced to the pre-existing gap, none to `group_by` itself).
- **`spec/rust_conformance_fuzz_spec.rb --tag io`**: 0 failures (2 pending, logging pre-existing, already-documented refusal-wording gaps unrelated to this change).
- Full sweep: `bundle exec rspec` (2232/0), `bundle exec rubocop` (645 files, 0 offenses).
- Every real domain builds clean: `cargo build --no-default-features --features <domain>` for banking, compliance, pizzas, roster, meta. (`embryonaut` fails to build on this branch independent of this change — confirmed via `git stash` — a pre-existing gap from a stale hand-patched generated file, not a regression from this work.)
- All real corpus domains besides banking regenerate byte-identically — no unintended drift from the rootless-read-model kernel change.
- `git status` confirmed clean of unrelated byproduct drift (`Cargo.toml`/`mod.rs` default-feature bookkeeping, `governance` framework-regen attribution-comment churn) before commit.

## What's still out of scope

`count`/`median_field` — genuinely need a two-head-join framework (correlating a "counted" aggregate against a "counting" one), not an extension of this rootless/function-pointer design. Left for a future round, same as ADR 0041 already scoped.

**UPDATE (same session)**: this framing was wrong. `docs/decisions/0052` ships both — they turn out to need no two-head-join framework at all, reusing the SAME single-root, single-filtered-many-side-head machinery `ComplianceDashboard` already exercises (`DisputedPaymentCount`/`DisputedPaymentMedian` are rooted, not rootless, unlike `AccountsByKind`), reducing the filtered row set instead of returning it as rows.
