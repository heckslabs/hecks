# Cross-aggregate door-argument type-bridging — ported for real

**Status:** Shipped. ADR 0041 listed cross-aggregate door-argument type-bridging as "not yet investigated." Investigating it directly, against real Ruby behavior via a purpose-built fixture, found a genuine equivalence gap — Rust refuses to generate a `delegates_to` door whenever its own argument's declared type name differs from the target's, even though Ruby happily dispatches exactly that shape — and the fix reuses machinery this session had already built and trusted (`bridgeable_value_types?`/`value_rhs`, ADR 0042's own neighbor).

## The refusal

`delegate_skip_reason` (`rust/project/commands.rb`, mirrored in `rust/codegen/src/commands.rs`) refused to generate any `delegates_to "Entity.Command", with: {...}` door whose mapped source argument's declared type name didn't EXACTLY match the target entity command's declared type — `"door argument #{source_name} is #{source[:type]}, target wants #{attr[:type]} — not generated yet"`.

## Zero real corpus motivation, but for a different reason than usual

Grepping every `.bluebook` file in `examples/` for `delegates_to` finds exactly three real doors — chess's `MovePiece`/`CapturePiece` and roster's `Retire` — and **all three pass their door argument straight through with an identical declared type name** (`PieceId`→`PieceId`, `Square`→`Square`, `MemberId`→`MemberId`, etc.). So unlike `multiply`/`clamp`/`list_of admits:/pattern:` (ADR 0041), this refusal has never fired on real corpus content either — but that turned out to be incidental, not because the capability itself is speculative. A purpose-built fixture (a temp copy of `examples/roster`, `Roster.Retire`'s own door argument retyped from `MemberId` to a new, differently-named single-field String VO `RetireeRef`, target left declaring `MemberId`) dispatched correctly through Ruby's real interpreter — `MemberRetired` emitted, no refusal — confirming Ruby genuinely supports this shape and the "no real corpus example" fact was just that nobody had needed a differently-named door argument yet, not that the feature doesn't work.

## Why Ruby doesn't care about the type-name mismatch at all

`CommandInterpreter#step_delegate_to_entity` (`lib/hecks/runtime/command_interpreter.rb:187`, read directly): `target_args = ctx.args.merge(delegation.source.to_h { |target_key, source_key| [target_key.to_sym, ctx.args[source_key]] })` — this copies the door's own RAW wire value under the target's argument name and hands it to the target command exactly as if a caller had dispatched the target directly. It never once compares the two arguments' DECLARED type names — the target's own `Value.for` coercion is what makes sense of the value, at dispatch time, the same way it would for any other argument.

The Rust kernel's delegate mechanism mirrors this exactly at the JSON level, not a typed Rust-level field copy: `Json::with_aliases` (`rust/src/kernel/json.rs:312`) — its own doc comment literally cites the Ruby line above — copies the door's raw JSON value under the target key, and `TmplTargetArgs::from_json` (the target's own `Deserialize`) does the actual coercion. Confirmed in the generated fixture output: `let delegate_facts = args.to_json().with_aliases(&[("id", "id")]); let target_args = MemberRetireEntityArgs::from_json(&delegate_facts)?;` — no typed struct-field assignment between `RetireeRef` and `MemberId` ever happens; the target's own deserializer decides, from the raw JSON, exactly as Ruby's `Value.for` does. **The refusal was guarding against a problem that doesn't exist in this mechanism at all** — it was checking a static type-name equality neither engine's own real dispatch path ever requires.

## The fix — reuse `bridgeable_value_types?`, not a new mechanism

`bridgeable_value_types?`/`value_rhs` (`rust/project/bridging.rb`) already answer exactly this question — "is copying source into target semantically sound" — for `sets`'/`append`'s own RHS, checking VO field-NAME alignment, closed-set member coverage, and scalar-representation equivalence (`effective_scalar_type`). That is precisely what the JSON-alias-then-deserialize mechanism cares about too: the target's `from_json` will succeed exactly when the source's own JSON shape carries the field names the target expects, which is what `vo_field_bridgeable?` (field-name matching) already checks.

`delegate_skip_reason`'s exact-type-equality check was replaced with `bridgeable_value_types?(source[:type], attr[:type], value_objects_by_name)` in both generators, keeping the separate list-ness check (`bridgeable_value_types?` doesn't reason about lists, and no real or fixture motivation existed to widen that dimension too — left exactly as strict as before). No change was needed to the EMITTED Rust code (`aliases`/`with_aliases`/`from_json`) at all — the mechanism already handles arbitrary JSON reshaping; only the compile-time refusal was too conservative.
