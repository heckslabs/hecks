# `checks_codegen_drift` auto-discovers its own domain list, instead of a maintained one

**Status:** Adopted. `bin/regen_codegen_domains` (2026-09-13) replaces `.github/workflows/ci-checks.yml`'s `checks_codegen_drift` step's hand-maintained list of `bin/project_rust <domain>` lines with a walk over `examples/`, `qa/stress_domains/`, and `spec/fixtures/rust_project/` that regenerates any domain already carrying committed output under `rust/src/generated/<name>/`.

## The recurring failure this closes

The step exists to catch Rust codegen drift on the push that caused it, per its own header (see docs/decisions/0037's own finding — a Ruby-side `given` grew with nobody regenerating, and every coverage/conformance check that only reads the committed tree stayed green because the committed tree itself was wrong). But the step's own mechanism — a hardcoded list of domains to regenerate — carried the identical failure mode one level up: a domain not on the list was never regenerated by CI at all, so its own committed Rust output could silently drift arbitrarily far behind its Bluebook source, with nothing catching it until an unrelated differential fuzz sweep tripped over the staleness and reported what looked like a fresh Ruby/Rust divergence — actually the same already-fixed bug, just never regenerated into the artifact being fuzzed.

Confirmed recurrences, by name: `nested_pieces` (BUG#23), `referral_chain`, `has_many_fixture` (BUG#25), `lease_clock`, `corrections` (BUG#126), `chess` (BUG#138), `generated_entity_no_identity` (BUG#122 — whose own fix, PR #652, claimed to add it to the list but never actually did: `git show 63102c4d -- .github/workflows/ci-checks.yml` is empty). `tenant_ledger` was a long-acknowledged, deliberately-unfixed instance of the same gap, named in the step's own comment rather than silently patched as a drive-by. Auditing the repo directly while building this fix found the gap wider than even that history had caught: `generated_reaction_wording`, `generated_revalued_shape`, `generated_route_append`, and `bug28_existence_fixture` all had real, committed `rust/src/generated/` output and were not on the list either — no fuzz sweep had tripped over any of the four yet.

Every one of those additions to the old list, and PR #664's attempt at one more (`generated_entity_no_identity`, open and unmerged when this ADR landed), was the same one-line manual patch: find a stale domain, add its `bin/project_rust` line, re-verify the diff by hand. The user's own framing: "can we do something to make this mechanical" — this ADR is that fix.

## The mechanism

`bin/regen_codegen_domains` (its own header carries the full argument in more depth):

1. **Discover.** Walk every immediate subdirectory of `examples/`, `qa/stress_domains/`, `spec/fixtures/rust_project/`. A candidate becomes a domain to regenerate if and only if it already has committed output at `rust/src/generated/<name>/` — the same rule the old list always followed by convention (every domain on it was added only after a human ran `bin/project_rust` once by hand and committed the result), now self-enforcing instead of relying on someone also remembering to edit `ci-checks.yml`.
2. **Exclude.** `EXCLUDED_DOMAINS = ["embryonaut"]` is a defensive guard, not the real mechanism — `embryonaut`'s Bluebook source lives in a separate client repo, so no `examples/embryonaut`/`qa/stress_domains/embryonaut`/`spec/fixtures/rust_project/embryonaut` directory exists in this checkout for the walk to ever find. It stays coverage-checked against its own committed snapshot only, unchanged from before.
3. **Sort, deterministically.** By full relative path (`examples/*` before `qa/stress_domains/*` before `spec/fixtures/rust_project/*`, alphabetical within each). This matters because every domain that `uses_framework "Governance"` (or `"Identity"`) regenerates that framework's shared `rust/src/generated/<framework>/` output as a side effect, and each pass re-stamps its "GENERATED by ... examples/<domain>" attribution comment with whichever domain ran last — real, load-bearing text a diff check would otherwise flag every run. `rust/Cargo.toml`'s `default` feature and `rust/src/generated/mod.rs`'s domain-exclusivity `cfg`s track whichever domain ran last, period. A fixed, mechanical sort makes "which domain wins" a checkable fact instead of a hand-verified ordering someone re-derives from scratch on every addition.
4. **Regenerate each in order**, then run the same `git diff --exit-code -- rust/src/generated/ rust/Cargo.toml` gate the step always ended with.

The workflow step itself is now one line: `bundle exec bin/regen_codegen_domains --check`.

## Consequences of the new sort, landed in the same commit

`tenant_ledger` (`uses_framework "Governance"`, like `banking`/`compliance`/`pizzas`/`nested_pieces`) is now the alphabetically-last Governance-using domain, so it now wins `rust/src/generated/governance/`'s attribution stamp — previously `nested_pieces` won it, only because `tenant_ledger` was never on the list. `banking` remains the sole `uses_framework "Identity"` domain, so it keeps winning `identity/`'s stamp regardless of order. `spec/fixtures/rust_project/has_many_fixture`, alphabetically last overall, now wins `rust/Cargo.toml`'s `default` feature and `mod.rs`'s cfg comments — previously `waybill`, only because it was hand-placed last. All three are regenerated for real into the committed tree by the same commit that introduced this mechanism, not left as a follow-up.

## Proof of the actual claim

A throwaway toy domain (`qa/stress_domains/zzz_toy_regen_proof`, a minimal single-aggregate Bluebook) was added the normal way — write the Bluebook, run `bin/project_rust` on it once by hand, commit the output — with zero edits to `ci-checks.yml`. `bin/regen_codegen_domains --check` picked it up automatically (19 domains discovered instead of 18), and correctly flagged real drift left over from the single-domain run (the `default` feature reverting from the toy domain to `has_many_fixture`, the true alphabetically-last domain once the full deterministic sequence ran) — confirming both halves of the mechanism: discovery finds a new domain with no `ci-checks.yml` edit, and the check gate still catches real drift. The toy domain was reverted before this branch's real PR; it was never a genuine corpus addition.

## Verification

- `bin/regen_codegen_domains` (no `--check`) run against a clean checkout discovered and regenerated all 18 real domains (12 from the old list, plus `tenant_ledger`, `generated_entity_no_identity`, `generated_reaction_wording`, `generated_revalued_shape`, `generated_route_append`, `bug28_existence_fixture`), producing real content diffs for all six additions — not just attribution-comment churn — confirming each really had drifted.
- `bin/regen_codegen_domains --check` against the resulting committed tree exits 0 (no diff) — the new deterministic order is stable and idempotent.
- Full local suite (`bundle exec rspec`), `rubocop`, `bin/model_check`, and `bin/doc_coverage` all green against the regenerated tree.
