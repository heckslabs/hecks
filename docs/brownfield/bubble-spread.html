The idea

A bubble is a chapter wrapped around legacy

Evans called it a bubble context: a small, clean bounded context built inside a legacy system, protected by an anti-corruption layer. In Hecks it needs no new keyword. It is a chapter, loaded into a host like any other, whose hecksagon binds to the legacy systems.

  • Legacy keeps working. Nothing in it has to change for the first step. The bubble sits beside it.
  • The model stays clean. Legacy field names, table shapes and vendor quirks stop at the hecksagon and never reach the bluebook.
  • Callers move one at a time. Each legacy entry point is repointed at the bubble's commands when it is ready, which is the strangler pattern.
  • Several bubbles, one host. Refunds, Onboarding and Inventory are separate chapters that talk through translates, uses_framework and cross-domain policies.

The parts

Given a bluebook, supply adapters and settings

Building an integration should mean writing no application code. A company takes a bluebook (written once, shared) and supplies two things of its own.

PartHoldsWho supplies it
BluebookThe clean model and its ports: the aggregates, commands, events and the outside services it needs, named as ports. Says nothing about any one company.Shared, vendored, versioned
HecksagonWhich adapter fulfils each port, and the field mappings from legacy shapes to the bluebook's language. Inbound adapters that watch legacy live here too.The company
WorldPer-environment settings: base URLs, tenant ids, credential references (never values), rate limits, and the read-only switch. Dev, staging and prod are different worlds over one hecksagon.The company, per environment

Check before boot. The model check refuses a hecksagon that leaves a port unbound or binds an adapter to a port it does not implement, and refuses a world that lacks a setting an adapter declares as required.

The path

Five steps from watching to retiring

A company can stop at any step and still have something useful. Each step adds trust before it adds risk.

1

Watch

Read-only. The bubble's state is a view built from legacy. Nothing can write.

2

Shadow

The bubble computes its own answers on real traffic and compares them with legacy's. None take effect.

3

Write through

Commands in the bubble now call legacy through the hecksagon. Rules live in one declared place.

4

Take over

One aggregate's source of truth moves into Hecks storage. Legacy becomes the downstream copy.

5

Retire

Nothing reads the old system. Its adapter is deleted and the chapter stands alone.

What the company gets along the way

  • One vocabulary over systems that each name things differently.
  • One audit trail across systems that had none.
  • Swappable vendors. Moving from one payments or CRM provider to another is an adapter change.
  • Safe agent access. An agent works through declared commands and never touches the legacy database.
  • Rules in one place, in place of stored procedures, spreadsheets and cron scripts.

Where it gets hard

  • Dirty data. Rows that fit no aggregate need a reviewable quarantine with a reason, not an error.
  • Two writers. While both systems accept changes, a cutover needs a written procedure. The transactional outbox gives retries an owner.
  • Systems that change on their own. A legacy app that writes straight to its database needs polling, change capture or webhooks, or the bubble drifts.
  • Modeling discipline. A bluebook that mirrors the legacy schema gains nothing.

Read-only is a setting, not a promise. Step 1 depends on the adapter client refusing writes when the world says read-only, and on the model check confirming that a read-only adapter exposes no write operations.

The plumbing

Prewritten adapters, as thin wrappers

Each adapter calls a shared client and adds only what is particular to its service. The per-service part is data, so it is written once and read by both the Ruby and Rust runtimes.

Shared transport clients

  • Http. Base URL, auth, retries, rate limits, pagination, error mapping.
  • Cli. Argv, environment, exit codes, output parsing. Builds on the existing Shell adapter.
  • Protocol. SQL, SFTP and files, SMTP, SOAP, queues and webhooks. These are the workhorses of brownfield, since legacy mostly speaks them.

Per service

  • A declarative mapping from a port ask to a request: method, path, body, response fields, auth scheme.
  • Credentials by reference, resolved at run time and never on disk.
  • A recorded-response fixture checked against the conformance corpus in both runtimes, so drift fails the build.
  • An escape hatch for services that do not fit the table, flagged as a known parity gap until ported.

Worked example

A Supabase adapterDesign sketch, not built

Supabase is the first service we would wrap, because one project is a legacy database, a change feed, an identity provider and a file store behind a single key. It exercises every part of the design.

Supabase givesReached throughWhich bubble port
Postgres tablesREST (/rest/v1) or SQLPersistence and read models
Realtime, database webhooksChange feed, HTTP callbacksInbound change events (the role a tap plays)
Auth/auth/v1Identity
Storage/storage/v1Files
Edge functions/functions/v1Outbound asks

1. The adapter declaration

The same two-file shape every adapter has today: this file says what it binds and which settings it needs.

Hecks.adapter "Supabase" do
  port   "persistence"
  field  :url
  secret :service_key
  field  :read_only
end

2. The hecksagon binds the model

The clean aggregate is bound to the company's existing tables.

Hecks.hecksagon "Refunds" do
  Refunds::Refund.persisted_by("Supabase")
end

3. The world supplies the environment

URL and mode vary by environment. The key is a secret, read from the environment and never written in a file.

url:         the project's API URL
service_key: from the secret store
read_only:   true      # step 1

What the shared client does

  • Sends the apikey and bearer headers, filters with query operators, and pages with ranges.
  • Refuses every write while read_only is true.
  • Maps table columns to aggregate fields from the hecksagon's mapping, so legacy names stop here.

Open point this example raises. The persistence port is append-before-project, and an existing table has no journal. For step 1 the bubble should read the table as a projection, and a table that takes writes needs a different port or a journal built beside it. Settle this before the first slice.

Next

Beyond adapters, and what is open

More ways to help a company move

  • Importer. Point it at a schema, an OpenAPI spec, a CLI's help or a CSV export and it drafts a chapter and hecksagon for a person to edit. This removes the blank page.
  • Shadow mode. Real traffic, compared answers, no effect. A mismatch report is a plain go or no-go signal.
  • Drift report. What the bubble holds against what legacy says, on demand.
  • Characterization capture. Record real inputs and outputs from legacy and turn them into conformance fixtures.
  • Rules extraction. Surface candidate invariants from stored procedures and scripts for a person to approve.
  • Reference bubbles. Prebuilt chapters for common domains, so a company writes only its hecksagon and world.
  • Cutover playbook. Generated per bubble, with the checks and rollback for each step.

Build order

  • 1. Port declarations, adapter-to-port checks and typed world settings in the model check.
  • 2. Transport clients and the data-driven adapter format, Ruby and Rust.
  • 3. First slice: Stripe, Slack, gh, generic SQL and webhooks, with fixtures.
  • 4. The rest of the catalog.
  • 5. Importer, then shadow mode and the drift report.

Settled

  • A bubble is a chapter plus its hecksagon, not a new construct.
  • The model check guards the generated wiring.
  • Adapters are thin wrappers over shared clients.

Open. Whether the field mappings live in the hecksagon (the recommendation, so the hecksagon is literally the translation layer) or in the world. Whether each chapter carries its own hecksagon (recommended) or the host has one. How read-only is enforced and checked. Whether the catalog and transport layer keep these working names.
