# Comment style guide (Rust)

The standard for comments in this repository's Rust: `rust/`, hand-written
files only. A file whose first line reads `// GENERATED by ...` belongs to
its generator (`bin/project_rust` and friends) — fix its wording in the
Ruby template that emits it, not in the `.rs` output. `bin/standardize_comments_rust`
checks the parts of this guide a machine can check, and skips generated
files entirely.

Nothing enforces this in CI. `bin/standardize_comments_rust` is run by hand.

This guide is the Rust sibling of `docs/COMMENT_STYLE_GUIDE.md`, which
governs this repository's Ruby. The two agree wherever Ruby and Rust agree
(prose, history, emphasis, line length); they differ where the languages'
own doc-comment conventions differ (YARD tags vs. rustdoc sections).

## 1. Public items carry a `///` doc comment

Every `pub fn`, `pub struct`, `pub enum`, `pub trait`, `pub mod`, and
`pub type` gets a doc comment directly above it, in rustdoc form:

```rust
/// Finds the single adapter bound to a port, refusing an ambiguous wiring.
///
/// # Errors
///
/// Returns `WiringError::Ambiguous` if more than one adapter implements
/// `port`, and `WiringError::Missing` if none does.
pub fn adapter_for(registry: &Registry, port: &str) -> Result<&Adapter, WiringError> {
```

- **Lead sentence.** Required. It starts with a verb (third person: "Finds",
  not "Find"), says what the item does for its caller, and adds something
  the name does not. A blank `///` line separates it from any sections
  below. Existing prose that explains *why* stays, above the sections.
- **`# Errors`** for a `fn` returning `Result`: what condition produces
  which `Err` variant, in the words a caller would use to decide how to
  handle it.
- **`# Panics`** for a `fn` that can panic on some input (an `unwrap`,
  `expect`, indexing, or arithmetic that isn't checked) — what input
  triggers it.
- **`# Safety`** for every `unsafe fn`: the invariant the caller must
  uphold that the compiler cannot check.
- **`# Examples`** only where a usage isn't obvious from the signature and
  the lead sentence; most items don't need one.
- A struct or enum's doc comment says what it represents, not what fields
  it has — the fields are the code, right below.
- A line that would pass 100 characters continues on the next line, at the
  same `///` indentation.

### Exemptions

- A method inside `impl SomeTrait for Type { ... }` takes no doc comment of
  its own when the trait's own contract is the whole story (`Display::fmt`,
  `Debug::fmt`, `Default::default`, `Clone::clone`, `PartialEq::eq`,
  `Hash::hash`, `From::from`, `Iterator::next`, and similarly fixed
  contracts). Rust itself doesn't let a trait impl's methods take a `pub`
  keyword, so this exemption falls out automatically — nothing to remember.
- `pub fn main()` needs nothing; it is an entry point, not API.
- Items inside a `#[cfg(test)]` module are test scaffolding, not API, and
  take no doc comments. A file under `rust/*/tests/` is a whole integration
  test and is exempt entirely.
- `pub(crate)` and `pub(super)` are not public API in the sense this rule
  means; only unrestricted `pub` items are covered. A private item takes a
  doc comment only when its logic is not obvious from its name and body —
  same as Ruby's private-method rule.

## 2. Modules: `//!`, what it is, not what it contains

Every `mod.rs`, `lib.rs`, and `main.rs` opens with a `//!` module doc
saying what the module is, why it exists as its own thing, and, where it
helps, what it is not. It never inventories the items below it.

```rust
//! The one place that knows the sandbox and the journal both exist.
//!
//! ## Why one function, not two
//!
//! `PolicyInterpreter#react` and `SagaInterpreter#advance`, the Ruby
//! originals this ports, run off the same announced-event list in one
//! pass — splitting them here would silently reorder log entries.
```

A comment longer than about 25 lines is broken up with `##` Markdown
headers, the same threshold as Ruby.

## 3. Code comments explain why

A comment earns its place by saying what the code cannot: why this
approach and not the obvious one, which edge case a line exists for
(stated at that line), or which invariant the surrounding code relies on.

```rust
// nil first: Postgres and the in-memory store disagree on NULL ordering by
// default, so this pins it rather than depending on either engine's own
// comparator.
rows.sort_by(|row| (row.get(field).is_none(), row.get(field).cloned()));
```

A comment that narrates the next line in English is deleted. If the code
needs narrating, it needs a better name or an extracted function.

## 4. No design history

Comments describe the system as it is. The linter flags "used to", "was
originally", "previously", "formerly", "historically", "renamed from",
"before this change/fix", "an earlier version/draft", "has since", and a
bare pull-request number (`PR #123`).

Rewrite the comment in the present tense and keep the reason, which is the
valuable part:

```rust
// Before: This used to raise, which hid a half-written snapshot. It now
//         returns nil.
// After:  Returns nil rather than raising, because raising hides a
//         half-written snapshot.
```

The history itself belongs in `docs/decisions/NNNN-slug.md`. A comment may
cite an ADR, an audit document, a spec, or a bug ID that already exists.
Never invent one.

## 5. Markdown emphasis, never all caps

This is the rule this codebase's Rust comments depart from the most: long
stretches of hand-written prose here lean on shouted capitals for
emphasis — whole clauses, not just single words. All-caps is not emphasis
here either. Use backticks for identifiers, `##` headers for structure,
and `**bold**` sparingly.

The one routine use of bold is a paragraph's heading phrase, the short
lead-in before a dash or full stop:

```rust
// **Hand-written, once, generic** — a direct port of `Dispatcher#dispatch`'s
// own reaction plumbing.
```

Emphasis on a single word in running prose is normally just dropped:
`the SAME call` becomes `the same call`. Keep it, as bold, only where the
sentence misreads without it.

Capitals stay where they are the correct spelling: initialisms (`SQL`,
`JSON`, `WASM`, `ADR`), SQL written as SQL, proper nouns (`Rust`, `Ruby`,
`Postgres`), and constant/static names. A `SCREAMING_SNAKE_CASE` constant
named in prose goes in backticks (`` `POLICIES` ``); the linter reports a
bare one as `bare_constant` because it cannot tell a reference from a
shout — decide by reading the constant's actual definition.

## 6. Comment lines stay under 100 characters

Wrap at a word boundary. Do not break inside a backtick span or a URL.

## Checking a tree

```
bin/standardize_comments_rust --report rust                        # summary tables
bin/standardize_comments_rust --check  rust                        # one line per violation
bin/standardize_comments_rust --fix    rust                        # all_caps and long_line only
```

`--fix` rewrites only the two mechanical categories, the same restriction
as the Ruby tool: an all-caps run that opens a paragraph and ends before a
dash becomes a bold heading; a lone shouted word is recased to fit the
sentence. Everything else — `missing_doc`, `missing_module_doc`,
`bare_constant`, `unknown_capitals`, `design_history` — needs someone to
read the code, so the fixer leaves it alone.

The prose rules (`all_caps`, `bare_constant`, `design_history`,
`unknown_capitals`) share their acronym list, proper-noun list, and
English word list with `bin/standardize_comments` (the Ruby linter), so a
name added to either language's exemptions there is recognised in both.

## Known gap: doc-comment coverage

`missing_doc` is the one category sized like a second project, not an
afternoon: roughly 400 public items across `rust/` currently have no `///`
at all (mostly small, self-explanatory `fn`s where a one-line summary
would still be non-trivial to write well for hundreds of call sites at
once). This guide and linter land the mechanical pass — no more shouting,
no more design history, no stray bare constants — the same way
`docs/COMMENT_STYLE_GUIDE.md`'s Phase 1 did for Ruby before its later
RDoc wave filled in undocumented methods directory by directory. Filling
`missing_doc` in Rust is that same kind of follow-up, not part of this
pass: run `bin/standardize_comments_rust --check --only missing_doc rust`
to see the current list.
